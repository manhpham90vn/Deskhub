# Deskhub — アーキテクチャ

本書は Deskhub が**どう作られているか**を記述する。レイヤ、プロセスとスレッド、ワイヤ
プロトコル、そしてその背後にある設計判断である。製品がユーザーから見て何をするかは
[`SPECIFICATION.ja.md`](SPECIFICATION.ja.md) に、脅威モデルは
[`SECURITY.ja.md`](../SECURITY.ja.md) にある。

本書は [`ARCHITECTURE.md`](ARCHITECTURE.md) の翻訳である。相違がある場合は英語版が正典と
なる。

- **状態：** 現在のコードを記述している。
- **読者：** コードを変更するすべての人。

## 1. レイヤ

全体の配置をひとつの規則が支配している：ロジックは一度だけ書き、すべてのクライアントで
共有する。

```
core/       純粋な C++20。OS ヘッダなし、サードパーティコードなし、オフラインでユニットテスト
platform/   ヘッダごとに同一の API を 1 つ持つ薄い OS 抽象（core に依存）
client/     OS ごとのアプリ：windows、linux、macos、ios、android（platform + core に依存）
            さらに client/cli、デスクトップ 3 種共通のコマンドラインクライアント
```

| レイヤ | 内容 |
| --- | --- |
| `core/protocol` | ワイヤフォーマット（`Wire.h`）、ストリーム用のレコードフレーミング（`RecordStream.h`）、QUIC と Deskhub のビーコンデータグラムを見分けるパケット分類器 |
| `core/transport` | 映像の Packetizer/Reassembler、FEC、再送キャッシュ、送信ペーサ |
| `core/session` | セッション状態機械。役割で分割：`session/host`（ビューアごとのセッション、ビューア表、ビーコン、ファイル受信、認証スロットル）、`session/client`（画面クライアント、ファイル送信、ターミナルクライアント、接続フロー）、およびその隣に置かれた共有部品（転送の型、ターミナルセッション表、クリップボード同期、リンク回復） |
| `core/control` | ビットレート制御器、品質ラダー、ストリームのサイズ決定、クロックオフセット |
| `core/terminal` | すべてのクライアントが共有する VT エミュレータ：`VtParser`、`Screen`、`KeyEncoder`、`Palette` |
| `core/net` | 信頼ストア（クライアント側）、ペアリング済み端末（ホスト側）、バインドアドレス選択、LAN 走査のロジック |
| `core/ui` | ユーザーに見えるすべての文字列、設定のパース、表の行の構築 — 5 つのクライアントが同じことを言うために |
| `platform/net` | `UdpSocket`（OS ごと）、`QuicEndpoint`（pimpl の背後の quiche）、`SessionTransport` |
| `platform/auth` | `AuthNegotiation` — 双方が話す唯一のペアリング/パスコードのハンドシェイク |
| `platform/client` | `HostLink`（ダイヤル + 信頼 + 認証 + チャネル。すべての画面が共有）、`ScreenViewer`、`TerminalViewer`、`FileTransferClient`、`SourceQuery`、ホストプローブ、LAN スキャナ |
| `platform/host` | `HostEngine`、`HostNetLoop`、`SharingHost`、`TerminalHost`、`FileHost`、`ViewerBroadcast` |
| `platform/system` | クロック、乱数、PTY（ConPTY / forkpty）、ホストの身元（鍵）、信頼/ペアリング済み端末のファイル、自動起動、スリープ防止 |
| `core/cli` | コマンドラインの文法とその JSON ライタ — テキストを入れ、検証済みのコマンドを出す |
| `client/<os>` | キャプチャ、エンコード、デコード、描画、ウィンドウ、ダイアログ — プロトコルの形をしたものは何もない |
| `client/cli` | フラグからセッションへ：GUI ツールキットなしでホストになり、接続し、シェルを開く 1 つのバイナリ。デスクトップアプリと同じ OS ごとのメディアライブラリをリンクする |

`core/` はネットワークも GPU もなしにオフラインでテストできる状態を保たねばならない。
`platform/` は OS に触れてよいが、どこでも同一の API を出さねばならない。同じコードが 2 つの
クライアントに現れたら、それは下のレイヤに属している。

## 2. ひとつのポート、ひとつのトランスポート

ホストが差し出すすべては、ひとつの `SessionTransport`（内部に単一の `QuicEndpoint`）を
通って**ひとつの UDP ポート**（既定 47777）に乗る：

```
                      UDP ポート 47777
                            |
                 ClassifyPacket（先頭バイト）
                   /                    \
            QUIC パケット          Deskhub データグラム
                 |                        |
   +-------------+------------+       ビーコンのみ：
   |             |            |       LIST_SOURCES / PING に平文で
 streams     datagrams     (TLS)      応答。それ以外の生パケットは
   |             |                    すべて破棄
 control      video
 input        audio       ストリームはフレーム化されたレコードを運ぶ
 clipboard                （RecordStream）：長さ前置のメッセージ、最大 16 KiB。
 terminal                 データグラムは映像か音声のパケットを 1 つずつ
 files                    運ぶ（1200 B 以下）。
```

- **ストリーム**（信頼性あり・順序あり）：制御、入力、クリップボード、ターミナル、ファイル
  — 各接続は、クライアントが開く双方向ストリームを 1 本使う。ある接続で詰まったストリームが
  別の接続を止めることはない。受信したストリームデータはサービス 1 巡につき 64 KiB の
  予算で吸い出される：それを消費するもの（とりわけターミナルの VT エミュレーション）が
  スライスの合間にループを ACK、キープアライブ、タイムアウト処理へ返すので、`cat` の嵐が
  接続を自分自身のアイドルタイムアウトまで飢えさせることはもうない。
- **データグラム**（信頼性なし・順序なし、ただし暗号化はされる）：映像と音声のパケット。
  失われたものを QUIC が再送することはない。映像はアプリ自身の FEC/NACK 機構が損失を扱い、
  音声は何も扱わない — 9 章を参照。
- **生の UDP** は探索のためだけに存在する：ビーコンは QUIC を話さないスキャナに応答し、
  招いていないプローブには空のソース一覧を返す。探索の種類でない受信生パケットは、
  セッションのコードに届く前に捨てられる。

`QuicEndpoint` は quiche を完全に隠す（pimpl。`QuicEndpointNone.cpp` がスタブにするが、
それは `-DDESKHUB_QUIC=OFF` でビルドが明示的に降りたときだけ — quiche が無ければ configure が
失敗する。スタブのバイナリは共有も接続もできないからである）。接続はピアのアドレスで識別され、
コネクションマイグレーションはない。quiche の接続は契約上シングルスレッドなので、エンドポイントに
触れるたびにトランスポートの送信ミューテックスの下に入る — そしてトランスポートはブロックする
ソケット待ちをまたいでそのミューテックスを保持しない（まずロックせずに `WaitReadable`、
それから短くロックして `Poll`）。待ちをまたいで保持すれば、すべての送信側が飢える。

## 3. 入場：ペアリング

各マシンは初回起動時に ECDSA P-256 の鍵を作る（`HostIdentity`）。その SHA-256 SPKI ハッシュが
人の見るフィンガープリントである。TLS はその鍵に対する自己署名証明書を使う。TLS の上で、
アプリケーションレベルのハンドシェイク（`AuthNegotiation`）が接続ごとに入場を決める。
トランスポートがそれを走らせ、認証が決着していない接続からのメッセージはすべて捨てる：

| クライアントが差し出すもの | ホストがそのマシンを知っているか | 結果 |
| --- | --- | --- |
| 何も出さない | ペアリング済み | **署名**：クライアントが nonce + ホストのフィンガープリントのトランスクリプトに自分の鍵で署名する。黙って入場。 |
| 何も出さない | 未知 | **承認**：ホストの前の人に尋ねる（*このマシンを入れますか？*）。 |
| パスコード | ホストにもある | **パスコード**：ソルト付き検証子に対する SPAKE2 — コードは流れず、1 接続 1 回の試行で、双方が証明し、MAC はクライアントが実際に見たホスト鍵に束縛される（中継を殺す）。入力されたコードはペアリング済みかどうかに関わらず常に検査される。 |
| パスコード | ホストには無い | 照合する相手がない → ペアリング済みなら署名、そうでなければ承認。 |
| 何であれ | ペアリングがオフ | **拒否**（ペアリング済みのマシンは署名で入れる）。 |

成功するとクライアントはホストの `paired_devices` に書き込まれる。ペアリングはアドレスでは
なく鍵で行う。パスコードを 3 回間違えるとパスコードの経路が 30 秒ロックされる
（`AuthThrottle`。旧来のセッションロックアウトと定数を共有）。承認の経路にスロットルは
要らない — 門番が人間だからである。

クライアント側では `known_hosts`（`TrustStore`）がホストの鍵をピン留めする。鍵が**変わった**
場合は目立つ警告の後ろで接続を止め、未知の鍵はハンドシェイク自体で決着する（パスコードを
証明したホストはプロンプトなしで記憶される）。

ワイヤを流れるのは公開鍵そのものであって、裸のフィンガープリントではない — ホストは受け取った
ものをハッシュするので、他人の身元をまとうには、なりすます側が持っていない鍵で署名する必要が
ある。そして入場は接続ごとに一度決着するので、トランスポートより上は二度と尋ねない：自分を
証明したマシンは以後のどのメッセージにもパスコードを載せず、セッションのコードは接続全体を
認証済みとして扱う。

## 4. ホスト側

```
HostEngine（アプリに 1 つ、SessionTransport を所有）
 ├─ ネットループのスレッド：RunHostNetLoop
 │    recv → ビーコン応答 | 映像経路への取り込み | Chan::Terminal → TerminalHost
 │    ソースごとのセッション Tick、クリップボードのフラッシュ、再設定、統計
 ├─ キャプチャ/エンコード：ソースごとに、OS のキャプチャコールバックが駆動（client 層）
 │    フレーム → エンコーダ（ソースごとのミューテックス）→ Packetizer → FEC → SendTo（データグラム）
 ├─ 音声ワーカー：キャプチャコールバック → ロックフリーのフレームリング → Opus エンコード →
 │    ビューアごとのデータグラム（AudioBroadcaster）
 └─ TerminalHost（テナント。ターミナルが共有されているとき）
      ├─ ネットループのスレッド上の HandleMessage：TERM_OPEN/DATA/RESIZE/CLOSE → PTY
      └─ ポンプスレッド：PTY 出力 → ホスト側の Screen ミラー + TERM_DATA レコード、
           期限切れ、キック
```

- 何かが共有されている間はエンジンが動く。画面ソースがゼロでターミナルにチェックがあれば
  ソースなしで動き、ターミナルが生きている限りループも生きている。
- 各画面ソースは `SourcePipelineState` である：自分の `ScreenHostSession`（ビューア表、
  ネゴシエーション、入力の調停）、エンコーダ、品質ラダー、診断を持つ。1 回のエンコードが
  そのソースの全ビューアを賄う。
- フィードバックループ：ビューアは毎秒 `Feedback`（損失/RTT）を送り、ホストは自前の信号を
  1 つ足す — フレームが送信段に届いたときの古さで、`enc_lat_ms` が報告するのと同じ量である。
  `BitrateController`（AIMD）と `QualityLadder` がその 3 つからエンコーダのビットレート、
  解像度、fps を調整する。FEC は最初のフレームから armed で、長くきれいに走った後にだけ
  解除される。守るべき損失は最初のレポートより先に現れるからである — バックログでは arm
  しない。パリティは待ち行列をさらに深くするだけだからである。データグラム経路の下には
  quiche の CUBIC 輻輳制御があり、両者は直列に働く — quiche がマシンから出る量を縛り、
  アプリはその結果生じた損失にエンコーダを合わせる。
- 入力：「ホストが勝つ」— マシンの前の人が自分のマウスを動かしている間、`LocalInputMonitor`
  がリモート入力を一時停止する。操作するのは一度に 1 人。
- シェル：シェルごとに PTY 1 つ（Windows では `ConPTY`、それ以外は `forkpty`）、最大 8 個。
  接続が切れるとシェルは切り離され、同じマシンが再接続できるよう PTY は 2 分間生かされる。
  開始・終了・切り離し・再接続はすべて、アドレス・名前・鍵とともに監査ログに残る。
- 各シェルの出力は開始した瞬間から、ホスト側の `core/terminal` の Screen にも流れる。
  *Stop & attach* はリモートのクライアントを切断し、そのミラーを — スクロールバックごと —
  ホストのターミナルウィンドウに開く。こうして引き取られたシェルはホストのものになり、
  期限切れにならず、ホストのウィンドウが閉じたときに終わる。

## 5. クライアント側

どのクライアント画面も、同じ部品 `HostLink`（`platform/client/HostLink`）を通してホストへ
届く：QUIC 接続をダイヤルし、信頼ストアを調べ、認証ハンドシェイクを走らせ、リンクを生かし、
そして — それを求める画面のためには — リンクが切れたときにバックオフしながらダイヤルし直す。
もはや自分でダイヤルしたり認証したりするサービスはない。サービスはワイヤの `Chan` ごとに
チャネルを開き、自分の受信キューを得て、自分のスレッドでそれを吸い出す：

```
HostLink（開いている画面ごとに 1 つ）
 ├─ リンクスレッド：ダイヤル → 信頼確認 → 認証 → ポンプ
 │   （受信したレコードとデータグラムを Chan ごとのキューへ振り分ける。
 │    リンクパルス。回復が有効なところではバックオフして再ダイヤル）
 ├─ Chan::Control/Video/Audio ─> ScreenViewer
 │    ├─ ネットスレッド：HELLO/ネゴシエーション、映像の取り込み（Reassembler+FEC）、
 │    │   NACK、フィードバック、クリップボード
 │    └─ デコードスレッド：デコーダ + 描画キュー
 ├─ Chan::Terminal ─> TerminalViewer のサービススレッド
 │    ├─ core/terminal の Screen がグリッドを持つ
 │    └─ UI が Snapshot() をポーリングし、キーをコマンドキューへ投げる
 └─ Chan::File ─> FileTransferClient のサービススレッド（FileUpload のリング）
```

入場が済むと、リンクは自分の脈をとる（`core/session/LinkPulse`）：セッション id 0 の `Ping`
データグラムが毎秒出て、ホストのビーコンがセッション不要で同じ接続の上から応答し、返ってきた
タイムスタンプが平滑化された RTT になり、戻ってこなかった pong の id が損失率になる。
`ClassifyLinkQuality` がその 2 つを Good / Fair / Poor に畳み込み、デバイス一覧と、ホストに
応答した側のパネル — デスクトップでは専用のウィンドウ、Android と iOS では接続画面 — に
渡す。セッションのウィンドウはもうそれを持たない。`HostLink` は `onPulse` と `Pulse()` で
読みを差し出し、ping は ack を誘発するのでキープアライブも兼ねる。素のキープアライブ
タイマーが今も意味を持つのは、リンクが `Deciding` に停まっている間だけである。session-0 の
ping に答えられないほど古いホストでは読みが Unknown のままになる — 何も後退しない。回復中の
リンクではパルスが生存確認でもある：5 秒 pong が無ければ（ただし最初の pong でホストが答えると
証明された後にだけ）接続は既存の再ダイヤル経路へ落ちる。

画面ビューアも、ターミナルが以前からそうしていたように、その回復に自ら乗るようになった：
リンクが切れるか黙り込むか、セッションが 5 秒受信しないと、ウィンドウを終わらせるのではなく
`Reattaching` に停める（最後のフレームは残り、ステータス行が再接続中の文言に切り替わる）。
セッションのほうが先に気づいたときは `HostLink::RequestRedial` が再ダイヤルを強制し、リンクが
再び入場を許されるとビューアは同じクライアント id で `HELLO` をやり直し — ホストがビューアの
枠を結び直す — 新しいキーフレームからストリーミングが再開する。60 秒
（`kViewerReattachGraceUs`）戻れなければ、ウィンドウはいつもの理由とともに終わる。

ソース照会（`QuerySources`）は同じリンクの上を、1 回きりのブロッキング形式で走る。UI は今も
意図（キー、リサイズ、フィンガープリントの受理）をコマンドキューへ投げる。ホスト鍵が変われば
人が受理か拒否をするまでリンクは `Deciding` に停まる。ターミナルのウィンドウはエスケープ
シーケンスを一切解釈しない — `core/terminal` がバイト列をセルのグリッドに変え、ウィンドウは
セルを描いてキーイベントを転送するだけである。今日はまだ各ウィンドウが自分のリンクを持って
いる。同じホストに向いたすべてのウィンドウで 1 本の入場済みリンクを共有するのが次の一手で、
それは別のハンドシェイクとしてではなく `HostLink` に — レジストリと観察者へのファンアウトと
して — はまる。

## 6. 探索

ビーコンは `LIST_SOURCES` と `PING` に平文 UDP で答える。スキャナが 254 回の TLS ハンドシェイク
なしにサブネットを掃けるようにするためである。見知らぬ相手への返答は空の一覧で、本当のソース
一覧は入場済みの接続の上でしか明かされない。その返答は `SOURCE_LIST` のヘッダフラグで、ホストに
何ができるか — 入力を受け取るか、ターミナルを共有しているか — も運ぶので、クライアントは
ウィンドウを開く前に、スマートフォンは見ることしかできないと知る。フラグが存在する前のホストは
どれも立てない。最近の端末、その オンライン状態（ping/pong プローブ）、LAN 走査の結果は 1 つの
統合デバイス一覧になり、`core/ui/DeviceRows` が組み立て、5 つのクライアントすべてが表示する。

## 7. ディスクの上のデータ

すべてはユーザーの Deskhub フォルダ（`~/.deskhub`、`%USERPROFILE%\.deskhub`）にある：
`host_key.pem` + `host_cert.pem`（身元）、`known_hosts`（このマシンが信頼するホスト）、
`paired_devices`（このホストが入れるマシン）、`auth_salt`（秘密でない検証子のソルト）、
`ui-settings.txt`、`recent-devices.txt`（アドレスと難読化したパスコード）、Linux では
`portal-restore-token.txt`（画面共有ダイアログで選んだ画面に対するデスクトップ自身のトークン）、
そして実行ごとのログ。ファイル I/O は `platform/` に留まり、パースとデータ構造は `core/` に
あってユニットテストされている。

ビューアが送るファイルはまったく別の場所へ届く：ホストが選ぶフォルダ（`ui-settings.txt` の
`transfer_dir`。既定はユーザーのホームフォルダの `Deskhub`）である。`FileStore` は各ファイルを
`<name>.deskhub-part` として書き、CRC-32 が一致してファイル全体が届いてから改名するので、
書きかけのファイルが本来の名前で現れることはなく、`UniqueFileName` が何も上書きされないことを
保証する。ワイヤ上の名前は、`platform/` がファイルシステムに触れる前に `core/` の
`SafeFileName` が洗う — パス区切り、制御バイト、Windows が拒む文字、予約デバイス名はすべて
落ちる。

## 8. テスト

| スイート | 実行環境 | 対象 |
| --- | --- | --- |
| `make test` | オフライン、ソケットなし | `core/` のすべて：ワイヤ、フレーミング、FEC、セッション、VT エミュレータ、設定、文字列、決定論的な構造化ファジング |
| `make test-platform` | ループバックソケット | 実際の QUIC ハンドシェイク、SPAKE2 のエンドツーエンド、ターミナルのホストとビューア、実シェルに対する PTY、ロックアウト、承認 |
| `make test-integration` | ループバック、疑似キャプチャ/エンコード | ホスト↔クライアントの完全なセッション：ネゴシエーション、映像の伝送、入力、パスコード/承認のゲート、ゴミ耐性、そして交差負荷下の遅延 — 生きたストリームの隣でファイル転送、溢れるターミナル、キー入力を走らせ、それぞれ観測された最悪の停止で判定する |
| ファズターゲット | PR ごとに各 30 秒、夜間は各 15 分 | ワイヤ、H.264、再組み立て、ターミナルバイト、UI テキストの各パーサ、およびホストとビューアのセッション状態機械 |
| `make test-perf` | リリースビルド、オフライン + ループバック | ホットパスを走らせるだけでなく測る：`core_perf` が純 C++ の経路を、`platform_perf` がループバック上の実 QUIC を覆う。どちらも単位あたりの確保回数、入力 4 倍でのコスト、そのマシンで記録したベースラインからのずれで落ちる |

`platform_tests` と `integration_tests` は、どの OS でもそれぞれ自分の app data ディレクトリを
持つ。ホスト鍵も、信頼済みホストの一覧も、ペアリングのファイルも共有された一つのファイルなの
で、開発者のホームを読むスイートは、インストール済みのアプリやこのマシンの他のすべての
Deskhub プロセスと競走することになる。

CI はさらに clang-format と clang-tidy（どちらもピン留め）、SwiftLint `--strict`、
Android Lint、actionlint + shellcheck、3 スイートの ASan/TSan 実行、C++/Kotlin/Swift への
CodeQL、履歴全体への gitleaks、そして `core/` の行 90 % / 分岐 80 % 以上のカバレッジを
強制する。3 スイートはさらに arm64 Linux、Android エミュレータ、iOS シミュレータ向けに
クロスビルドされて走り、Windows のジョブは 1 巡ごとに統合スイートをさらに 3 回走らせて、
3 回に 1 回ほど現れる `DrainStreams` の間欠的なスタック破壊を追う。Linux と macOS の
リリースジョブは `core_perf` と `platform_perf` を、確保回数とスケーリングのゲート付きで
走らせる（共有ランナーに時間のベースラインは存在しない）。各プルリクエストにはさらに、
性能と遅延のレポートが自己更新する 1 つのコメントとして投稿される：両方の性能スイートを
同じランナー上でベースコミットと A/B した結果（ずれは警告であって失敗ではない）、
プルリクエストのビルドから得た負荷下の統合数値、そして core のカバレッジ行である。

## 9. 覚えておく価値のある判断

以下の FEC に関するいくつかの判断の背後にある A1 bake-off は、プロジェクト外の読者向けに
[`docs/posts/fec-under-burst-loss.ja.md`](posts/fec-under-burst-loss.ja.md) にまとめてある。引用元の
生の CSV は隣の [`docs/data/bake-off/`](data/bake-off/) に置いてある。

- **false を返す機能問い合わせひとつで、制御ループ全体が切れることがある**：Media Foundation
  のエンコーダは、MFT が `CODECAPI_AVEncCommonMeanBitRate` を出さないときに `SetBitrate` へ
  `false` を返し、`ApplyFeedback` は拒否を「何もコミットされなかった」として正しく扱う。
  `MeanBitRate: NOT SUPPORTED` と報告する Intel Quick Sync の MFT では、その結果ビットレートを
  まったく変えないホストになった：このハードウェアでの実測で、29-40 % の損失が 30 秒続いても
  `Bitrate` の判断はゼロ件、したがって品質ラダーも 1 段も動かなかった。起動時のログはずっと
  `NOT SUPPORTED` と言っていたのに、誰もそれを「適応は死んでいる」とは読まなかった。同じ
  ファイルの `SetFps` と `RequestKeyFrame` は既に `ReinitTransform()` にフォールバックして
  いた。諦めていたのは `SetBitrate` だけで、今は同じようにフォールバックする —
  `ConfigureTransform` が `cfg` から `MF_MT_AVG_BITRATE` を書くので、再構築すれば新しいレートが
  効く。再構築は IDR のコストを伴うので、生きた `codecapi` の経路をまず試すのは変わらない。
  デバイスごとの機能が制御入力を左右するなら、フォールバックは必須にすること。「遅くなる」への
  劣化は選択だが、黙って「決してしない」に劣化するのは選択ではない。

- **追いつけない送信側は、きれいなリンクとまったく同じ顔をしている**：`BitrateController` が
  持っていた入力 — 損失、RTT、受信レート — はすべてビューア由来なので、ループの中の何も
  「遅れているのは自分だ」と言えなかった。2 人のビューアにホストしている Pixel 4 での実測：
  フレームはエンコーダを 15 秒古い状態で出ていったのに、ビューアは損失 0 %、RTT 15 ms と報告し、
  制御器はそれを余裕と読んでビットレートを上限の 20 Mbps まで戻していった — 送信側の内部で
  起きるバッファブロートであり、リンクがきれいに見えるほど強く送り込む。ホストは今、送信の
  段でフレームの古さを測り、ビューアの数字と並べて入力する：`kBacklogMs` を超えれば損失 2 %
  相当で退き、`kSevereBacklogMs` を超えれば 5 % 相当で退き、どちらでも通常どおり 2 秒は
  ランプアップを止める。制御変数は今もビットレートだけなので、`QualityLadder` はその後ろで
  一段下がり、fps 上限も追随する。遠端だけに養われた制御ループは、自分が本当に所有している
  半分に対して盲目である。

- **fps の上限は、どこかがフレームを捨てる場所でしか効かない**：ラダーの fps の段は要求で
  あって、各プラットフォームがフレームを捨てられる場所でそれを果たさねばならない。Windows と
  Linux はキャプチャで `FrameGate` を挟み、Android は `max-fps-to-encoder` で MediaCodec の
  入力を抑え、macOS は ScreenCaptureKit のフレーム間隔を再設定する。iOS には場所がなかった：
  ReplayKit は画面のレートで届け、`VtEncoder::SetFps` は
  `kVTCompressionPropertyKey_ExpectedFrameRate` を設定するだけで、それは何も捨てないレート
  制御のヒントである。そこで段を変えてもエンコーダを調整し直すだけで、飲み込まねばならない
  フレーム数は何も変わらなかった。`OfferVtFrame` は今、両方の Apple アプリで同じ `FrameGate`
  を走らせる。静止画面でも再送するフレームがあるよう、アイドル用のフラッシュキャッシュを
  更新した後にである。すべてのプラットフォームにつまみがあるときは、ラダーを信じる前に、
  各プラットフォームがそれで何をするのかを確かめること。

- **送信ペーサはエンコーダ自身の出力レートより十分上に保つこと**：`Pacer::Gate` は
  `SendEncodedFrame` が走るスレッドで眠り、Android ではそれが MediaCodec の吸い出しループで
  ある — エンコーダが次のフレームを渡せるようになる前に `releaseOutputBuffer` を呼ばねば
  ならない、まさにそのループである。したがってペーシングはワイヤのレートだけでなく吸い出しの
  レートを決めてしまい、その間 VirtualDisplay は画面のレートで新しいフレームを押し込み続ける。
  送信のバーストを均そうと `kPacingRateMultiple` を 2 から 1.2 に狭めた結果を Pixel 4 で実測：
  フレームあたりのバーストは 20 ms から中央値 63 ms になり、エンコーダのバックログは際限なく
  伸びた — `enc_lat_ms` は 100 秒で 46 秒を超え、ビューアは 4.6 秒遅れた。2 のままなら同じ
  実行で `enc_lat_ms` は 0 だった。この余裕は回収できるたるみではない。エンコードのパイプラインが
  埋まるより速く吸い出されるようにしているのがそれである。送信のバーストにはソケットバッファか、
  ペーシングを吸い出しスレッドから外すことで対処し、決してこの数字を締めて対処しないこと。

- **性能スイートはコストで判定するので、結果を見る第 2 のゲートが要る**：`core_perf` は
  パケットあたりの確保回数と、時間が入力に対してどう伸びるかを測る。そして実リンクで
  1 個の損失パケットが無傷のフレームの 22 % を捨てさせていた間も、その再組み立て系ワークロードは
  すべて合格していた。捕まえられるはずがない：良い映像を捨てるほうがデコードするより*安い*ので、
  壊れた方針のほうがスイートの見るすべての数字で良い点を取る。`LossGoodputTests` はその相棒で、
  コードが本来すべきより少ない仕事しかしないときに落ちる — 実際の往復を伴う末尾損失リンクを
  模擬し、パケットが全部届いたフレームのうち実際にデコーダへ届いた割合と、届いたフレームどうしの
  最長の間隔で判定する。どちらもマシン非依存なので、ノート PC でも CI ランナーでもスマート
  フォンでも成り立つ。方針が仕事を捨てることで「成功」できるときは、常にグッドプットのゲートを
  持ち出すこと。

- **失われたパケットの代償は 1 フレームであって、次のキーフレームまでの画面全部ではない**：
  再組み立て器は損失のたびに `waitingForIdr_` を立てていたので、1 個の欠けたパケットが、新しい
  IDR が来るまで後続の*完全な*フレームをすべて捨てていた。Wi-Fi 越しにホストするスマートフォンでの
  実測では、それが本当に不完全な 64 フレームを 381 の破棄フレームに変えていた — デコードできる
  映像 6.4 MB がゴミ箱に入り、画面は中央値 146 ms、最大 1.4 秒ずつ凍った。今は不完全なフレーム
  だけを落とし、その後ろのフレームはそのままデコーダへ行く。デコーダは欠けた参照を隠蔽し、
  `InvalidateRef` が悪いフレームをホストに名指しして、キーフレーム要求が修復する。短い
  マクロブロックのノイズは、凍らせないために意図して払う代償である。`waitingForIdr_` は、それが
  唯一正しかった場合のために残っている：途中参加のビューアには参照がまったくないので、最初の
  IDR を待たねばならない。

- **停止判定の窓は再送より長くなければ、NACK は飾りである**：かつてフレームは失われたと宣言される
  までに 2 フレーム間隔（60 fps なら 33 ms）しか与えられていなかったが、同じリンクで実測した
  RTT は 24-49 ms だった。NACK は出ていき、その答えはフレームが既に捨てられた後に届いた —
  `late_ms_avg=24` と、もう存在しないフレーム宛に毎秒 87 パケットが着地する形で見えていた。
  `StallTimeoutUs` は今、ペースの窓と 1.5 往復の大きいほうを取り（ハードタイムアウトの上限は
  そのまま）、再送を頼む価値のあるリンクでちょうど頼むようになった。

- **性能スイートは確保回数と形で判定し、ミリ秒では判定しない**：3 つのテストスイートはデバッグで
  ビルドされ、CI は ASan、TSan、カバレッジの下でもう一度走らせる。そこでの実時間の予算は
  コードではなくサニタイザを測ってしまう。だから `core_perf`（リリースプリセット、
  `make test-perf`）はマシン非依存な 2 つで落ちる — グローバルな `operator new` を差し替えて
  数える、パケット/フレーム/KB あたりの確保回数と、入力よりはるかに速く時間が伸びる `-scaling`
  の行である — そして計測の半分は `out/perf/baseline.txt` との比較として残す。このファイルは
  `make perf-baseline` がマシンごとに記録し、コミットしない。この分割こそが、「再組み立て器が
  今はすべての断片を 2 回コピーする」ような後退を、ノート PC でも CI ランナーでもスマート
  フォンでも同じように落とせるようにし、なお数字そのものが要点である経路については単位あたりの
  ns と MB/s を印字させる。CI はこの 2 つのマシン非依存なゲートを Linux と macOS のリリース
  ジョブで走らせる。Windows はバイナリをビルドするだけである。MSVC の deque は 16 バイトを
  超える要素に対して 1 要素ごとにブロックを確保するので、同じコードでも確保回数が変わるからで
  ある。プルリクエストには共有ランナーのノイズでは覆せない計測比較も付く — ベースコミットと
  プルリクエストを同じランナーで測り、許容 50 %、警告のみ。`platform_perf` は同じゲートを
  ループバック上の実 QUIC に広げる。そこでは実時間がサービスループの刻み — 64 KiB のストリーム
  吸い出し予算 × 1 ms のポーリング — を測るので、予算の縮小、線形に伸びなくなった吸い出し、
  ポーリングループでの新たな確保は、同じ仕事の CPU コストがほとんど動かなくても跳ねとして
  現れる。

- **`FileHost` は自分のロックを持ったまま送らない**：QUIC のサービスループは
  `SessionTransport::sendMutex_` の下で `QuicEndpoint::Poll` を走らせ、そこで閉じた接続は
  そのまま `FileHost::OnPeerGone` を呼び返し、それが `FileHost::mutex_` を取る。つまり
  `sendMutex_ -> mutex_` の順序はトランスポートが決めている。`mutex_` を先に取ってから送る
  経路 — `FileReceiver` が `hooks.send` 経由で accept、ack、cancel を出す — はこの環を
  閉じてしまい、TSan が受信ループと、生きた転送に対して `SetAccepting(false)` を切り替える
  UI スレッドとの間のロック順序逆転として捕まえた。したがって受信側が出すレコードは `mutex_`
  の下で `outbox_` に積み、解放した後にだけ送る。両方の半分にまたがって `outboxMutex_` を
  保持するので、ピアには生成された順序どおりに見える。`OnPeerGone` はそもそも送れない：
  既に `sendMutex_` の下で走っているので、積んだものは捨てる。

- **コマンドラインクライアントは 4 つ目のフロントエンドであって、2 つ目の実装ではない**：
  `core/cli` でフラグを解析し、あとはデスクトップアプリが駆動するのとまったく同じ部品を
  駆動する — ホストになるなら `SharingHost`、見るなら `ScreenViewer`、シェルを開くなら
  `TerminalViewer`。自前で持っているのはウィンドウだけである：Linux では X11 + EGL、
  Windows ではデスクトップアプリ自身の `RunViewer`。各クライアントの `cpp/` ツリーが静的
  ライブラリ（`deskhub_linux_core`、`deskhub_win_core`、`deskhub_win_view`、
  `deskhub_mac_core`）で、GUI のコードがその上に載っているのはそのためである — この分割は、
  CLI が GTK も wxWidgets もリンクせずにメディアパイプラインをリンクできるようにするために
  ある。

- **`preflight` はキャプチャすべき画面があるときにだけ走る**：どのクライアントもこれで
  キャプチャ経路を確かめる — Linux では xdg portal、macOS では画面収録の許可、Windows では
  D3D11 デバイス。シェルだけを運ぶ共有にはどれも要らないので、それでも尋ねると、ヘッドレスな
  マシンでの `share --terminal` が「画面キャプチャの権限が無い」になってしまった。
  `HostEngine::Start` はソース一覧が空なら今はそれを飛ばす。

- **シェルがあって画面のないホストは生き続ける**：ネットループは生きているソースが無くなると
  セッションを終える。そしてターミナルだけの共有には定義上ソースが無い。`keepAlive` は今、
  ループが走り出した後にしか付かない `TerminalHost` ポインタではなく、呼び出し側の意図
  （`ShareOptions::terminal`）から答える。

- **フレームゲートは締切に向けて数え、最後に通したフレームからは数えない**：30 fps の目標に
  対して 40 fps を渡してくるコンポジタは、33 ms の境界のほとんどでフレームを持っていない。
  だから「通したものから十分離れているか」だけを問うゲートは 1 枚おきに落として 20 fps で
  落ち着く — 目標より遅く、しかもばらつく。それは遅いストリームではなくジャダーである。
  `FrameGate` は代わりに走行中の期限を持つ：通過は期限をちょうど 1 間隔進めるので余りが残り、
  40 入れれば 30 出る。目標より遅いキャプチャが間引かれることはなく、実時間より遅れた期限は
  バーストを貯め込むのではなく再同期するので、静かな時間が後のバーストを買うことはない。

- **Linux のホストは自前のスレッドでエンコードし、そのスレッドに渡すのは大きいフレームでは
  なく小さいほうである**：PipeWire の `process` コールバックの中でエンコードすると、
  キャプチャが `1000 / enc_ms` fps に絞られ、エンコード時間の揺らぎがそのままクライアント側の
  フレーム間隔のジッタになった。エンコードは今や自前のスレッドで走り、`FrameMailbox` — 最新
  勝ちの 1 枠キュー — 経由で供給される。エンコーダが遅れれば新しいフレームが勝ち、古いほうは
  積まれるのではなく数えられる。キューを渡るのは既にエンコードサイズへ縮小されたフレームで、
  おおよそ 7 分の 1 のバイト数である。代わりにフルサイズのフレームを渡すと、コピーそのものより
  はるかに高くついた：キャプチャ側のコアに 20 MB のキャッシュラインがダーティなまま残り、
  エンコード側のコアがそれを引き寄せねばならず、実測で 16 ms。自分の所有するメモリを同じだけ
  読む場合は 3.4 ms だった。キャプチャスレッドはどのみち全ソースピクセルに一度触れねばならない
  ので、その 1 巡を払う場所としてそこが正しい。dma-buf のフレームは今もインラインでエンコード
  する：コールバックが返った瞬間にコンポジタが裏のメモリを再利用するので、それより長生きできず、
  どのみち VA-API が GPU 上でスケールするからである。
- **Linux のホストはインストール状況ではなく、フレームがどこにあるかでエンコーダを選ぶ**：
  dma-buf のフレームは VA-API へ行く。それを生んだ GPU 上でゼロコピー取り込みできるからである。
  マップ済み（CPU）のフレームは NVIDIA ドライバがあれば NVENC へ行く。NVIDIA GPU が描く
  デスクトップでは、コンポジタが screencast を共有メモリに再ネゴシエートするので、エンコードは
  システムメモリから直接ピクセルを取れるカードのものになるからである。`HwEncoder` は
  エンコーダ再構築ごとにその判断をし、後から別種のフレームが来たら `false` を返す。それが
  再構築の合図である。
- **NVENC の手前の縮小は自前であって、swscale のものではない**：NVENC はパックされた 32 ビット
  ピクセルを取るがリサイズはしない。そしてキャプチャはフル解像度のデスクトップである。
  `libswscale` は 3440x1440 → 1280x534 で 9.2 ms を計測した — およそ 2 GB/s で、このマシンの
  メモリ帯域より一桁遅い。パック RGB のリスケールは最適化された経路から外れるからである。
  `core/` の `RgbDownscale` はまさにこの形のために書かれた面積平均である：ソースピクセルごとに
  32 ビット 1 回のロード、整数の累算、同じフレームで 4.0 ms、しかも swscale が返していた
  バイリニアのタップではなく正しいアンチエイリアスになる。フレーム全体の NVENC のコストは
  約 5 ms に収まるので、60 fps には余裕がある。
- **性能の数字はリリースビルドからでなければ意味がない**：`make build-linux` と
  `make run-linux` は `x64-debug` プリセット、つまり `-O0` を構成する。そしてエンコード経路は
  今や `core/` のピクセル演算である。同じフレームがそこでは約 19 ms、`make release-linux` から
  なら約 5 ms である。デバッグバイナリに対して測ったジャダー報告は、ビルド種別を測っている。

- **Apple のビューアは制御タイムベース上で PTS により映像のペースを取り、ペーサは自分を
  信用しない**：届いた瞬間に毎フレーム表示すると、Wi-Fi の到着ジッタがジャダーとして見えるのに、
  遅延の数字はどれも優秀なままだった — 間隔は遅延ではない。`VideoPacer`（core、オフラインで
  テスト）はホストの PTS をローカルの表示時刻へ、e2e の指標と同じやり方で写す — `arrival − pts`
  の窓最小値 — に、到着ジッタを支払う約 33 ms のリードを足す。`VtDecoder` はそこから
  `AVSampleBufferDisplayLayer` の制御タイムベースを駆動し、250 ms を超える乖離でのみ再同期する。
  2 秒を超える pts の飛びはジッタではなく新しいストリームとして読むので、写像は窓ぶん凍る
  代わりに引き直される。外部タイムベースを描画側が守るかどうかを、あらゆる OS バージョンで
  ここから証明はできないので、デコーダは自分の背中を見張る：ペース調整したフレームが満杯の
  描画キューに飲み込まれ続けたら、即時表示に戻してフラッシュする。画面ではなく平滑化のほうを
  手放すのである。

- **音声は 1 データグラムに 1 フレーム、失われたものは決して追わない**：64 kbps の 20 ms Opus
  フレームは実測で約 160 バイト、最大でも 209 バイトで、データグラムに空いている 1180 バイトに
  対して十分小さい — だから音声経路にはパケタイザも FEC も再組み立ても NACK もない。それは
  映像経路のほとんどである。損失は最も安く済む場所で吸収する：Opus は次のフレームに帯域内 FEC を
  持ち、受信側はジッタバッファが報告した穴をデコーダに隠蔽させる。再送は無駄より悪い。200 ms
  遅れて届いたフレームは再生できないのに、後ろの 10 フレームを遅らせるからである。
  `make opus-smoke` はこのライブラリをビルドできるどのマシンでもその数字を測る。
- **ジッタバッファにタイマーは入っていない**：`AudioJitterBuffer` は純粋な状態であり、目標
  遅延は再生を始める前に何フレーム貯めるかにすぎない — 60 ms なら 3 つである。おかげで全体が
  眠りなしにオフラインでテストでき、失敗の仕方も明示的になる：バーストは積まれずに上限で
  切られ、空のバッファは途切れるのではなく貯め直し、シーケンスの飛びは数千の損失ではなく
  新しいストリームとして読まれる。ペーシングは `AudioPlayer` にあり、実時間 20 ms ごとに
  1 フレームを PCM リングへ送り出し、それをシンクの描画コールバックが吸い出す。
- **キャプチャコールバックはエンコードしない**：PipeWire と ScreenCaptureKit は数ミリ秒の
  締切を持つリアルタイムスレッドで音声を届け、そこで締切を落とすと Deskhub だけでなくホスト
  自身の再生が xrun する。Opus のエンコードは 0.3–1.5 ms でスパイクもあり、以前はビューア
  ごとの `sendto` がその後ろに同じスレッドで乗っていた。`AudioBroadcaster::Offer` は今、
  20 ms のフレームを事前確保したロックフリーの枠リングへコピーし、キャプチャ時刻を刻むだけで
  ある。エンコード、診断、ビューアごとの送信はワーカースレッドが行う。ワーカーが遅れた代償は
  数えられるドロップ（`framesRefused`）であって、ホストの音声のグリッチでは決してない。
- **音は両端が首を縦に振って初めて出る。古いクライアントには決して聞こえない**：ビューアが
  `Hello.features` のビット 0 を立て、ホストが機能に `kHostSharesAudio` を広告し、ホストは
  そのビットが立っているビューアにだけパケットを送る。`kProtocolVersion` が 2 のままなのは
  そのためである：5.0.x のビューアは `features = 0` を送るので、5.1 のホストは相手が解析
  できないメッセージをワイヤに載せない。

- **ターミナルのリンクは自分で生き延び、自分でダイヤルし直す**：ターミナルのビューアは映像
  セッションとは別の自分の QUIC 接続を持つので、映像経路のキープアライブはひとつも届かない。
  プロンプトで放っておかれると通信がまったく無く、30 秒の QUIC アイドルタイムアウトで死に、
  ビューアはそのままスレッドを `Reattaching` で止めて再ダイヤルもしなかった — シェルはホスト側で
  丸 2 分待っていたのに、誰も取りに戻らなかった。`TerminalViewer` は今、タイマーで ack を
  誘発するパケットを送り、バックオフしながら再ダイヤルし、`TerminalClient::Reattach()`
  （core に書かれてテストもされていたのに、ただ一度も呼ばれていなかった）を再利用して、同じ
  シェルをスクロールバックごと呼び戻す。`deskhub::KeepaliveIntervalUs` / `ReconnectDelayUs`
  が core にタイミングを持つ：キープアライブはアイドルタイムアウトの半分以下でパケットを 1 つ
  落としても耐えられ、再試行は `kTerminalReattachGraceUs` でぴたりと止まる。それを過ぎれば
  ホストは既にシェルを捨てており、つなぎ直すと黙って新しいシェルが開いてしまうからである。
- **レコードはまるごとストリームに載るか、まったく載らないか。そして遅れたクライアントには
  全バイトを流すのではなく描き直す**：信頼性のあるもの — 制御、認証、ターミナル出力 — は
  すべて 1 本の QUIC ストリームを共有する長さ前置のレコードなので、ワイヤに半分のレコードが
  出た時点で相手側のフレーミングは永久にずれる。`RecordStream` に再同期する手段はなく、ピアは
  接続を閉じる。`QuicEndpoint::SendStream` は以前、入るだけ書いて残りを捨てていた。それは
  `make test` のようなコマンドがリンクを追い越すまで保っていた：1 MiB のストリームウィンドウが
  埋まり、`TermData` レコードの末尾が落ち、ビューアのフレーマが失敗し、シェルは開いて 1 分後に
  「切断」した。今はストリームに余地のないレコードを拒み、それでも部分書き込みが起きたら接続を
  閉じる。裂けたストリームはその場では直せないからである。その上で `TerminalHost` は未送出の
  出力をシェルごとのキューに保持し、ティックのたびに再試行するので、一瞬リンクを追い越しただけの
  バースト — たとえばビルドの出力 — は今もバイト単位でクライアントに届く。`kMaxPendingBytes` を
  超えるとキューは伸ばされるのではなく捨てられる：どのバイトも既にホスト側のミラー `Screen` に
  届いているので、クライアントは `deskhub::term::RenderScreen` で追いつく — 現在のグリッドを
  1 回描き直すだけで、頻度は最大でも `kRepaintIntervalUs` ごとである。誰も読めなかった出力は
  バッファされずに飛ばされるので、溢れさせるコマンドは自分の速度で走り切り、それでも正しい
  画面が残る。再接続したクライアントも同じ描き直しを受け取る。ギャップの後ではバイト列上の
  位置に意味がないからである。
- **自動共有はデスクトップを待つのであって、一度列挙して終わりではない**：Windows は自動起動を
  `ONLOGON` のスケジュールタスクとして登録し、それはセッションに列挙できるモニタが揃う前に
  発火する。だから構築時の 1 回の `ListDisplays()` は空で返り、アプリは共有できるものが無いと
  報告していた。`deskhub::ui::AutoShareGate`（core、ユニットテスト済み）が再試行の規則
  — `kAutoShareProbeMs` ごとに調べ、`kAutoShareGiveUpMs` で諦める — を所有し、各クライアントは
  自分のタイマーからそれを駆動するので、方針はひとつしか存在しない。`NextAutoShareStep` は
  同じ規則の状態なし版で、Swift クライアントは `dh_auto_share_step` からそれに届く。自動共有は
  モーダルを決して開かない：ログイン時のウィンドウはトレイに隠れていることがあり、そこでは
  ダイアログは見えず共有を永久に止めてしまうので、拒否は Host のバナーとログへ行く。デスクトップの
  クライアントは OS のディスプレイ変更シグナルでピッカーを更新もする。後からモニタを挿したときに
  一覧が正しいままなのはそのおかげである。
- **msquic/ngtcp2 ではなく quiche**：Android と iOS の両方で本番の実績がある唯一の QUIC
  ライブラリである。BoringSSL が付いてきて、それが SPAKE2 とホストの身元にも使える — 2 つ目の
  暗号ライブラリが要らない。
- **コネクションマイグレーションはしない**：候補のどのライブラリにも使えるクライアント側の
  対応がない。再接続して再アタッチする方式（tmux 流。モバイルのバックグラウンド化のためどのみち
  必要）がそれを賄う。
- **Ed25519 ではなく ECDSA P-256**：BoringSSL のサーバ側は quiche 経由で Ed25519 の TLS
  ハンドシェイクに署名しない。戻さないこと。保存された Ed25519 の身元は読み込み時に差し替えられる
  — さもないと画面に何の説明も出ないまま、毎回 `QUICHE_ERR_TLS_FAIL` でハンドシェイクに失敗する。
- **パスコードの検証子は高価な KDF ではなく SHA-256 1 回**：SPAKE2 が既に攻撃者を 1 接続 1 回の
  オンライン推測に制限し、オフラインで解く価値のあるトランスクリプトを残さない。それこそ KDF の
  硬さが存在する目的そのものである。
- **quiche は FetchContent ではなく事前ビルド**：`scripts/build-quiche.sh` が
  `third_party/quiche/` の下に rust ターゲットごとのディレクトリと共有の `include/` を書く —
  quiche.h と、boring-sys が同梱する BoringSSL のヘッダをコピーして置く。Deskhub がホストの身元の
  ために BoringSSL を直接呼び、include パスをひとつにして 2 つ目の TLS ライブラリを持ちたくない
  からである。`DeskhubQuiche.cmake` がそれを `deskhub::quiche` にする。ライブラリが無ければ
  configure が失敗する。
- **Apple は `libplatform_bundled.a` をリンクする**：Xcode のアプリは platform のアーカイブを
  CMake の外から取り込むので、quiche への PRIVATE リンクはリンク行に届かない — そこで `libtool` の
  ステップが platform と quiche を、`.pbxproj` がリンクするひとつのアーカイブへ融合する。
- **Windows のツールチェーンの罠は既に片付いている — 片付いたままにすること**：quiche は Rust の
  オブジェクトを `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS` で静的 CRT に対してビルドし、
  BoringSSL のオブジェクトは `CFLAGS_x86_64_pc_windows_msvc` の `/MT` で扱う（msvc の既定は DLL
  ランタイムで、包括的な `RUSTFLAGS` でこのフラグを押し込むと cargo のビルドがまるごと壊れた）。
  ツリー全体が `MultiThreaded` を固定して合わせ、exe が VC++ 再頒布可能パッケージ無しで出せる
  ようにしている。wxWidgets は configure のたびに `wxBUILD_USE_STATIC_RUNTIME` を固定し直す。
  `wx_option()` がそれを永久にキャッシュするからである。BoringSSL は既定の Visual Studio
  ジェネレータでビルドしなければならない — cmake クレートはそこでしか /MT を構成ごとのフラグで
  伝えられないので、`CMAKE_GENERATOR=Ninja` を強制すると BoringSSL は黙って /MD に戻り、最終
  リンクが LNK2038 で死ぬ。MSBuild が長いパスで MSB6003 を出すなら、Windows の長パスを有効に
  すること。Git Bash の `/usr/bin/link.exe` は MSVC のリンカを覆い隠す（`cl.exe` のディレクトリを
  先に置く）。そのパス書き換えは `/` 形式の引数を壊す（`MSYS2_ARG_CONV_EXCL`）。NASM の
  インストーラは PATH に触れない。
- **Windows ホストでの Android 版 quiche は cargo-ndk を使わない**：cargo-ndk は boring-sys に
  拡張子のない `clang` のパスを渡し、CMake は Windows でそれを拒む。だから `build-quiche.sh` は
  `CC_*`/`CXX_*`/`AR_*`、cargo のリンカ、ABI 向けの `--target=` を自分で設定し、素の cargo を
  呼ぶ。BoringSSL はそこでも Ninja を要求し（Visual Studio ジェネレータは NDK を対象にできない）、
  bindgen は Visual Studio の libclang を拾って、自分のバイナリの隣に `stddef.h` を探す —
  `BINDGEN_EXTRA_CLANG_ARGS` がスラッシュ区切りで NDK のリソースヘッダを指す。bindgen はその
  変数をシェルの規則で分割し、バックスラッシュを食べてしまうからである。
- **クロスコンパイルするアプリはどれも先に自分の quiche をビルドする**：`build-android`、
  `build-ios`、`build-macos`、`build-linux` は、`debug`/`release` がホスト向けにそうするのと
  同じように、自分の ABI の quiche ターゲットに依存する。quiche は ABI ごとであり、それが
  無ければ CMake の configure が失敗するので、この手順を飛ばしたビルドは「ライブラリが無い」
  ではなく「ツールチェーンが壊れている」ように見える — そして最後に成功したビルドのまま
  取り残されたアプリは、ピアがもう答えないプロトコルを話す。
- **iOS の quiche は `IPHONEOS_DEPLOYMENT_TARGET=17.0` を固定する**：boring-sys の clang は
  SDK の既定に流れ、rustc は自分の最小バージョンでリンクする。その食い違いはリンク時に未定義の
  `___chkstk_darwin` として現れる。
- **クロックは 2 つ、意図的に**：`NowUs()` は単調（起動からの秒）で間隔用、`NowUnixSeconds()`
  だけが日付として表示できる。混ぜても大きな音は出ない — 保存した単調のスタンプは 1970 年
  1 月 1 日のどこかの時刻として現れる。
- **Windows の PTY の子プロセスに標準ハンドルを渡さない**：ホスト自身の stdout がリダイレクト
  されていると、Windows はそのリダイレクトを疑似コンソールの属性を越えて引き継がせ、シェルは
  パイプに向かって話す。ハンドルをまったく渡さないことが、シェルをアタッチ済みの ConPTY へ
  戻す。
- **Windows のターミナルグリッドには `wxWANTS_CHARS`**：これが無いと、フレームのダイアログ
  ナビゲーションが Enter、Tab、矢印キーをターミナルより先に食べてしまう。
- **macOS の TCC は許可をコード署名と結びつける**：ローカルでビルドした app.app（アドホック署名、
  ビルドのたびに署名し直す）と Developer ID の dmg が同じ `com.deskhub.macos` の行を取り合う —
  システム設定は許可済みと表示しているのに、いま起動したコピーは拒否される。アクセシビリティに
  ついては黙ってそうなる。`make reset-macos-permissions` がすべての許可を消し、次の起動で
  改めて尋ねさせる。
- **macOS は CI ではデスクトップビルド、リリースでは署名ビルド。同時に両方にはならない**：
  `build-desktop` は push のたびにアドホック署名でアプリをコンパイルするので、ビルドできなく
  なった Cocoa の変更はそのプルリクエストで落ちる。`deploy` は `release-macos`、つまり fastlane の
  経路 — Developer ID、公証、dmg — で同じアプリに到達し、ユーザーが実際に開けるものを作る。
  だから再利用可能なワークフローは `for_release` が立っているとき macOS のジョブを飛ばす。
  さもないとタグひとつのために、誰も出荷しないバンドルを作るだけの macOS ランナーをもう 1 台
  払うことになる。`build-mobile` が iOS と Android だけを担うのも同じ理由、同じ分け方である。
- **どのワークフローも quiche と opus をひとつの action から得る。そしてキャッシュキーが契約
  そのものである**：`.github/actions/third-party` はジョブが名指しした任意のターゲット向けに
  両ライブラリをビルドする。同じ「キャッシュしてビルド」のブロックが 19 個あったのが、ジョブ
  あたり 1 行になったのはそのおかげである。その `cache-key` 入力は飾りではない — 2 つのジョブが
  互いのライブラリを復元し合うのを防いでいる唯一のものである。ターゲットの集合が違えば別物だし、
  同じトリプルをビルドする 2 つのランナーイメージも別物である：ubuntu-latest でコンパイルされ
  ubuntu-22.04 で復元された `libquiche.a` は、そのリリースが避けるために存在している glibc を
  リンクする。ビルドの成果物を変えるものは何であれ、そのキーに属する。
- **Windows では静的なリリース CRT ひとつ、すべての構成で**：cargo は quiche を静的リリース CRT に
  対してビルドし（msvc の既定 — `RUSTFLAGS` で強制しないこと。proc-macro に漏れて cargo を殺す）、
  CMake ツリー全体が `MultiThreaded` を固定して合わせる。それがアプリを VC++ 再頒布可能パッケージ
  なしの単一 exe に保つものでもある。Rust にデバッグ CRT のビルドは無いので Debug も同じにする：
  `_ITERATOR_DEBUG_LEVEL=0`、`/U_DEBUG`、`/RTC1` は外す — リリース CRT には `_CrtDbgReport` も
  ランタイムチェックの支援も無い。食い違えば LNK2038 の壁で終わる。
- **パスコード = セルフサービスの入場、承認 = その代替**：入力されたコードは常に検証され、
  コードが無ければ人が決める。パスコードは、攻撃者が持ち帰れるどんな形でもネットワークを
  渡らない。
- **VT エミュレータは自前**：5 つのクライアントすべてで使えるライセンスのプラットフォーム
  ターミナルウィジェットは存在せず、自分で持つことでターミナルの挙動がオフラインでテストでき、
  どこでも同一になる。
- **ホストのシェルミラーは 1 バイト目から養われる**：PTY の出力は破壊的な単一消費者のストリーム
  である — 読んでビューアへ送ったバイトは後から再生できない — ので、*Stop & attach* が開く
  グリッドは、ボタンが押されたときではなくバイトが通り過ぎるときに組み立てねばならない。
  リモートのビューアが付いている間、ミラー自身のターミナル問い合わせへの応答は捨てられる：
  ビューアの画面が既に答えており、シェルが 2 つの答えを聞いてはならないからである。
- **ポートはひとつ**：ビーコン、画面、ターミナルが 1 つのリスナーを共有し、QUIC が接続と
  ストリームを多重化する。かつての 2 つ目のポートは、QUIC 以前の画面経路がソケットを独占して
  いたからだけ存在していた。
- **ひとつの `HostLink`、かつての 4 つのハンドシェイク**：ダイヤル + 信頼確認 + 認証 + 回復は、
  クライアント側で 4 回書かれていた — ソース照会、ビューア、ファイル送信、そして自前の生の
  `QuicEndpoint` の上のターミナル — だから送信ウィンドウがホスト鍵の変化を知ったのは、ビューアの
  3 つ後の修正だった。`HostLink` は今やクライアント側でダイヤルも認証もする唯一のコードである。
  サービスは自分の `Chan` を開き、自分の受信キューを得て、自分のスレッドで吸い出す。ターミナルの
  「バックオフして再ダイヤル」はリンクへ移り、回復を求めるすべての画面がそれを継承する。信頼の
  規則もひとつの場所にある：鍵が変わればリンクは `Deciding` に停まり、人が答えるまで待つ
  （素通しなのはソース照会だけで、`trustGate=false`、何も記憶しない — その呼び出し側には出す
  プロンプトが無いからである）。そしてホストが暗号的に証明したパスコードだけが、鍵を自動的に
  ピン留めする。
- **`HostLink` は `SendMessage` ではなく `Send` で送る**：Windows では platform 層の背後の OS
  ヘッダが `SendMessage` を `SendMessageA` のマクロとして定義し、`HostLink.cpp` ではそれがクラス
  宣言の後、メソッド定義の前に来ていた — その結果 MSVC は、どのヘッダも宣言していない
  `SendMessageA` というメンバの定義を要求した。Win32 API の名前（`SendMessage`、`PostMessage`、
  `CreateWindow`、`GetObject` など）は、OS ヘッダが届きうる翻訳単位ではメソッド名として決して
  安全ではない。直し方は `#undef` ではなく改名である。
- **portal の ScreenCast セッションは D-Bus 接続と生死を共にする**：GLib は共有のセッション
  バスを弱参照でキャッシュするので、最後のハンドルに `g_object_unref` すると接続そのものが
  破棄される。すると `xdg-desktop-portal` はセッションを落とし、コンポジタは PipeWire のノードを
  壊し、portal が渡したばかりのノード id は何も指さなくなる — ストリームは `paused` に至り、
  *no target node available* で失敗する。だから `PortalScreenCast` は呼び出しごとに借りるのでは
  なく、セッションが開いている間ずっと自分の `GDBusConnection` を所有する。デスクトップアプリは
  長らくこれを覆い隠していた。GTK がプロセスの生存期間中セッションバスへの参照を保持するからで
  ある。`deskhub-cli` は GTK をリンクせず、その参照が無かった。
- **アイコンはすべて派生物で、丸いのは一部だけ**：`make icons` は唯一のマスター
  `assets/icon_1024.png` からセット全体を作り直す。macOS、iOS、Play ストアの掲載、Android の
  アダプティブアイコンの処理は、素材を自分の形にマスクするので、それらのアセットはフルブリードの
  正方形のままにする。Windows、Linux、API 26 以前の Android ランチャーは渡されたものをそのまま
  描くので、それらのアイコンには角丸と透明が焼き込まれている — さもないとアプリは、ほかの丸い
  アイコンの隣で硬い青い四角として現れる。`scripts/make-icons.py` は意図して標準ライブラリ
  だけで書かれている：bootstrap は画像ツールを何も入れないからである。
- **デスクトップのクライアントは同時に多くのホストを抱え、スマートフォンは 1 台だけ抱える**：
  Windows、Linux、macOS の接続画面は自分では接続状態を持たない。応答したホストは接続ウィンドウ
  — `client/windows/win32/MainFrame.cpp` の `ConnectionFrame`、`client/linux/gtk/MainWindow.cpp`
  の `ConnectionWindow`、`client/macos/app/swift/App.swift` の `connection` `WindowGroup` — を
  得て、そのホストのアドレス、パスコード、機能、ソース、操作チェックを所有するので、画面は
  次をダイヤルする自由を保つ。メインウィンドウは開いているものの一覧だけを持ち、同じホストを
  二度ダイヤルしたときにウィンドウを前面へ出し、各ステータスプローブをアドレスの一致する
  ウィンドウへ押しやり、終了時にすべて閉じる。Android と iOS は意図して単一接続のままである：
  スマートフォンの画面に 2 枚目のパネルの余地は無く、開くセッションはどのみち全画面である。
  「同じホスト」の意味はどこでも `ui::SameDeviceAddr` である — 次の項目を参照。
- **ひとつのホスト、2 つの綴り、1 つの比較**：`ScanAddressText` はポートが既定なら省くので、
  走査で出た行は `192.168.1.60` と読めるのに、ユーザーが入力して接続したアドレスは
  `192.168.1.60:47777` と読める。それを文字列として比べると黙って失敗し、そうしていた場所は
  どこも本当に何かを失っていた：接続パネルは一致するデバイス行を見つけられず ping を表示せず、
  `PasscodeForDevice` は走査一覧から選んだホストに保存したコードを見つけられなかった。だから
  アドレスの等価は `ui::NormalizedDeviceAddr` / `ui::SameDeviceAddr`（`core/ui/Strings.h`）を
  通す。Swift と Kotlin のクライアントには `dh_same_device_addr` として公開されている。
  2 つのデバイスアドレスを `==` で比較しないこと。
- **パリティはグループ内で最も長いパケットに合わせる。MTU に合わせない**：パリティパケットは
  守っているデータパケットがどれだけ短くても、常に丸ごとの `Packetizer::kParityStride`
  （`kFecLenPrefix + kMaxVideoPayload`、1176 B）で送られていた。だから 1 パケットに収まる
  フレーム——動きの少ないデルタフレームのごく普通の形——が、数百バイトを守るために full-MTU の
  パリティパケットを丸ごと買っていた。オーバーヘッド 100 % である。パリティは今、
  `kFecLenPrefix` にそのグループで最も長いデータパケットを足した長さまで切り詰められる。
  `BuildFecPacket` は元から可変長の span を受け取り、`Reassembler::TryRecover` も元からそれ
  以上は必要とせず、それより短いものは拒否していたので、ワイヤ形式は動いていない。これが何を
  **直さない**かに注意すること：パケタイザは飛び飛びにインタリーブし（`i % numGroups`）、短い
  のはフレームの最後のパケットだけなので、2 パケット以上ではどのグループにも full-MTU の
  パケットが残り、フルストライドのパリティを受け取り続ける。その大きさから上では、コストを
  決めるのはパリティの**個数**、`ceil(count / kFecGroupSize)` だ——9 パケットのフレームは
  12.5 % ではなく 22 % を払う。FEC のオーバーヘッドはフレームサイズに対する曲線であって、
  グループサイズが示唆する単一の 1/8 では決してない。
- **トランスポートが拒んだデータグラムは、ネットワークが落としたものと見分けがつかない**：
  quiche 自身の輻輳制御か `kDatagramQueue` がそのパケットを受け取らないとき
  `quiche_conn_dgram_send` は失敗するが、`SendDatagram` はその結果で分岐しておきながら返す
  だけで、信号そのものを捨てていた。そういうパケットはマシンから出ていかないのに、視聴側の
  `Reassembler` にはただの穴に見えて損失として報告される。つまりホストは、自分で落とした
  パケットのために FEC のパリティを使い、自分のエンコーダのビットレートを下げうる。
  `QuicSendStats::datagramsRefused` がそれを数え、ホストの `evt=sum` 行が窓ごとに `dgram_tx`
  と `dgram_refused` を損失の数字の隣に載せる。FEC や輻輳制御の測定を信じる前にこの 2 つを
  読むこと：quiche の輻輳制御はデータグラム経路の下に `BitrateController` と直列に座っており、
  どちらも相手の存在を知らない。
- **FEC のグループ数は、これまでゼロだったヘッダのバイトに乗るようになった**：以前は両端が
  `ceil(pktCount / kFecGroupSize)` で導出していて、それが本来別々の二つのこと——何個の
  パケットが 1 個のパリティを共有するか、そして連続するパケットがグループ上でどれだけ離れるか
  ——を縛り付けていた。だからインタリーブ深度はフレームサイズの結果であって選択ではなかった：
  40 パケットのキーフレームは深度 5 を得るのに、60 fps でごく普通の形である 8 パケットの
  デルタフレームはグループが 1 つだけ、インタリーブは皆無。いちばん強いバースト耐性が、いちばん
  必要のない場所に座っていたことになる。`FecHeader::groups` がその数を、`BuildFecPacket` が
  かつて常に 0 と書いていたバイトに載せる。0 は今も「導出せよ」の意味なので、ヘッダの大きさは
  変わらず `kProtocolVersion` も上げていない。`FecGroupCount` が両端の呼ぶ唯一の関数であり、
  signalled なグループ数をパケット数で挟み込むので、グループ番号について両端が食い違うことは
  ない。代償は、そのフレームの最初のパリティパケットが届くまでデータパケットをグループに
  対応づけられなくなること——復元にはどのみちパリティが要るので無害だ。`LossGoodputTests` で
  平均バースト 4 パケット・5 % の Gilbert-Elliott 損失のもとで測ると、キーフレーム要求は
  導出深度での毎分 171 回から深度 8 での毎分 81 回へ下がり、壊れたフレームの救出率は 34 % から
  79 % へ上がった。
- **FEC のスキームは両端で設定するものであって、決して交渉しない**：`FecScheme` は
  インターフェースで、登録された実装は今のところ `xor` の一つだけ。`Packetizer` と
  `Reassembler` がそれぞれ一つ持つ。あるパリティパケットをどのスキームが書いたかは線上に
  一切書かれていない——ペイロードの形式はスキーム自身の領分だ——ので、ホストとビューアに違う
  スキームを与えると何も復元できず、その食い違いは「復元が一度も起きない」という形でしか
  表に出ない。実装が一つしかない段階ではこれは意図的である：`deskhub-cli share` と
  `connect` の `--fec NAME` は候補どうしを測り比べるために存在し、そのビルドに同名の
  スキームがなければ引数解析の時点で拒否される。誰かが選ぶための設定ではない。スキームを
  線上で伝えるのは、bake-off に勝って唯一の本番経路になった実装の仕事だ。それまでは
  `--fec` は測定器であり、同じセッションの両端にまったく同じものを設定しなければならない。
- **インタリーブ深度に順位をつけられるのはバースト損失モデルだけだ**：`LossGoodputTests` の
  リンクシミュレータは、損失率と平均バースト長でパラメータ化された、シード付きの 2 状態
  マルコフ連鎖に従ってパケットを落とし、その隣で一様乱数モデルを対照として走らせる。この対照は
  飾りではない——バーストモデルが本当にバーストしているかを確かめるための検査だ。同じ 5 % の
  損失で 1 グループあたりパリティ 1 個のとき、一様な損失は 71 % 救われるのに、固まった損失は
  34 % しか救われない。散らばった単独の損失こそパリティ 1 個が吸収できるものであり、1 つの
  グループの中に収まったバーストこそ吸収できないものだからだ。もし二つのモデルが同じ点数を
  出したなら、その連鎖は独立損失に退化しており、そこから得た深度やスキームの順位はすべて
  無意味になる。掃引の各点は `[csv]` の行を印字するので、FEC のどの判断の裏にある数字も
  テストを走らせ直せば再生成できる。
- **FEC が実際に働くかどうかを決めるのは FEC の方式ではなく、その起動ポリシーだ**：ホストは
  ビューアが損失を報告したときにパリティを起動し、`kCleanSecondsBeforeDroppingFec` の後に
  下ろす。二つの細部が、実際のリンクが示す種類の損失に対してこのポリシーを盲目にしている。
  `MakeFeedback` は損失を整数パーセントに丸めるので
  (`fb.lossPct = uint8_t(std::lround(w.lossPct))`)、0.5 % 未満はすべて平坦な 0 % として
  `BitrateController` に届く。そして起動条件は `fb.lossPct >= 1` なので、毎秒 1 パケットを
  落とすリンク——540 パケットの 1 秒における 0.1 %——はそもそも一度も起動しない。家庭の
  WiFi 上の実機ホストに対する実測：196 秒で 5 回の単独パケット損失、118 個すべての窓で
  `fec_rx` はゼロ、そして高々 1174 B の失われたパケット 1 個ごとに、フレームの破棄と約
  150 KB の完全な IDR を支払っていた。二台目のホストではサイクル全体が見えた：10 窓きれい、
  1 窓が 0.5 %、そのあときっかり 10 窓だけパリティ、そしてまた停止——1224 個のパリティ
  パケットを費やして修復できたのは 1 個。`LossGoodputTests` は今や本物の
  `BitrateController` を本物の `MakeFeedback` で駆動するので、シミュレータがこれを再現する：
  実測した動作点（損失 0.1 %、バースト長 1）で、常時オンの FEC は壊れた 16 フレームすべてを
  救いキーフレーム要求はゼロなのに対し、出荷中のポリシーは 30 % の時間しか起動しておらず、
  16 のうち 6 しか救わず、毎分 20 回の IDR を要求する。パリティが線上にあることを前提にした
  FEC 方式の比較はすべて、このポリシーがほとんど作り出さない構成を測っている。
- **目的関数は原因ごとに数えなければ、別のものを数えてしまう**：A1 は FEC を毎分のキーフレーム
  要求回数で採点するが、ネットワークが原因なのは `KeyframeReason::Loss` だけだ。ビューアが
  2 つ、リンクは 0 % 損失を報告し、再構成も一度もなかった 148 窓の間に、ホストはそれでも
  約 72 KB の完全な IDR を 10 回出した——そのどれもが、自分のデコードキューを溢れさせた
  ビューアからの要求だった。`q_overflow`、`dec_fail`、`display_congested` はクライアント側の
  パイプラインから来ており、`wait_idr` は起動時のものだ。ひとまとめにすると、試している
  トランスポートの変更の点数が水増しされる。原因はログ行にはあったのにカウンタのどこにも
  なかったので、`KeyframeRequestLog` は型付きの `KeyframeReason` を受け取り、窓ごとに原因別の
  カウントを持つ `evt=kf_sum` を印字する。それでビューアは直ったが、ホストは見えないままだった。
  IDR を払うのはホストの側であり、`RequestKeyframe` は空のデータグラムだったので、点数がまさに
  そのビットレートについて語っている当の機械にとって、どの要求も同じ顔をしていた。この
  メッセージは今、ペイロード 1 バイトで原因を運び、`ScreenHostSession` がそれを
  `onKeyframeRequest` に渡し、ホストは同じ分け方で `evt=kf_req_sum` を印字する。使えるものに
  している要点が二つある。このバイトができる前に作られたピアはペイロードを送らず、列挙の
  最初の枠ではなく `unknown` に入ること。そしてホスト自身の途中からの再参加は、ビューアの原因を
  借りずに `viewer_join` と名付けられること。その数字で何かを採点する前に、まず分解すること。
- **再送が何かを救えるかどうかを決めるのは、フレームがどれだけ保持されるかであって、再送
  経路ではない**：`PlanNack` と `RetransmitCache` は書かれたとおりに動く——シミュレータでは
  ホストはビューアが求めたすべてのインデックスを提供し、提供されたパケットはすべて届く。
  それでも 1 フレームも救えない。`PopReady` は、より新しいフレームが 2 つ完成した時点で
  未完成の非 IDR フレームを捨てる。60 fps ではおよそ 33 ms だ。一方 NACK は 2 ms の
  `kNackHoldUs` に加えて往復まるごとを要する：家庭のリンクの往復 40 ms では、修復パケットは
  それが直すはずのフレームが捨てられてから約 24 ms 後に着く。同じシミュレータで往復を 4 ms
  に縮めれば、同じ経路がフレームを救い始める。つまり A1 の「NACK-only」案は再送についての
  問いではまったくない——`kStallTimeoutMultiple` と overtaken 規則を RTT に対して見る問いで
  あり、RTT で FEC と NACK を切り替えるハイブリッドは、実際には「修復が届くときにそのフレーム
  がまだ在るか」で切り替えている。もう一つ：パリティが起動していると、NACK されるほど長く
  未完成のままのフレームは存在しない。FEC と NACK が同じ修復を奪い合うことはなく、両者の
  寄与は重なるのではなく足し合わさる。
- **保持ルールこそが答えのすべてで、単一の動作点で読んだことがそれを隠していた**：直前の段落は
  NACK-only を行き止まりだと結論した。それは損失 0.1 %、overtaken ルールを「より新しい 2 枚」に
  固定した条件での測定であり、つまり再送ではなく*ルール*を測っていた。修復モード × 往復時間 ×
  保持長を回した 72 点の掃引は、別のことを言う。損失 5 %・バースト 4・往復 40 ms では、出荷中の
  ルールで NACK-only は破損フレームを 11 枚救い、毎分 171 回キーフレームを要求する。フレームを
  自分の修復が届きうるまで待たせると、同じコードが **30** 枚を救い、要求は **72** 回になる——
  同じ点の `fec-only`（21 枚、171 回）より良く、しかもパリティを**一切送らない**。80 ms でも
  傾向は続き、`fec+nack` は毎分 63 回という、この網目で最良の数字に届く。往復 4 ms では何も
  変わらない。修復はもともと 2 フレーム以内に届くからだ。つまり利得は RTT とフレーム間隔の比
  そのものであり、だからこそ `OvertakenLimit()` は定数を引き上げるのではなく、修復窓から
  **導出**する。買えないのは無料の遅延だ——配信された 2 フレーム間の最大間隔は網目の中で上にも
  下にも動く。キーフレーム要求が減ることが、長い待ちの分を上回って払えることがあるからだ。
  単一の動作点で得た否定的な結果は、その点に
  ついての言明にすぎない。そして今回それは 3 倍の差を隠していた。
- **その導出がいまや出荷時の既定であり、根拠は掃引だけだ**：長らくこの門は閉じていた——呼び出し側
  が上限を 2 フレームより上に上げない限り `OvertakenLimit()` は古い 2 フレーム保持を返すので、
  掃引は導出を走らせられる一方、本番は測ったとおりの振る舞いを保っていた。
  `ScreenViewer::Config::overtakenLimit` は今 `kDefaultOvertakenLimit`（8 フレーム、60 fps で
  133 ms）を既定とし、それが門を開ける。8 はチューニングではない。掃引では 8 と 30 がどの点でも
  区別できなかった。往復およそ 130 ms までは導出値のほうが効いており、上限は裾を切るだけだからだ
  ——上限が無ければ 300 ms の回線は 29 フレーム、半秒近い遅延を、キーフレーム一つを節約するために
  抱え込む。利得は条件付きであり、省かずに述べる必要がある。40 ms 以上ではキーフレーム率を 1/2
  から 1/4 に下げ、高損失下では最長の停止**さえ短くする**。IDR を使わずに済めば、そのキーフレーム
  が費やすはずだった 120 ms も浮くからだ。往復 20 ms・損失 1% では小さな勝ち、20 ms・損失 5% では
  何も買えず最長停止に約 34 ms を足す。つまり LAN の視聴側が少し払い、WAN の視聴側が得をする。
  ⚠️ **これはすべてシミュレーションだけに立っている。**上の数字はどれも `core/tests` の種付きモデル
  から出ており、片道遅延は固定、**ジッタも並べ替えも輻輳も無く**、映像ではなくランダムなバイトを
  運ぶ。NIC には一度も触れていない。Phase 3 の検証のうち `netem` の半分こそがこれを裏づけるか覆す
  かを決めるものであり、それは**まだ走っていない**。
- **Reed-Solomon はグループあたり 2 つ以上のパリティパケットを要し、それは実装の細部ではなく
  ワイヤ形式の変更だ**：`FecHeader` はちょうど 16 バイトで全部に持ち主がいる（frameId 4、
  timestampUs 8、pktCount 2、groupIndex 1、groups 1）。`Packetizer` はグループごとに FEC
  パケットを 1 つだけ出し、受信側もグループごとにパリティを 1 つだけ保持していた。パリティ行が
  1 本の RS(k,n) は算術の重い XOR にすぎないので、この三層のどれもそれを運べない。パリティの
  番号は今、共通ヘッダの flags バイトに乗る。そこは bit 0（`kVideoFlagIdr`）と bit 1
  （`kVideoFlagFrameEnd`）しか使っていなかった：残る 6 ビットでグループあたり 64 個まで運べ、
  ヘッダを大きくすることも `kProtocolVersion` を動かすことも要らない。そのビットを読まない
  受信側は各グループの最初のパリティだけを残して他を無視するので、壊れるのではなく XOR に
  退化する。受信側のパリティは、入れ子の vector ではなくグループ番号と番号を 1 つの `uint16_t`
  に詰めた鍵で持つ——入れ子の形はグループごとに 1 回余分に確保し、それはすぐ表に出た：
  `video/reassemble-fec-recovery` が 1 パケットあたり 1.30 回から 1.43 回へ上がったのだ。方式
  そのものの実測コストは、グループあたりパリティ 2 個のとき、符号化が 1 フレーム 143 µs、XOR の
  22.7 µs に対して 6.3 倍。復元は 1 グループだけを回るのでわずか 1.4 倍にとどまる。グループ
  あたり 2 個の損失を救える力を買う値段がこれだ。
- **一つのインターフェースの背後にある四つの輻輳制御と、それぞれが実際に見えているもの**：A2 の
  選択肢は今、`aimd`（出荷中の AIMD、変更なし）、`delay-trend`、`scream`、`hybrid` であり、
  `MakeCongestionControl` が作り、`SourcePipelineState` が値ではなくポインタで持つ。読むうえで
  重要なのは、プロトコルの `Feedback` が 1 秒に一度、損失率・RTT・受信レートしか運ばないことだ。
  パケットごとの到着時刻は無いので、グループ間の遅延変動に対する文字どおりの WebRTC
  delay-gradient フィルタはここでは**作れない**。だから `delay-trend` は、RTT がその走行最小値を
  超えた分から導かれるキュー遅延を使い、`scream` は同じキュー遅延で抑えた報告受信レートに従う。
  これらはこのワイヤが運ぶ信号への適応であって論文の再実装ではなく、公表された GCC や RFC 8298
  の数字と比べることは別のアルゴリズムを比べることになる。`hybrid` は 二つのうち低いレートと、
  両者の FEC 判断の和を取る。四つとも同じ FEC 起動規則を共有するので、制御を切り替えても
  パリティがいつ出るかが黙って変わることはない。
- **ジッタのない再接続バックオフは、すべてのビューアを同じ瞬間に呼び戻す**：`ReconnectDelayUs`
  は試行回数の純関数として 500 ms から上限 5 s まで倍々に増えていたので、同じ瞬間に同じホストを
  失ったビューアは足並みを揃えて再試行し、毎回まとめて叩きに行っていた。今は呼び出し側が渡す
  `jitter` 語を受け取り、名目バックオフの上半分から引いた遅延を返す。再試行の頻度は有界のまま、
  戻ってくる時刻だけが散る。`core/` は `deskhubp/system/Random.h` に手が届かないので、乱数は
  引数として入ってくるしかない——すべての呼び出し側で署名が変わることこそが要点であって、
  不便ではない。
- **パリティ 1 行の Reed-Solomon は XOR そのもので、桁まで一致する**：Phase 3 の掃引は、方式 ×
  パリティ行数 × インタリーブ深度 × 損失率 × バースト長 × 往復時間にわたる 180 点を、FEC を
  強制的にオンにして走らせる。起動ポリシーではなく方式を測るためだ。損失 5 %、バースト 4 で、
  パリティ 1 行の `rs` と `xor` はどの深度でも同一の数字を出す——導出深度で壊れたフレームの
  33.9 % を救い、キーフレーム要求は毎分 171 回。深度 8 では 78.7 % と 81 回。代数がそうなると
  言っているとおりであり、実装が正しいことの有用な検算でもある。同時にそれは、パリティが 2 行
  未満では RS が何も生まないのに符号化 CPU を 6.3 倍払うことを意味する。だから 1 行は、RS を
  実際に載せる構成には決してならない。**オーバーヘッドを数に入れれば、この網目の中に出荷中の既定値を上回る点は一つも無い。そして
  その列を見ずに掃引を読むことが、逆の結論に至る道だ。**インタリーブ深度の切り離しは CPU を
  増やさないので、つい無料だと呼びたくなる：救出率を 33.9 % から 78.7 % へ、キーフレーム要求を
  毎分 171 回から 81 回へ動かすのだから。しかし同時にパリティのオーバーヘッドを 15 % から
  **100 %** へ引き上げる——1 パケット 1 グループでは、どのパケットも自分のパリティを背負う。
  それは符号化ではなく複製だ。20 Mbps の予算では、絵のおよそ半分を使ってキーフレーム要求を
  半分にすることになる。深度 4 でパリティ 3 行の `rs` は毎分 36 回に届くが、オーバーヘッドは
  **150 %** だ。したがってこの掃引は**昇格させるべき勝者を出さない**。その結論は、既定値は
  そのまま据え置き、参加者は `--fec` の後ろに参照として残る、である。`overhead_pct` は今や
  CSV の独立した一列であり、深度がパリティを 3 倍以上多く払うことをテストが表明する——同じ
  掃引についての最初の記述が、深度をこの網目でいちばん安い梃子と呼び、間違っていたからだ。
- **残した実装が場所に値するのは、まだ届いて、まだテストされているからであって、あらゆる
  sanitizer の下で掃かれるからではない**：Phase 3 の掃引は誰も昇格させなかったので、`rs` は
  本番から選ぶ手立てのないままツリーに残る——`Packetizer` も `Reassembler` も
  `kDefaultFecScheme` から始まり、`ShareOptions` と `ScreenClientConfig` は何かが求めるまで
  どの方式の名も挙げず、求めるのは `deskhub-cli --fec=NAME` だけだ。その届くということこそ、
  負けた実装を残しておく理由のすべてであり、だから今はそれを習慣に委ねず、テストが表明する。
  残すことも無料ではない：`rs` は 1 フレームを 143.9 µs で符号化し、XOR の 22.8 µs に対して
  6 倍以上かかる。その両方を回す掃引は `core_tests` の時間の大半を占める——完全な行列で 8.6 s、
  出荷している方式だけなら 2.9 s、しかも ASan や TSan がそれを掛け算する前の話だ。
  `DESKHUB_FEC_MATRIX=shipping` が小さいほうの行列を選び、sanitizer のジョブは差分が
  `FecScheme` かそのテストに触れていない限りそれを設定する。こうして参照実装は、それを壊し
  うる変更のときにこそ sanitizer の下で掃かれ、通常の 8 つの unit ジョブは毎コミット変わらず
  それを覆う。認識できない値は黙って選ばずに実行を失敗させる。「この実行が実際にどの実装を
  覆ったのか」は、打ち間違いに答えさせてよい問いではないからだ。
- **自分のテスト以外に呼び出し元のないつまみは、つまみではない**：Phase 3 の掃引は三つの軸——
  方式・パリティ行数・インターリーブ深度——を動かすが、ビルド済みのバイナリから届くのは最初の
  一つだけだった。`--fec` は方式を選ぶ。そしてその方式こそ、掃引自身が最も効かない軸だと示した
  ものだ。パリティ 1 行の `rs` は `xor` を桁まで再現する。数字を実際に動かす二つには手が届かな
  かった。`Packetizer::SetFecGroups` は `core/tests` の外に呼び出し元が無く、Phase 1 が
  `SetVideoPath` で踏んだのと同じ形の誤りだ。さらに悪いことに、パリティ比は届きはするが
  **保てなかった**：`ViewerBroadcast` は放送のたびに `wantFecParity` から
  `SetFecParityPerGroup` を呼び、その `wantFecParity` を `ApplyFeedback` が毎秒
  `FecParityRowsFor(lossPct)` で書き換える——損失 3 % 未満なら 1 行、6 % 未満なら 2 行、それ以上
  なら 3 行。つまり良いリンクでは方針が 1 を返し、そこでの `--fec=rs` は `xor` そのものに、
  6.3 倍の符号化 CPU が付いただけになる。自宅 Wi-Fi で測った人は「Reed-Solomon は何も変えない」
  と結論しただろう——それが違いを見せる構成で一度も走らせないまま。今は `--fec-parity` が方針に
  上書きされないよう比を固定し、`--fec-depth` が `SetFecGroups` に届き、`--fec-arm always` が
  パリティを線上に保つので、測られるのは方式であって起動方針ではない——これはシミュレーションの
  掃引がやっていることそのもので、これらのフラグの意味は、同じ問いを本物のリンクにも投げられる
  ようになったことにある。あるフラグが測定を再現できると信じる前に、本番コードでそれを読む行を
  探すこと。setter とテストは、その行ではない。各ソースは、自分が最終的に落ち着いた構成もログに
  残す。しかもオプションからではなく packetizer から読み戻した値だ——パリティ 3 行を求められた
  あとに出る `FEC measurement: scheme=xor parity=1 depth=4 arm=policy` こそが正直な答えである。
  `xor` は 1 行しか運べないからだ。そして掃引の 1 行が、実際に走った値ではなく要求された値で
  ラベル付けされているなら、その行は無いほうがましだ。
- **同じ「呼び出し元がない」がさらに四箇所にあり、うち一つは今もそうだ**：その検査を Tier A の
  残りに走らせると、`SetCongestionControl`、`SetAdaptiveTarget`、`SetAdaptiveLead`、
  `SetDisplayIntervalUs`、`MakeClockOffsetEstimator` のいずれも、自分のテスト以外に呼び出し元が
  **0** だった。4 つの輻輳制御のうち 3 つは選べず、適応音声目標は入れられず、3 つの時計推定器は
  掃引の中にしか存在しなかった。今は `--cc` がホストの制御ループに届き、
  `--audio-delay` / `--audio-adaptive` がビューアのジッタバッファに届く。どちらも生きている
  オブジェクトから読み戻してログに残す。残る二つは**意図して手を付けない**：`ClockOffset` を
  使うのは `VideoPacer` だけで、その `VideoPacer` を使うのは `VtDecoder` だけだ——つまり
  Windows と Linux には設定すべき pacer が存在せず、そこに `--clock` や `--vsync` を足すことは、
  この項目が問題にしているまさにその偽のつまみを作ることになる。`RollingMinEstimator` は
  `ClockOffset` の**純粋なラッパ**だと確認済みなので、`VideoPacer` を契約に載せ替えるのは
  振る舞いを変えない変更だ——ただし Apple 以外のビューアが pacer を使い始めたときにやるので
  あって、その前ではない。本番の呼び出し元を持たない契約は、インタフェースの衣をまとった掃引の
  治具にすぎず、その裏に実装を書き足してもそれは変わらない。
- **pacer は、3 つの時計推定器が食い違う当のメソッドを一度も呼んでいなかった**：`VideoPacer` を
  `ClockOffsetEstimator` 契約に載せ替えたうえで——`rolling-min` は元々埋め込まれていた
  `ClockOffset` の純粋なラッパなので、これは振る舞いを変えない変更だ——到着揺れ 0/5/20 ms、
  30 ms の伝送段差あり・なしで 3 つすべてを回す 18 点の掃引を走らせた。**区別がつかない**：
  位相の散らばりはどの推定器のどの点でも 6898〜6937 µs に収まり、`kalman` は `rolling-min` を
  マイクロ秒まで再現する。理由はアルゴリズムではなくインタフェースにある。pacer が呼ぶのは
  `AddSample`・`ready`・`Reset`・`floorUs` であって、**`LatencyUs` は一度も呼ばない**。そして
  3 つが違う実装をしている唯一のメソッドがその `LatencyUs` だ。`KalmanEstimator::floorUs()` は
  `lowest_` を返す——それは**まさに**移動最小値である。したがって A5 はジャダーでは採点できない。
  動かす軸は公開される `e2e_abs_ms` のほうで、A5 自身のテストはすでにそこで測っている。
  bake-off を走らせるために契約を利用側へ接ぐ前に、その利用側が参加者たちの食い違うメソッドを
  実際に呼ぶかを確かめること。さもなければ掃引は、同じ数字の整った表を出すだけだ。
- **参照が失われたあと符号器に何を頼むかは方針であり、それが定数になっていた**：ビューアの
  `InvalidateRef` メッセージはすでにワイヤを端まで渡っており、ホストはそれに
  `forceIdr.store(true)` で答えていた——つまり「参照の無効化」はどの場合も丸ごとの IDR
  だった。`media::RecoveryPolicy` は今、バックエンドが自分にできると申告した内容から三つの
  答えを選ぶ：失われたフレームより古い最新の長期参照へ戻る、転がる intra refresh を始める、
  あるいはキーフレームを送る。覚えるべき規則が二つある。失われたフレームより**新しい**参照は
  決して使えない。ビューアがそれを一度も復号していないかもしれないからで、安全なのは古い方
  だけだ。そして、まだ一枚も符号化されないうちに二度目の損失報告が届いたなら、安い答えが
  効かなかったということなので、堂々巡りせずキーフレームへ格上げする。
  `ReferenceInvalidatingEncoder` と `IntraRefreshEncoder` は `VideoContract.h` の任意
  concept に加わった。Windows の二つのバックエンドは今それらを実行する。残る四つは何も宣言しない
  ので能力集合は空のままで挙動も変わらない——方針の良さは、それを実行できるエンコーダの分だけだ。
- **コーデック交渉はビット 1 本の判定でしかなく、マスクは最初から 16 ビット幅だった**：
  `Hello` は `codecMask` を、`HelloAck` は `Codec` を運んでいたのに、ホストは
  `codecMask & kCodecMaskH264` しか見ず `Codec::H264` と答えていた。マスクは今
  H264 4:2:0、H264 4:4:4、HEVC、AV1 に名前を与え、`NegotiateCodec(hostMask, clientMask)` は
  明示的な優先表のうち両端が持つ最初の項目を選び、その表の末尾に座る 4:2:0 の基準へ落ちる。
  末尾に置いてあるのは、それが床であって決して第一候補にならないようにするためだ。古い対向は
  ビット 0 だけを申告し、これまでどおり H264 で合意して値 0 を受け取るので、ワイヤ上で動かす
  必要のあるものは何もなかった。ツリーの中のどの符号器も H264 4:2:0 以外を作らないので、この
  仕組みは今日のところ不活性だ——それこそ C3 が求めたもの、レースではなく能力表と交渉である。
  順序そのものは**暫定**だ：文字の鮮明さのための 4:4:4 が、ビットレートのための AV1 より上に
  来るべきかどうかは、まさに C3 が解くために在る問いであり、この順序がまだ持っていない測定を
  必要とする。
- **片道の流れからは、推定器がどれだけ良くても絶対遅延は決して出てこない**：三つのオフセット
  推定器——移動最小値、トレンドライン、カルマン——が受け取る入力は同じで、フレームのホスト側
  タイムスタンプとローカル到着時刻の差だ。そしてその差は、クロックオフセットと片道遅延が
  溶接されたものである。どれも下限を引いて超過分を報告するので、`e2e_ms` は待ち行列についての
  数字であって遅延についての数字ではなく、他のツールの数字と並べても意味がなかった。直し方は
  もっと良いフィルタではなく、**二つ目のタイムスタンプ**だ：`PingPong` はクライアントの
  `sendTimeUs` の隣に `hostTimeUs` を運ぶようになり、`ClockSync` は 10 秒窓の中で往復が最小の
  やり取り——待ち行列がいちばん少なかったもの——を保持してクロックオフセットを推定する。
  端から端までの絶対遅延はそれで `(到着 - オフセット) - hostPts` となり、相対の `e2e_ms` の
  隣に `e2e_abs_ms` として報告される。ペイロードは 12 バイトから 20 バイトに伸びたが、これは
  安全だ。共通ヘッダはペイロード長を運ばず、`ParsePingPong` は元から最初の 12 バイトしか
  要求していなかったからである：古い対向は元の三つのフィールドを読んで残りを無視し、新しい
  対向が古い 12 バイトのメッセージを読めば `hostTimeUs == 0` を見て相対の数字に戻る。これは
  経路が対称であることに依っている。それは NTP の仮定であり、コードの限界ではなく手法の限界だ
  ——非対称な経路は、その非対称の半分をそのままオフセットに押し込む。
- **符号なしで書かれた指数フィルタは、入力が初めて下がった瞬間に逆方向へ走り出す**：音声側の
  ジッタ推定も pacer 側のそれも `jitterUs_ += (spread - jitterUs_) >> shift` と書かれており、
  `spread` も `jitterUs_` も `uint64_t` だった。走行平均より静かな標本が来ると、この引き算は
  2^64 近くまで回り込み、シフトはそのほとんどを残すので、推定値は減衰せず**膨張する**。これは、
  音声の遅延／途切れ曲線を実際に描いてみて、15 ms しか揺れないリンクで適応目標が 500 ms の上限
  に張り付いているのを見るまで、見えないままだった。どちらも今は `int64_t` で計算する。見つけた
  のは曲線であって、その周りの単体テストでもコードの見た目でもない。
- **遅延対途切れの曲線は、固定の音声目標が今も正しい既定値だと言っている**：フィルタを直し、
  再生を到着ではなく時計で駆動するようにしたうえで、掃引は三段階のジッタに対して六つの目標遅延を
  走らせる。適応目標は安定したリンクで完勝する——起動時の 1 回の途切れはそのままに、60 ms では
  なく 20 ms を保つ——が、ジッタの下では**負ける**：40 ms の揺れでは固定目標と同じ 60 ms に
  落ち着きながら、隠蔽を 1 回ではなく 4 回払う。代償は適応そのものにある。途中で目標を上げると、
  その水位まで貯まるのを待つことになり、その待ちが欠落だ。キューがすでに足りているときだけ
  上げるようにすればその大半は消えるが、今度は目標が不足しがちになる。これを既定で有効にするのは、
  実測された途切れの増加を、そもそも問題ではなかったリンクでしか掃引が確かめていない遅延の利得と
  引き換えにすることだ。
- **vsync 合わせは遅延との取引ではない、というのが掃引の示したことだ**：A6 はジャダーを「追加
  遅延に対して描くもの」として枠付けたので、掃引は pacer のリードを 8 ms から 66 ms まで変え、
  スナップの有無それぞれで走らせる。スナップしないと、6944 µs のリフレッシュ間隔の中でフレームが
  落ちる位相は**どのリードでも**およそ 6000 µs に散らばる——遅延を 8 倍にしても 1 マイクロ秒も
  狭まらない。その散らばりは 60 fps の内容が 144 Hz のパネルに出会うことから来るのであって、
  到着の揺れから来るのではないからだ。スナップはそれをちょうど **0** にし、遅延を一切払わない。
  ここに取引していける曲線は無い。あるのは欠陥と、その直し方だけだ。
- **HRESULT は bool ではなく、`ICodecAPI::IsSupported` は「はい」を `S_OK` で返す**：Media
  Foundation エンコーダが設定するレート制御プロパティは、すべて
  `if (!codecApi->IsSupported(&api)) { report("NOT SUPPORTED"); return; }` を通っていた。`S_OK`
  は 0 なので、この分岐は MFT が**実際に対応している**プロパティでちょうど発火し、`SetValue` は
  対応していないものにしか試されていなかった。生の HRESULT をログに出したうえでこのマシンで実測
  すると、`MeanBitRate`、`RateControlMode=CBR`、`GOPSize`、`BufferSize(VBV)` はすべて
  `hr=0x00000000` を返し、そのすべてが飛ばされていた。つまり MF バックエンドは生涯ずっと MFT の
  既定値で符号化していた——CBR も、目標ビットレートも、無限 GOP も、VBV も無しで——一方 NVENC は
  レートプランを丸ごと受け取っていた。この修正より前の両者の比較は、設定済みのエンコーダと未設定の
  エンコーダを並べていたことになる。これは本節の最初の項目の根拠も裏返す：そこで引用されている
  `MeanBitRate: NOT SUPPORTED` の行は、Intel の MFT がそのプロパティを**持っていた**という意味
  だった。その項目が主張する「フォールバックは必須にせよ」は今も正しい。誤っていたのは、そのために
  挙げた理由が裏返しに読まれたログだったという点だ。同じファイルの `SetBitrate` と
  `RequestKeyFrame` は逆の極性を使っていた——三値の戻り値を bool の形で読むとこうなる：両方が同時に
  正しいことはあり得ない二つの呼び出し箇所と、それを見分けられるテストが一つも無いという状態だ。
- **C1 のつまみに欠けていた呼び出し元は、A1 に欠けていたのと同じものだった**：`CreateEncoder` は
  NVENC を試し、次に Media Foundation を試し、先に起動したほうを使っていた。だから NVIDIA
  ドライバのあるマシンでは MF 側をそもそも測れなかった。いまは
  `--encoder auto|nvenc|mf|vaapi|videotoolbox` がバックエンドを名指しし、起動しないものを名指し
  した場合はソースを**止める**——黙ってもう一方を測ったりしない。フォールバックが隠してしまう失敗
  こそが測定結果だからだ。採点には新しいカウンタも要った：`enc_ms_avg`/`enc_ms_max` では裾が見え
  ないので、`evt=sum` は 512 µs のヒストグラムから `enc_us_p50` と `enc_us_p99` を運ぶようになっ
  た。各バックエンドは復旧能力も、仮定ではなく**ドライバから読んで**報告する：NVENC は
  `nvEncGetEncodeCaps` 経由（RTX 5070 Ti で `max_ltr_frames=8`、`ref_pic_invalidation=1`、
  `intra_refresh=1`）、Media Foundation は三つの LTR プロパティと `GradualIntraRefresh` への
  `IsSupported` 経由で、いずれも対応。これは A4 が待っていた答えになる——Windows の両バックエンド
  とも長期参照フレームを保持できる——が、エンコーダが実行できるようになるまで、この能力は
  **ログに出すだけ**で `RecoveryPolicy` には渡さなかった：`invalidateBeforeFrame` も
  `wantIntraRefresh` もまだ誰も消費していない段階で能力を宣言すれば、損失復旧が何もしない処理に
  変わってしまう。最初の数字は、
  固定クリップではなくアイドルのデスクトップ上のもの：NVENC は p50 2.5-5.6 ms・p99 2.7-5.7 ms、
  Media Foundation は p50 0.5-13.8 ms・p99 12.3-17.6 ms。ここでは両者とも同じシリコンに届いている
  ——このマシンでは `mf` は "NVIDIA H.264 Encoder MFT" に解決される——ので、これはまだ C1 が問う
  Intel 対 NVIDIA の問いではない。同じハードウェアに Media Foundation 経由で届くことの代価だ。
  二台目の Windows マシンがその二つを切り分ける。NVIDIA のドライバが一切入っていない Intel UHD
  750 では `mf` は "Intel Quick Sync Video H.264 Encoder MFT" に解決され、三つの LTR プロパティと
  `GradualIntraRefresh` をすべて対応と報告し、1920 × 802 を p50 1.5-2.6 ms・p99 2.5-8.4 ms で符号
  化する（ときおり 27 ms に達する窓もある）。これが C1 の求めていた Intel の列であり、Quick Sync
  も長期参照を保持できると言っている——ただし上の NVENC の行との公平な勝負では**まだない**。マシ
  ンが違い、キャプチャ寸法が違い、デスクトップの中身が違い、どちらも固定クリップではない。同じ実
  行が名指しの規則も端から端まで裏づけた。そのマシンで `--encoder nvenc` は "Failed to load
  nvEncodeAPI64.dll" と出して該当ソースを止め、NVENC の名前のまま黙って Quick Sync で符号化した
  りはしない。`--encoder auto` は Media Foundation まで落ち、なぜ先へ進んだかを記録する。
- **`QuicEndpoint::Poll` は毎回スリープで終わっていた。それを見えるようにしたのがバッチ読み取り
  だ**：読み取りループは何も返らなくなるまで `RecvFrom` を呼び続けるが、「何もない」が返るのは
  `SO_RCVTIMEO` が切れた後だけだ——つまりソケットをすでに空にしたポーリングでも、そのタイムアウト
  の下限、よくある場合は 1 ms を、呼び出しのたびに払っていた。`SessionTransport::RecvFrom` は
  同じ `Poll` を自前の `WaitReadable(10 ms)` の後ろに置いているので、このスリープは受信のたびに
  積み増されるだけの費用だった。`recvmmsg` によるバッチ読み取りは、その探りの読み取りを丸ごと
  不要にする：バッチが短く返ってきたらソケットは空であり、ループはもう一度尋ねずに止まれる。
  残ったのが `SetRecvTimeout(0)` で、POSIX はこれを「永遠に待つ」と読むため旧コードは 1 ms へ
  丸めていた。いまは「待たない」を意味する（POSIX では `O_NONBLOCK`、Windows では `FIONBIO`）。
  `Poll(now, 0)` がずっと名乗っていたとおりのものだ。安全なのは、0 を渡す呼び出し側がすでに自分
  の待ちを持っているからだ——`WaitEstablished` はポーリングしてから待ち、`RecvFrom` は待ってから
  ポーリングする——ので、どこもスピンにはならない。`platform_perf` がループバックで測った値：
  アイドルのポーリング 1 978 692 ns → 732 ns、512 バイトの端末レコード 4 244 632 ns → 9 201 ns、
  64 KB のストリーム 16.7 MB/s → 500.7 MB/s、QUIC データグラム 248 515 ns → 3 986 ns、そして
  64 KB→256 KB の吸い出しは線形のまま（4 倍の仕事に対して 3.78x → 3.84x）。ループバックは実際の
  リンクのスループットについては何も語らないが、取り除いた 1 ms の下限はどのリンクでも実時間だ。
- **バッチ化そのものが買ったものは、それが暴いたスリープより小さく、送信側は受信側より大きい**：
  `sendmmsg` はすでにバーストを一回のシステムコールにまとめていたので、`UDP_SEGMENT`（GSO）が
  買うのはシステムコール数ではなくカーネル側の仕事だ——UDP/IP スタックを十六回ではなく一回通る。
  ループバックで 16 × 1200 バイト：データグラムごとに `sendto` 一回と `recvfrom` 一回で
  2036 ns/データグラム、送信側だけバッチ化すると 636 ns、両側で 623 ns。つまりここでは GSO が
  3.2 倍ぶんで、最後の一段は実行ごとのノイズの中にある——バッチ化した二行は走らせるたびに順位が
  入れ替わった——カーネルがすでに全パケットを持っていて受信がほぼ無料のループバックだからだ。
  それでも `recvmmsg` に居場所があるのは、ループが探りを入れねばならない理由そのものを取り除く
  からだ：`strace` の下で `platform_tests` を一回走らせて測ると、17 317 個のデータグラムが
  1631 回の実りある呼び出しで届き、システムコールあたり 10.6 個だった。
  GSO が使えるのは同じ大きさのデータグラムの並び（最後だけ短くてよい）に限られ、それはまさに
  `quiche_conn_send` が作る形だ。拒む カーネル（`EIO`、`EINVAL`、`ENOPROTOOPT`、`EOPNOTSUPP`、
  `EMSGSIZE`）に当たったら、そのソケットはバーストごとに試し直すのではなく恒久的に `sendmmsg`
  へ戻る。
- **ホットループのアロケーションは自分のスリープの陰に隠れられる**：`Service()` は呼び出しの
  たびに接続 id の `std::vector` を作り、`DrainStreams` は毎回 16 KB のチャンクバッファを、
  `DrainDatagrams` は 1350 バイトのものを作っていた——`Poll` あたり約 1.5 回のアロケーションで、
  しかもパケットごとに走る経路の上でだ。どのポーリングも 1 ms 眠っているあいだは何も見えなかった。
  スリープが消えた途端、`quic/terminal-record-delivery` はレコードあたり 9 回から 27 回へ跳ねた。
  同じレコードがいまや三倍のポーリング回数を要し、その一回ごとにアロケートしていたからだ。修正は、
  二つの id リストを `kMaxConnections` で上限を切ったスタック配列にし、二か所の吸い出しを
  エンドポイント自身が持つバッファにし、読めるストリームが無いときは `DrainStreams` がバッファに
  触れる前に戻ることだ。`quic/poll-idle` はポーリングあたり 3.00 回から 0.00 回になった。この形は
  覚えておく価値がある：パケットごとに走って眠る経路は自分の費用を隠し、何年も通っていた
  アロケーション予算が測っていたのは、そのスリープだった。
- **損失カウンタが測っていたのは修復を生き延びたものであって、リンクが実際に何をしたかではない**：
  `packetsLost` と `lossRuns` ヒストグラムはどちらも `Drop()` の中で加算されるため、**捨てられた**
  フレームで欠けたパケットしか数えてこなかった。FEC が再構築したパケットも、NACK が取り戻した
  パケットも、どこにも痕跡を残さない。Tailscale 越しの、中央値 5.7 Mbps の負荷ありの五分間セッションが、
  その死角を直接測った：**48 個のパケットが欠席**し、うち 41 個は二度と到着せず、7 個は NACK が
  フレームの完成に間に合うように取り戻した。その 7 個——およびヒストグラムに一度も届かなかった
  2 パケットのランひとつ——こそが旧カウンタに見えないものだ。旧カウンタは捨てられたフレームしか
  見ないからである。したがって、そこから引き出す Gilbert-Elliott パラメータはすべて**修復不能な**
  損失のパラメータであり、FEC と NACK がうまく働くほど偏りは大きくなる。（`latePackets` は別物で
  あり、ここでの証拠にはならない：フレームが**すでに**捨てられた後に到着した修復を数えており、
  その損失は破棄の時点で計上済みだ。）修正は隙間を走査するのではなく、隙間が実際に姿を現す三つの瞬間に
  印を付ける——見た最大インデックスより小さい位置をパケットが埋めたとき、`TryRecover` が断片を
  再構築したとき、そして断片が空のままフレームがキューを去るとき（失われた末尾が気付かれる唯一の
  経路だ。それを暴くより大きなインデックスはもう来ないのだから）。以後、欠席したパケットはちょうど
  四つの箱のどれか一つに入る：到着しなかった、FEC が修復した、NACK の要求後に修復された、単に順序が
  入れ替わっただけ。最後の箱を分けるのは装飾ではなく構造だ——順序の入れ替わりは損失ではなく、
  混ぜ込めばバーストモデルを膨らませる——ゆえに `wire_loss%` は
  `(everAbsent − reordered) / (received + neverArrived)` である。既知の偏り：`nacked[i]` は
  `PlanNack` がそのインデックスを選んだ時点で立つので、要求もされ単に遅れてもいたパケットは NACK
  修復として記録される。これは損失と見なす側に寄せる誤差だ。`evt=sum` は今 `wire_loss` /
  `absent` / `gone` / `nack_fix` / `reorder` を運び、`wire runs` ヒストグラムが従来の `loss runs`
  の隣に並ぶ。どちらも他方の代わりにはならない：古い行は視聴者が被ったもの、新しい行はリンクが
  したこと。バイクオフには後者が要り、ユーザーの不具合報告には前者が要る。
- **方針に行為を名指しさせる前に、エンコーダへ実行する力を渡す**：`RecoveryPolicy` は A4 の時点
  で完成していて、A4 の時点からずっと動いていなかった。能力集合を空にしてあったのは意図的だ。
  長期参照フレームを一枚も保持しないエンコーダを抱えたまま能力を宣言したホストは、参照フレームを
  失ったときに `invalidateBeforeFrame` を立て、誰もそれを読まず、しかもかつて要求していた IDR も
  もう要求しない——損失復旧が「高価」から「無い」に変わる。だから実行を先に入れ、`SetCaps` を最後
  に置いた。`IVideoEncoder` には `MarkLongTermReference`・`InvalidateReference`・
  `BeginIntraRefresh` が加わり、`static_assert` が `ReferenceInvalidatingEncoder` と
  `IntraRefreshEncoder` に縛り付ける——あの二つの任意 concept が書かれた目的そのものだ。NVENC は
  LTR Per Picture（`enableLTR=1`、`ltrTrustMode=0`）を四スロットのリングで回し、
  `maxNumRefFrames` もそれに合わせて上げる：マークは `ltrMarkFrame`/`ltrMarkFrameIdx`、修復は
  `ltrUseFrames`/`ltrUseFrameBitmap`、リフレッシュは `forceIntraRefreshWithFrameCnt`。
  `nvEncInvalidateRefFrames` はあえて使わない——ビットマップこそ決定的な道で、何が壊れたかを名指し
  して残りを推論に委ねるのではなく、次のピクチャが何を参照してよいかを直接述べるからだ。
  `InitializeEncoder` で LTR を拒むドライバには LTR 抜きで一度だけ再試行し、共有そのものを落とす
  ことはしない。Media Foundation は init で `AVEncVideoLTRBufferControl` を通し、以降はピクチャ
  ごとに `MarkLTRFrame`/`UseLTRFrame`/`GradualIntraRefresh` を使う。そして `RequestKeyFrame` は
  今やリングを忘れる——IDR は DPB を空にするので、記録を残したままにするのは自分を欺くことだ。
  `deskhubp/host/EncoderRecovery.h` がその継ぎ目になる：`PrepareRecovery()` は
  `invalidateBeforeFrame` と `wantIntraRefresh` を消費し、エンコーダが実行できないときは IDR に
  落ち、方針が後から名指しするフレームをちょうど過不足なくマークする——IDR も含めてだ。ここを抜か
  すと、エンコーダが持っていない長期参照を `core` が信じたままになる。二つの concept による
  `if constexpr` で包んであるので、Linux・Apple・Android はそれぞれのエンコーダが三つの呼び出しを
  備えるまで今日の挙動を保つ。Windows はエンコーダを作るたびに**毎回**
  `recovery.SetCaps(encoder->RecoveryCaps())` を呼ぶ。`SetCaps` は方針の状態もリセットするから
  だ——作り直されて保持していた参照をすべて失ったエンコーダに、まさに必要なことだ。前処理は
  `EncodeTimed` の中にあるので、フレーム経路も flush 経路も両方そこを通り、二か所に写す必要がない。
- **誰も呼んでいないクラスは、最初の呼び出し元を待っているデータ競合だ**：`RecoveryPolicy` は
  二つのスレッドから触られる——`OnReferenceLost` はホストの net loop、`NoteEncoded` と
  `ShouldMarkLongTerm` は `encMutex` の下のエンコードスレッド——のに、ロックを持っていなかった。
  復旧を実行できるバックエンドが無く、この経路が一度も走らないあいだは、それで何のコストもない。
  Windows で有効にした途端、TSan が最初の損失で報告した。このクラスは今は自前のミューテックスを
  持ち、コピーもできない。もともと誰もコピーしていなかった。空の能力集合の後ろに停めてある部品は、
  テストが緑だからスレッド安全だと示されたわけではなく、ただ触られていないだけだ。
- **クロスプラットフォームな最適化の半分は、それを一度も受け取らなかったプラットフォームだ**：P2
  は送信経路がバッチ化されると言い、実際そうなっていた——Linux では。`UdpSocketWin::SendBatch` は
  `sendto` のループで、データグラム一つにつき一システムコール。つまり上の記述がバッチ化された送信
  側を描いているあいだ、Windows ホストはパケットごとのコストを丸ごと払っていた。いまは
  `UDP_SEND_MSG_SIZE` 制御メッセージ付きの `WSASendMsg` を呼ぶ——`UDP_SEGMENT` の Windows 版だ。
  `Open` で `WSAID_WSASENDMSG` から一度だけ解決し、スタックに拒まれたらバーストごとにではなく
  **恒久的に**取り下げて、データグラムごとに一回 `sendto` する同じ経路へ落ちる。P2 が挙げたものの
  うち安いほうの半分であり、だからこそ RIO より先に来る。`LeadingRunOfEqualSegments` は
  `UdpSocketPosix.cpp` から `deskhubp/net/UdpSocket.h` へ移り、二つの OS が写しを二つ持つのでは
  なく一つの規則を共有するようになった。「短いデータグラムは run の最後のセグメントにしかなれない」
  という規則も、loopback の往復だけでなく単体テストで固定されている。上の loopback の表は Linux の
  数字だ：`platform_perf` はこの変更の前後を Windows で走らせていないので、あの数字は持ち込めない。
- **`enc_lat_ms` はそもそもキャプチャの数字ではなく、キャプチャ時計には読み手がいなかった**：C2
  が問うのは、DXGI Desktop Duplication に対して Windows Graphics Capture が遅延をどれだけ払うか
  だが、最初に分かったのはその数字が印字されていないのではなく**存在していない**ことだった。
  `ScreenCapture.cpp` は WGC の `SystemRelativeTime` から `fi.meta.timestampUs` を埋めていたのに、
  誰もそれを読んでいない：`SharingHost` はフレームから `width` と `height` だけを取り、`Encode`
  には真新しい `NowUs()` を渡す。だから `enc_lat_ms` はエンコーダを測っていて、キャプチャ→
  テクスチャについては何も言っていない。二つの時計は初めから揃っている——`SystemRelativeTime` は
  100 ns 単位の QPC で、Windows の `NowUs()` も QPC だ——ので差はそのまま使え、エポック変換も要ら
  ない。この問い全体が呼び出し一つで済むのはそのためだ。`SourceDiag::NoteCapture` はフレームの
  タイムスタンプとそれがホストに届いた時刻を受け取り、フレームの齢を `cap_us` のパーセンタイルに
  入れ、二度目に手渡されたフレームは測り直さずに `cap_repeat` として数える。繰り返しの齢は最初の
  キャプチャからの経過であり、裾を膨らませてしまうからだ。これは `core/` にあるので、残る四つの
  キャプチャバックエンドは一行ずつで接続できる。それまでは `ShareDiagCaps::captureLatency` の陰に
  隠れ、空の列を印字しない。「WGC の便利さの代価は」に答えるにはこの列だけで足り、他は要らない。
  数字が悪かったときに初めて Duplication バックエンドを書く価値が出るし、書くなら
  `--capture wgc|dxgi` を持ち、名指しされたバックエンドが起動しなければ**止まる**——`--encoder`
  がすでに従っている規則と、同じ理由で同じ形だ。その列はいま読めた。Intel UHD 750 で 3440 × 1440
  を取り込み 1920 × 802 に縮小した測定では、一秒の窓十六個を通して `cap_us_p50` は 0.5-2 ms、
  `cap_us_p99` は 2-20 ms に収まり、`cap_repeat` は終始 0 だった——WGC が一フレームを手渡すのに
  かかる時間は、その後エンコーダがそれを圧縮するのにかける時間とほぼ同じ（`enc_us_p50` 1.5-2.6
  ms）であり、つまりこの便利さは安く、**Duplication バックエンドを書く理由は無い**。唯一の外れ値
  は `Start` 直後の最初の窓で、そこでは `cap_us_p99` が 242 ms を示す。それは最初のフレーム自体の
  年齢であって、定常状態の裾ではない。
- **受信側の合体は送信側の鏡であり、その代価は読み取り契約のフィールド一つだ**：P2 の残り半分は
  Linux の GRO と Windows の URO で、両方を塞いでいたのは同じもの——`RecvBatch` がスロット一つに
  つきデータグラム一つを約束していたことだ。`UDP_GRO`（Linux）や `UDP_RECV_MAX_COALESCED_SIZE`
  （Windows）を使うと、一度の読み取りが同じ大きさのデータグラムの連なりを一つのバッファで返し、
  セグメント長は制御メッセージに入る。そこで `InboundDatagram` に `segment` フィールドが加わり、
  `DatagramsIn` / `DatagramAt` がスロットを送られたときのデータグラムへ割り戻す。`segment == 0`
  はスロットにちょうど一つのデータグラムが入っていることを意味し、それは合体を求めないすべての
  呼び出し側なので、古い契約は特例ではなく既定のままだ。合体は `EnableReceiveCoalescing()` による
  **明示的な申し込み制**で、決して自動では入らない。スロットが小さすぎればデータを失うからだ。
  ここで実測したところ、16 × 1200 バイトの GSO 送信は 19 200 バイトの合体した skb として届き、
  それを 2048 バイトのバッファへ読むと 2048 バイトが返って `MSG_TRUNC` が立ち、**残りの 17 152
  バイトは捨てられる**——次の読み取りには何も残っていない。カーネルは 64 KB の IP ペイロード一杯
  まで合体させるので、スロットが `kMaxCoalescedBytes` を収められる呼び出し側だけが合体を有効に
  でき、`RecvBatch` は `MSG_TRUNC` の場合をその要件を名指しするエラーとして記録する——バースト一
  つが黙って消えるのに任せはしない。したがって `QuicEndpoint` はスロット数をスロット長と交換する
  ——スタック上の 16 × 1350 バイトが、エンドポイントの持つ 4 × 65 535 バイトになる——そして数の方
  は結局重要ではなかった。4 個、8 個、16 個はいずれも実行ごとの雑音の内側に収まり、占有の一番小
  さいものが勝った。マシンのドリフトを打ち消すために二つのバイナリを交互に走らせ、ループバック上
  で四組の中央値を取った：16 データグラムのバースト読み取りが 573 → 203 ns/データグラム（2.8
  倍）、`quic/stream-drain-scaling` が 2095 → 1629 ns/KB、`quic/stream-throughput-64k` が 2114 →
  1785 ns/KB。両方のバイナリでコードが同一の行でも 3.3-5.1% 動いており、それがこのマシンの雑音の
  床だ。だから `quic/handshake` の +4.9%（確保回数 13 → 15、うち一つは 256 KB の読み取りバッファ）
  は雑音と切り分けられず、`quic/datagram-delivery` の +0.6% は制御メッセージを読むことが合体しな
  い経路に何の代価も課さないと言っている。Windows 側は `WSARecvMsg` と `UDP_COALESCED_INFO` で
  同じ形に書いてあり、いまやコンパイルも実行も済んでいる。スタックは
  `UDP_RECV_MAX_COALESCED_SIZE` を受け付けるが、ループバックでは**何も合体させない**——16 × 1200
  バイトの USO ランは十六回の独立した読み取りとして返り、どれも `segment == 0` を運んでくる。だ
  から 2048 バイトの小さすぎるスロットでも何も失われない。切り詰めるべきランがそもそも無いから
  だ。上の 2.8x は Linux の結果のままである。Windows で測定できる利得はすべて送信側にある。USO は
  16 パケットのバーストを 7183 から 3942 ns/datagram へ下げる（−45%、十一回の中央値）。一方、受信
  側のバッチ化も URO も 45-60% という雑音の床の中に収まる——Linux マシンの 5% より一桁広く、そこ
  ではおよそ 1.5x を下回るものは何も測れないほど広い。URO が実際に発火するかどうかは本物の NIC が
  なければ分からない。ループバックでは答えが出ない。
- **bake-off に最初に要るのは二つ目のバックエンドではなく一本のクリップだ**: C1 にはエンコーダの
  列が三つあったが、どの列も他の列と比較できなかった。機械が違い、キャプチャ寸法が違い、デスク
  トップの中身が違い、どれ一つ固定クリップの上を走っていなかったからだ。さらに悪いことに、数字
  はすべて遅延で、速さと引き換えにエンコーダが何を差し出したのかは誰も測っていなかった。
  `scripts/encoder-bake-off.sh` はその両方を一つのコマンドで埋める。クリップを用意し（決定的な
  `testsrc2`、あるいは実写なら `--clip FILE`）、**同じ**生フレーム・同じ寸法・同じ fps・同じ
  ビットレートをすべてのバックエンドに渡し、VMAF、`enc_us_p50`、`enc_us_p99`、CPU%、GPU% を一つ
  の表に出す。表の脇にはクリップの SHA-256 が付き、二台の機械が同じピクセルを測ったと証明でき
  る。エンコーダが受け取るのはファイルではなく `ID3D11Texture2D` なので、クリップは
  `client/windows/cpp/bench/EncoderBench.cpp` が流し込む。四枚のテクスチャのリングで BGRA フレー
  ムを上げ、計るのは `Encode` の呼び出しだけだ。代わりに ffmpeg の `h264_qsv` と `h264_nvenc` を
  測ればスクリプト一行で済むが、それは別の問いへの答えになる。あれは Deskhub が出荷するコードで
  はない。二つの限界は表の隣に印字してあり、隠していない。`cpu_pct` と `gpu_pct` はプロセス全体
  の数字で、ハーネス自身のフレーム転送を含む。そして `testsrc2` はデスクトップの絵ではない——合
  成クリップは実行同士を比較可能にするだけで、現実を代表させはしない。起動しないバックエンドは
  別のバックエンドの名前で測られるのではなく表から外れる。`--encoder` が従っている規則と同じだ。
- **ループバック上の十秒の沈黙は、誰も返さない答えを待っていたリンクだった**: `platform_tests` は
  Windows でおよそ五回に一回、ちょうど八つのチェックを落とした。落ちる場所は `HostLinkTests` と
  `FileTransferTests` にまたがり、ログは QUIC リンクがループバック上で十秒以上黙っていたと言ってい
  た——スケジューリングの圧では説明がつかないので、広げるべきものは締切ではなかった。リンクは詰まっ
  てもいなければ遅くもない。**停められていた**のだ。`HostLink::SettleTrust` はホストが提示した鍵を
  `known_hosts` と突き合わせ、`TrustVerdict::Changed` なら `Deciding` に移って、人が受け入れるか拒
  むかを待つ。停まったリンクは何も送らないので、両端が互いを沈黙と報告する。テストは
  `onTrustAsked` を渡しておらず受け入れもしないので、自分の締切を待ち切るだけになる。事故の残りは
  そこから導ける。"a terminal record goes out" は通る。QUIC 接続は生きているからだ。エコーは戻って
  くるが、チャネルに届く前に `Deciding` の読み取りループに飲まれ、さらに二つのチェックが落ちる。
  `FileTransferTests` は自分のポートで同じ理由からさらに三つ落とす。`127.0.0.1:47845` と
  `127.0.0.1:47836` に、正しい形式で中身だけ違う指紋を一つずつ植えると、八つの失敗が名前どおりに、
  同じ沈黙を伴って、いつでも再現する。
  **鍵が食い違ったのは、Windows でこれらのテストが自分の状態を持っていなかったからだ。**
  `KeepTestLogsOutOfTheDeveloperHome()` は POSIX では `HOME` をどけるが、Windows では空の関数だっ
  た。だから両方のテストバイナリが `%USERPROFILE%\.deskhub` を直接読み書きしていた——インストール済
  みのアプリと、このマシンの他のすべての Deskhub プロセスが使う、たった一組の `host_cert.pem`、
  `known_hosts`、`paired_devices` を共有していたのだ。さらに、その共有された identity は各スイートの
  下書き用紙でもある。一回の実行で五十個ほどが作られ、そのたびに前の組をスナップショットして後で戻
  す。そしてそれをやっている四つのファイルのうち三つは、関数の末尾で戻していた——間に四つから六つの
  早期 `return` を挟んで。早期脱出が一度でも、kill が一度でも、生きているアプリからの書き込みが一度
  でもあれば、次の `HostLinkTests` は今回の鍵を前回の記録と突き合わせることになる。修正は四つから成
  り、どれも締切を広げるものではない。両方のテスト main は Windows でも `SetAppDataDir` を専用ディ
  レクトリに向ける。`SessionTransportTests` が既に持っていた RAII の `SavedIdentity` を
  `TestSupport.h` へ移し、手書きの復元をすべて置き換えた。固定のエンドポイントへダイヤルするテスト
  は `ForgottenHost` ガードを取り、判定が前の実行の残りに左右されないようにした。そして
  `SettleTrust` は停まるその瞬間に、見た鍵の名前とともにログを出す。次の沈黙が、死んだハンドシェイ
  クに見えるのではなく、ログの中で自分を説明するように。
- **三回の `printf` で組み立てた行は一行ではない**: 同じログに
  `[Deskhub] [Deskhub] quic: …silencequic: …silence` が出ていた——二つのスレッドが行の途中で噛み合っ
  たのだ。これは追跡中に実際に時間を食った。肝心のチェック名がその壊れた出力の中に埋まっていたから
  である。Windows の `LOGI` は `printf("[Deskhub] ")`、次に呼び出し側の書式、次に `printf("\n")` だ
  った。別のスレッドが割り込む機会が三回あり、CRT は一回の呼び出しの間しか `stdout` を守らない。今
  はタグと本文と改行を一つのバッファに組み立て、`fputs` 一回で出す。POSIX 側が最初から持っていた形
  だ。Android と Apple の分岐に手を入れないのもそのためである。`__android_log_print` も、あの
  `fprintf` も、もともとそれぞれ一回の呼び出しだ。
- **エンコーダはアダプタのベンダーから選び、表はどの行が実測かを自分で明かす**:
  `CreateEncoder` は以前どのマシンでも NVENC を試してから Media Foundation を試していたため、
  Intel や AMD のアダプタは失敗する `nvEncodeAPI64` の読み込みを一度払ってからフォールバックして
  いた。この順序は今や `client/windows` ではなく `core/media/EncoderBackend.h` の
  `EncoderBackendOrderFor` から来る。これは OS 呼び出しではなく表であり、GPU がなくてもテストが
  読める場所にあるべきだからだ。NVIDIA は `nvenc`、Intel は `mf` が先頭で、どちらもそのシリコン上
  で走らせた bake-off の数字による。**AMD の行は推測であり、推測だと明記してある。** このプロジェ
  クトは AMD マシンを一度も持ったことがないので、その行は `measured = false` を運び、ログは誰も
  測っていない数字を引く代わりに "no measurement on this vendor yet" と言う。AMD マシンが手に
  入ったら、直すのはこの行とこのフラグである。推測が外れても安く済むように規則が二つある。どの
  ベンダーもフォールバックを失ってはならない——順序を誤っても起動が遅くなるだけで、まったく
  エンコードできないソースには決してならない——そして推測の行も含め全ベンダーについてテストがその
  線を守る。`DESKHUB_GPU_VENDOR` はアダプタを固定して両方の分岐を一台で測れるようにする。効いた
  ときは必ずログに出し、そのアダプタがないマシンでは実行を拒むので、測定が別ベンダーの名前で
  記録されることはない。
