# Deskhub — アーキテクチャ

本書は Deskhub が**どう作られているか**を記述する。レイヤ、プロセスとスレッド、ワイヤ
プロトコル、そしてその背後にある設計判断である。製品がユーザーから見て何をするかは
[`SPECIFICATION.ja.md`](SPECIFICATION.ja.md) に、脅威モデルは
[`SECURITY.ja.md`](../SECURITY.ja.md) にある。

本書は [`ARCHITECTURE.md`](ARCHITECTURE.md) の翻訳である。相違がある場合は英語版が正典と
なる。

- **状態：** 現在のコードを記述している。
- **読者：** コードを変更するすべての人。

## 1. レイヤ

全体の配置をひとつの規則が支配している：ロジックは一度だけ書き、すべてのクライアントで
共有する。

```
core/       純粋な C++20。OS ヘッダなし、サードパーティコードなし、オフラインでユニットテスト
platform/   ヘッダごとに同一の API を 1 つ持つ薄い OS 抽象（core に依存）
client/     OS ごとのアプリ：windows、linux、macos、ios、android（platform + core に依存）
            さらに client/cli、デスクトップ 3 種共通のコマンドラインクライアント
```

| レイヤ | 内容 |
| --- | --- |
| `core/protocol` | ワイヤフォーマット（`Wire.h`）、ストリーム用のレコードフレーミング（`RecordStream.h`）、QUIC と Deskhub のビーコンデータグラムを見分けるパケット分類器 |
| `core/transport` | 映像の Packetizer/Reassembler、FEC、再送キャッシュ、送信ペーサ |
| `core/session` | セッション状態機械。役割で分割：`session/host`（ビューアごとのセッション、ビューア表、ビーコン、ファイル受信、認証スロットル）、`session/client`（画面クライアント、ファイル送信、ターミナルクライアント、接続フロー）、およびその隣に置かれた共有部品（転送の型、ターミナルセッション表、クリップボード同期、リンク回復） |
| `core/control` | ビットレート制御器、品質ラダー、ストリームのサイズ決定、クロックオフセット |
| `core/terminal` | すべてのクライアントが共有する VT エミュレータ：`VtParser`、`Screen`、`KeyEncoder`、`Palette` |
| `core/net` | 信頼ストア（クライアント側）、ペアリング済み端末（ホスト側）、バインドアドレス選択、LAN 走査のロジック |
| `core/ui` | ユーザーに見えるすべての文字列、設定のパース、表の行の構築 — 5 つのクライアントが同じことを言うために |
| `platform/net` | `UdpSocket`（OS ごと）、`QuicEndpoint`（pimpl の背後の quiche）、`SessionTransport` |
| `platform/auth` | `AuthNegotiation` — 双方が話す唯一のペアリング/パスコードのハンドシェイク |
| `platform/client` | `HostLink`（ダイヤル + 信頼 + 認証 + チャネル。すべての画面が共有）、`ScreenViewer`、`TerminalViewer`、`FileTransferClient`、`SourceQuery`、ホストプローブ、LAN スキャナ |
| `platform/host` | `HostEngine`、`HostNetLoop`、`SharingHost`、`TerminalHost`、`FileHost`、`ViewerBroadcast` |
| `platform/system` | クロック、乱数、PTY（ConPTY / forkpty）、ホストの身元（鍵）、信頼/ペアリング済み端末のファイル、自動起動、スリープ防止 |
| `core/cli` | コマンドラインの文法とその JSON ライタ — テキストを入れ、検証済みのコマンドを出す |
| `client/<os>` | キャプチャ、エンコード、デコード、描画、ウィンドウ、ダイアログ — プロトコルの形をしたものは何もない |
| `client/cli` | フラグからセッションへ：GUI ツールキットなしでホストになり、接続し、シェルを開く 1 つのバイナリ。デスクトップアプリと同じ OS ごとのメディアライブラリをリンクする |

`core/` はネットワークも GPU もなしにオフラインでテストできる状態を保たねばならない。
`platform/` は OS に触れてよいが、どこでも同一の API を出さねばならない。同じコードが 2 つの
クライアントに現れたら、それは下のレイヤに属している。

## 2. ひとつのポート、ひとつのトランスポート

ホストが差し出すすべては、ひとつの `SessionTransport`（内部に単一の `QuicEndpoint`）を
通って**ひとつの UDP ポート**（既定 47777）に乗る：

```
                      UDP ポート 47777
                            |
                 ClassifyPacket（先頭バイト）
                   /                    \
            QUIC パケット          Deskhub データグラム
                 |                        |
   +-------------+------------+       ビーコンのみ：
   |             |            |       LIST_SOURCES / PING に平文で
 streams     datagrams     (TLS)      応答。それ以外の生パケットは
   |             |                    すべて破棄
 control      video
 input        audio       ストリームはフレーム化されたレコードを運ぶ
 clipboard                （RecordStream）：長さ前置のメッセージ、最大 16 KiB。
 terminal                 データグラムは映像か音声のパケットを 1 つずつ
 files                    運ぶ（1200 B 以下）。
```

- **ストリーム**（信頼性あり・順序あり）：制御、入力、クリップボード、ターミナル、ファイル
  — 各接続は、クライアントが開く双方向ストリームを 1 本使う。ある接続で詰まったストリームが
  別の接続を止めることはない。受信したストリームデータはサービス 1 巡につき 64 KiB の
  予算で吸い出される：それを消費するもの（とりわけターミナルの VT エミュレーション）が
  スライスの合間にループを ACK、キープアライブ、タイムアウト処理へ返すので、`cat` の嵐が
  接続を自分自身のアイドルタイムアウトまで飢えさせることはもうない。
- **データグラム**（信頼性なし・順序なし、ただし暗号化はされる）：映像と音声のパケット。
  失われたものを QUIC が再送することはない。映像はアプリ自身の FEC/NACK 機構が損失を扱い、
  音声は何も扱わない — 9 章を参照。
- **生の UDP** は探索のためだけに存在する：ビーコンは QUIC を話さないスキャナに応答し、
  招いていないプローブには空のソース一覧を返す。探索の種類でない受信生パケットは、
  セッションのコードに届く前に捨てられる。

`QuicEndpoint` は quiche を完全に隠す（pimpl。`QuicEndpointNone.cpp` がスタブにするが、
それは `-DDESKHUB_QUIC=OFF` でビルドが明示的に降りたときだけ — quiche が無ければ configure が
失敗する。スタブのバイナリは共有も接続もできないからである）。接続はピアのアドレスで識別され、
コネクションマイグレーションはない。quiche の接続は契約上シングルスレッドなので、エンドポイントに
触れるたびにトランスポートの送信ミューテックスの下に入る — そしてトランスポートはブロックする
ソケット待ちをまたいでそのミューテックスを保持しない（まずロックせずに `WaitReadable`、
それから短くロックして `Poll`）。待ちをまたいで保持すれば、すべての送信側が飢える。

## 3. 入場：ペアリング

各マシンは初回起動時に ECDSA P-256 の鍵を作る（`HostIdentity`）。その SHA-256 SPKI ハッシュが
人の見るフィンガープリントである。TLS はその鍵に対する自己署名証明書を使う。TLS の上で、
アプリケーションレベルのハンドシェイク（`AuthNegotiation`）が接続ごとに入場を決める。
トランスポートがそれを走らせ、認証が決着していない接続からのメッセージはすべて捨てる：

| クライアントが差し出すもの | ホストがそのマシンを知っているか | 結果 |
| --- | --- | --- |
| 何も出さない | ペアリング済み | **署名**：クライアントが nonce + ホストのフィンガープリントのトランスクリプトに自分の鍵で署名する。黙って入場。 |
| 何も出さない | 未知 | **承認**：ホストの前の人に尋ねる（*このマシンを入れますか？*）。 |
| パスコード | ホストにもある | **パスコード**：ソルト付き検証子に対する SPAKE2 — コードは流れず、1 接続 1 回の試行で、双方が証明し、MAC はクライアントが実際に見たホスト鍵に束縛される（中継を殺す）。入力されたコードはペアリング済みかどうかに関わらず常に検査される。 |
| パスコード | ホストには無い | 照合する相手がない → ペアリング済みなら署名、そうでなければ承認。 |
| 何であれ | ペアリングがオフ | **拒否**（ペアリング済みのマシンは署名で入れる）。 |

成功するとクライアントはホストの `paired_devices` に書き込まれる。ペアリングはアドレスでは
なく鍵で行う。パスコードを 3 回間違えるとパスコードの経路が 30 秒ロックされる
（`AuthThrottle`。旧来のセッションロックアウトと定数を共有）。承認の経路にスロットルは
要らない — 門番が人間だからである。

クライアント側では `known_hosts`（`TrustStore`）がホストの鍵をピン留めする。鍵が**変わった**
場合は目立つ警告の後ろで接続を止め、未知の鍵はハンドシェイク自体で決着する（パスコードを
証明したホストはプロンプトなしで記憶される）。

ワイヤを流れるのは公開鍵そのものであって、裸のフィンガープリントではない — ホストは受け取った
ものをハッシュするので、他人の身元をまとうには、なりすます側が持っていない鍵で署名する必要が
ある。そして入場は接続ごとに一度決着するので、トランスポートより上は二度と尋ねない：自分を
証明したマシンは以後のどのメッセージにもパスコードを載せず、セッションのコードは接続全体を
認証済みとして扱う。

## 4. ホスト側

```
HostEngine（アプリに 1 つ、SessionTransport を所有）
 ├─ ネットループのスレッド：RunHostNetLoop
 │    recv → ビーコン応答 | 映像経路への取り込み | Chan::Terminal → TerminalHost
 │    ソースごとのセッション Tick、クリップボードのフラッシュ、再設定、統計
 ├─ キャプチャ/エンコード：ソースごとに、OS のキャプチャコールバックが駆動（client 層）
 │    フレーム → エンコーダ（ソースごとのミューテックス）→ Packetizer → FEC → SendTo（データグラム）
 ├─ 音声ワーカー：キャプチャコールバック → ロックフリーのフレームリング → Opus エンコード →
 │    ビューアごとのデータグラム（AudioBroadcaster）
 └─ TerminalHost（テナント。ターミナルが共有されているとき）
      ├─ ネットループのスレッド上の HandleMessage：TERM_OPEN/DATA/RESIZE/CLOSE → PTY
      └─ ポンプスレッド：PTY 出力 → ホスト側の Screen ミラー + TERM_DATA レコード、
           期限切れ、キック
```

- 何かが共有されている間はエンジンが動く。画面ソースがゼロでターミナルにチェックがあれば
  ソースなしで動き、ターミナルが生きている限りループも生きている。
- 各画面ソースは `SourcePipelineState` である：自分の `ScreenHostSession`（ビューア表、
  ネゴシエーション、入力の調停）、エンコーダ、品質ラダー、診断を持つ。1 回のエンコードが
  そのソースの全ビューアを賄う。
- フィードバックループ：ビューアは毎秒 `Feedback`（損失/RTT）を送り、ホストは自前の信号を
  1 つ足す — フレームが送信段に届いたときの古さで、`enc_lat_ms` が報告するのと同じ量である。
  `BitrateController`（AIMD）と `QualityLadder` がその 3 つからエンコーダのビットレート、
  解像度、fps を調整する。FEC は最初のフレームから armed で、長くきれいに走った後にだけ
  解除される。守るべき損失は最初のレポートより先に現れるからである — バックログでは arm
  しない。パリティは待ち行列をさらに深くするだけだからである。データグラム経路の下には
  quiche の CUBIC 輻輳制御があり、両者は直列に働く — quiche がマシンから出る量を縛り、
  アプリはその結果生じた損失にエンコーダを合わせる。
- 入力：「ホストが勝つ」— マシンの前の人が自分のマウスを動かしている間、`LocalInputMonitor`
  がリモート入力を一時停止する。操作するのは一度に 1 人。
- シェル：シェルごとに PTY 1 つ（Windows では `ConPTY`、それ以外は `forkpty`）、最大 8 個。
  接続が切れるとシェルは切り離され、同じマシンが再接続できるよう PTY は 2 分間生かされる。
  開始・終了・切り離し・再接続はすべて、アドレス・名前・鍵とともに監査ログに残る。
- 各シェルの出力は開始した瞬間から、ホスト側の `core/terminal` の Screen にも流れる。
  *Stop & attach* はリモートのクライアントを切断し、そのミラーを — スクロールバックごと —
  ホストのターミナルウィンドウに開く。こうして引き取られたシェルはホストのものになり、
  期限切れにならず、ホストのウィンドウが閉じたときに終わる。

## 5. クライアント側

どのクライアント画面も、同じ部品 `HostLink`（`platform/client/HostLink`）を通してホストへ
届く：QUIC 接続をダイヤルし、信頼ストアを調べ、認証ハンドシェイクを走らせ、リンクを生かし、
そして — それを求める画面のためには — リンクが切れたときにバックオフしながらダイヤルし直す。
もはや自分でダイヤルしたり認証したりするサービスはない。サービスはワイヤの `Chan` ごとに
チャネルを開き、自分の受信キューを得て、自分のスレッドでそれを吸い出す：

```
HostLink（開いている画面ごとに 1 つ）
 ├─ リンクスレッド：ダイヤル → 信頼確認 → 認証 → ポンプ
 │   （受信したレコードとデータグラムを Chan ごとのキューへ振り分ける。
 │    リンクパルス。回復が有効なところではバックオフして再ダイヤル）
 ├─ Chan::Control/Video/Audio ─> ScreenViewer
 │    ├─ ネットスレッド：HELLO/ネゴシエーション、映像の取り込み（Reassembler+FEC）、
 │    │   NACK、フィードバック、クリップボード
 │    └─ デコードスレッド：デコーダ + 描画キュー
 ├─ Chan::Terminal ─> TerminalViewer のサービススレッド
 │    ├─ core/terminal の Screen がグリッドを持つ
 │    └─ UI が Snapshot() をポーリングし、キーをコマンドキューへ投げる
 └─ Chan::File ─> FileTransferClient のサービススレッド（FileUpload のリング）
```

入場が済むと、リンクは自分の脈をとる（`core/session/LinkPulse`）：セッション id 0 の `Ping`
データグラムが毎秒出て、ホストのビーコンがセッション不要で同じ接続の上から応答し、返ってきた
タイムスタンプが平滑化された RTT になり、戻ってこなかった pong の id が損失率になる。
`ClassifyLinkQuality` がその 2 つを Good / Fair / Poor に畳み込み、デバイス一覧と、ホストに
応答した側のパネル — デスクトップでは専用のウィンドウ、Android と iOS では接続画面 — に
渡す。セッションのウィンドウはもうそれを持たない。`HostLink` は `onPulse` と `Pulse()` で
読みを差し出し、ping は ack を誘発するのでキープアライブも兼ねる。素のキープアライブ
タイマーが今も意味を持つのは、リンクが `Deciding` に停まっている間だけである。session-0 の
ping に答えられないほど古いホストでは読みが Unknown のままになる — 何も後退しない。回復中の
リンクではパルスが生存確認でもある：5 秒 pong が無ければ（ただし最初の pong でホストが答えると
証明された後にだけ）接続は既存の再ダイヤル経路へ落ちる。

画面ビューアも、ターミナルが以前からそうしていたように、その回復に自ら乗るようになった：
リンクが切れるか黙り込むか、セッションが 5 秒受信しないと、ウィンドウを終わらせるのではなく
`Reattaching` に停める（最後のフレームは残り、ステータス行が再接続中の文言に切り替わる）。
セッションのほうが先に気づいたときは `HostLink::RequestRedial` が再ダイヤルを強制し、リンクが
再び入場を許されるとビューアは同じクライアント id で `HELLO` をやり直し — ホストがビューアの
枠を結び直す — 新しいキーフレームからストリーミングが再開する。60 秒
（`kViewerReattachGraceUs`）戻れなければ、ウィンドウはいつもの理由とともに終わる。

ソース照会（`QuerySources`）は同じリンクの上を、1 回きりのブロッキング形式で走る。UI は今も
意図（キー、リサイズ、フィンガープリントの受理）をコマンドキューへ投げる。ホスト鍵が変われば
人が受理か拒否をするまでリンクは `Deciding` に停まる。ターミナルのウィンドウはエスケープ
シーケンスを一切解釈しない — `core/terminal` がバイト列をセルのグリッドに変え、ウィンドウは
セルを描いてキーイベントを転送するだけである。今日はまだ各ウィンドウが自分のリンクを持って
いる。同じホストに向いたすべてのウィンドウで 1 本の入場済みリンクを共有するのが次の一手で、
それは別のハンドシェイクとしてではなく `HostLink` に — レジストリと観察者へのファンアウトと
して — はまる。

## 6. 探索

ビーコンは `LIST_SOURCES` と `PING` に平文 UDP で答える。スキャナが 254 回の TLS ハンドシェイク
なしにサブネットを掃けるようにするためである。見知らぬ相手への返答は空の一覧で、本当のソース
一覧は入場済みの接続の上でしか明かされない。その返答は `SOURCE_LIST` のヘッダフラグで、ホストに
何ができるか — 入力を受け取るか、ターミナルを共有しているか — も運ぶので、クライアントは
ウィンドウを開く前に、スマートフォンは見ることしかできないと知る。フラグが存在する前のホストは
どれも立てない。最近の端末、その オンライン状態（ping/pong プローブ）、LAN 走査の結果は 1 つの
統合デバイス一覧になり、`core/ui/DeviceRows` が組み立て、5 つのクライアントすべてが表示する。

## 7. ディスクの上のデータ

すべてはユーザーの Deskhub フォルダ（`~/.deskhub`、`%USERPROFILE%\.deskhub`）にある：
`host_key.pem` + `host_cert.pem`（身元）、`known_hosts`（このマシンが信頼するホスト）、
`paired_devices`（このホストが入れるマシン）、`auth_salt`（秘密でない検証子のソルト）、
`ui-settings.txt`、`recent-devices.txt`（アドレスと難読化したパスコード）、Linux では
`portal-restore-token.txt`（画面共有ダイアログで選んだ画面に対するデスクトップ自身のトークン）、
そして実行ごとのログ。ファイル I/O は `platform/` に留まり、パースとデータ構造は `core/` に
あってユニットテストされている。

ビューアが送るファイルはまったく別の場所へ届く：ホストが選ぶフォルダ（`ui-settings.txt` の
`transfer_dir`。既定はユーザーのホームフォルダの `Deskhub`）である。`FileStore` は各ファイルを
`<name>.deskhub-part` として書き、CRC-32 が一致してファイル全体が届いてから改名するので、
書きかけのファイルが本来の名前で現れることはなく、`UniqueFileName` が何も上書きされないことを
保証する。ワイヤ上の名前は、`platform/` がファイルシステムに触れる前に `core/` の
`SafeFileName` が洗う — パス区切り、制御バイト、Windows が拒む文字、予約デバイス名はすべて
落ちる。

## 8. テスト

| スイート | 実行環境 | 対象 |
| --- | --- | --- |
| `make test` | オフライン、ソケットなし | `core/` のすべて：ワイヤ、フレーミング、FEC、セッション、VT エミュレータ、設定、文字列、決定論的な構造化ファジング |
| `make test-platform` | ループバックソケット | 実際の QUIC ハンドシェイク、SPAKE2 のエンドツーエンド、ターミナルのホストとビューア、実シェルに対する PTY、ロックアウト、承認 |
| `make test-integration` | ループバック、疑似キャプチャ/エンコード | ホスト↔クライアントの完全なセッション：ネゴシエーション、映像の伝送、入力、パスコード/承認のゲート、ゴミ耐性、そして交差負荷下の遅延 — 生きたストリームの隣でファイル転送、溢れるターミナル、キー入力を走らせ、それぞれ観測された最悪の停止で判定する |

CI はさらに clang-format と clang-tidy（どちらもピン留め）、SwiftLint `--strict`、
Android Lint、actionlint + shellcheck、3 スイートの ASan/TSan 実行、C++/Kotlin/Swift への
CodeQL、履歴全体への gitleaks、そして `core/` の行 90 % / 分岐 80 % 以上のカバレッジを
強制する。3 スイートはさらに arm64 Linux、Android エミュレータ、iOS シミュレータ向けに
クロスビルドされて走り、Windows のジョブは 1 巡ごとに統合スイートをさらに 3 回走らせて、
3 回に 1 回ほど現れる `DrainStreams` の間欠的なスタック破壊を追う。Linux と macOS の
リリースジョブは `core_perf` と `platform_perf` を、確保回数とスケーリングのゲート付きで
走らせる（共有ランナーに時間のベースラインは存在しない）。各プルリクエストにはさらに、
性能と遅延のレポートが自己更新する 1 つのコメントとして投稿される：両方の性能スイートを
同じランナー上でベースコミットと A/B した結果（ずれは警告であって失敗ではない）、
プルリクエストのビルドから得た負荷下の統合数値、そして core のカバレッジ行である。

## 9. 覚えておく価値のある判断

- **false を返す機能問い合わせひとつで、制御ループ全体が切れることがある**：Media Foundation
  のエンコーダは、MFT が `CODECAPI_AVEncCommonMeanBitRate` を出さないときに `SetBitrate` へ
  `false` を返し、`ApplyFeedback` は拒否を「何もコミットされなかった」として正しく扱う。
  `MeanBitRate: NOT SUPPORTED` と報告する Intel Quick Sync の MFT では、その結果ビットレートを
  まったく変えないホストになった：このハードウェアでの実測で、29-40 % の損失が 30 秒続いても
  `Bitrate` の判断はゼロ件、したがって品質ラダーも 1 段も動かなかった。起動時のログはずっと
  `NOT SUPPORTED` と言っていたのに、誰もそれを「適応は死んでいる」とは読まなかった。同じ
  ファイルの `SetFps` と `RequestKeyFrame` は既に `ReinitTransform()` にフォールバックして
  いた。諦めていたのは `SetBitrate` だけで、今は同じようにフォールバックする —
  `ConfigureTransform` が `cfg` から `MF_MT_AVG_BITRATE` を書くので、再構築すれば新しいレートが
  効く。再構築は IDR のコストを伴うので、生きた `codecapi` の経路をまず試すのは変わらない。
  デバイスごとの機能が制御入力を左右するなら、フォールバックは必須にすること。「遅くなる」への
  劣化は選択だが、黙って「決してしない」に劣化するのは選択ではない。

- **追いつけない送信側は、きれいなリンクとまったく同じ顔をしている**：`BitrateController` が
  持っていた入力 — 損失、RTT、受信レート — はすべてビューア由来なので、ループの中の何も
  「遅れているのは自分だ」と言えなかった。2 人のビューアにホストしている Pixel 4 での実測：
  フレームはエンコーダを 15 秒古い状態で出ていったのに、ビューアは損失 0 %、RTT 15 ms と報告し、
  制御器はそれを余裕と読んでビットレートを上限の 20 Mbps まで戻していった — 送信側の内部で
  起きるバッファブロートであり、リンクがきれいに見えるほど強く送り込む。ホストは今、送信の
  段でフレームの古さを測り、ビューアの数字と並べて入力する：`kBacklogMs` を超えれば損失 2 %
  相当で退き、`kSevereBacklogMs` を超えれば 5 % 相当で退き、どちらでも通常どおり 2 秒は
  ランプアップを止める。制御変数は今もビットレートだけなので、`QualityLadder` はその後ろで
  一段下がり、fps 上限も追随する。遠端だけに養われた制御ループは、自分が本当に所有している
  半分に対して盲目である。

- **fps の上限は、どこかがフレームを捨てる場所でしか効かない**：ラダーの fps の段は要求で
  あって、各プラットフォームがフレームを捨てられる場所でそれを果たさねばならない。Windows と
  Linux はキャプチャで `FrameGate` を挟み、Android は `max-fps-to-encoder` で MediaCodec の
  入力を抑え、macOS は ScreenCaptureKit のフレーム間隔を再設定する。iOS には場所がなかった：
  ReplayKit は画面のレートで届け、`VtEncoder::SetFps` は
  `kVTCompressionPropertyKey_ExpectedFrameRate` を設定するだけで、それは何も捨てないレート
  制御のヒントである。そこで段を変えてもエンコーダを調整し直すだけで、飲み込まねばならない
  フレーム数は何も変わらなかった。`OfferVtFrame` は今、両方の Apple アプリで同じ `FrameGate`
  を走らせる。静止画面でも再送するフレームがあるよう、アイドル用のフラッシュキャッシュを
  更新した後にである。すべてのプラットフォームにつまみがあるときは、ラダーを信じる前に、
  各プラットフォームがそれで何をするのかを確かめること。

- **送信ペーサはエンコーダ自身の出力レートより十分上に保つこと**：`Pacer::Gate` は
  `SendEncodedFrame` が走るスレッドで眠り、Android ではそれが MediaCodec の吸い出しループで
  ある — エンコーダが次のフレームを渡せるようになる前に `releaseOutputBuffer` を呼ばねば
  ならない、まさにそのループである。したがってペーシングはワイヤのレートだけでなく吸い出しの
  レートを決めてしまい、その間 VirtualDisplay は画面のレートで新しいフレームを押し込み続ける。
  送信のバーストを均そうと `kPacingRateMultiple` を 2 から 1.2 に狭めた結果を Pixel 4 で実測：
  フレームあたりのバーストは 20 ms から中央値 63 ms になり、エンコーダのバックログは際限なく
  伸びた — `enc_lat_ms` は 100 秒で 46 秒を超え、ビューアは 4.6 秒遅れた。2 のままなら同じ
  実行で `enc_lat_ms` は 0 だった。この余裕は回収できるたるみではない。エンコードのパイプラインが
  埋まるより速く吸い出されるようにしているのがそれである。送信のバーストにはソケットバッファか、
  ペーシングを吸い出しスレッドから外すことで対処し、決してこの数字を締めて対処しないこと。

- **性能スイートはコストで判定するので、結果を見る第 2 のゲートが要る**：`core_perf` は
  パケットあたりの確保回数と、時間が入力に対してどう伸びるかを測る。そして実リンクで
  1 個の損失パケットが無傷のフレームの 22 % を捨てさせていた間も、その再組み立て系ワークロードは
  すべて合格していた。捕まえられるはずがない：良い映像を捨てるほうがデコードするより*安い*ので、
  壊れた方針のほうがスイートの見るすべての数字で良い点を取る。`LossGoodputTests` はその相棒で、
  コードが本来すべきより少ない仕事しかしないときに落ちる — 実際の往復を伴う末尾損失リンクを
  模擬し、パケットが全部届いたフレームのうち実際にデコーダへ届いた割合と、届いたフレームどうしの
  最長の間隔で判定する。どちらもマシン非依存なので、ノート PC でも CI ランナーでもスマート
  フォンでも成り立つ。方針が仕事を捨てることで「成功」できるときは、常にグッドプットのゲートを
  持ち出すこと。

- **失われたパケットの代償は 1 フレームであって、次のキーフレームまでの画面全部ではない**：
  再組み立て器は損失のたびに `waitingForIdr_` を立てていたので、1 個の欠けたパケットが、新しい
  IDR が来るまで後続の*完全な*フレームをすべて捨てていた。Wi-Fi 越しにホストするスマートフォンでの
  実測では、それが本当に不完全な 64 フレームを 381 の破棄フレームに変えていた — デコードできる
  映像 6.4 MB がゴミ箱に入り、画面は中央値 146 ms、最大 1.4 秒ずつ凍った。今は不完全なフレーム
  だけを落とし、その後ろのフレームはそのままデコーダへ行く。デコーダは欠けた参照を隠蔽し、
  `InvalidateRef` が悪いフレームをホストに名指しして、キーフレーム要求が修復する。短い
  マクロブロックのノイズは、凍らせないために意図して払う代償である。`waitingForIdr_` は、それが
  唯一正しかった場合のために残っている：途中参加のビューアには参照がまったくないので、最初の
  IDR を待たねばならない。

- **停止判定の窓は再送より長くなければ、NACK は飾りである**：かつてフレームは失われたと宣言される
  までに 2 フレーム間隔（60 fps なら 33 ms）しか与えられていなかったが、同じリンクで実測した
  RTT は 24-49 ms だった。NACK は出ていき、その答えはフレームが既に捨てられた後に届いた —
  `late_ms_avg=24` と、もう存在しないフレーム宛に毎秒 87 パケットが着地する形で見えていた。
  `StallTimeoutUs` は今、ペースの窓と 1.5 往復の大きいほうを取り（ハードタイムアウトの上限は
  そのまま）、再送を頼む価値のあるリンクでちょうど頼むようになった。

- **性能スイートは確保回数と形で判定し、ミリ秒では判定しない**：3 つのテストスイートはデバッグで
  ビルドされ、CI は ASan、TSan、カバレッジの下でもう一度走らせる。そこでの実時間の予算は
  コードではなくサニタイザを測ってしまう。だから `core_perf`（リリースプリセット、
  `make test-perf`）はマシン非依存な 2 つで落ちる — グローバルな `operator new` を差し替えて
  数える、パケット/フレーム/KB あたりの確保回数と、入力よりはるかに速く時間が伸びる `-scaling`
  の行である — そして計測の半分は `out/perf/baseline.txt` との比較として残す。このファイルは
  `make perf-baseline` がマシンごとに記録し、コミットしない。この分割こそが、「再組み立て器が
  今はすべての断片を 2 回コピーする」ような後退を、ノート PC でも CI ランナーでもスマート
  フォンでも同じように落とせるようにし、なお数字そのものが要点である経路については単位あたりの
  ns と MB/s を印字させる。CI はこの 2 つのマシン非依存なゲートを Linux と macOS のリリース
  ジョブで走らせる。Windows はバイナリをビルドするだけである。MSVC の deque は 16 バイトを
  超える要素に対して 1 要素ごとにブロックを確保するので、同じコードでも確保回数が変わるからで
  ある。プルリクエストには共有ランナーのノイズでは覆せない計測比較も付く — ベースコミットと
  プルリクエストを同じランナーで測り、許容 50 %、警告のみ。`platform_perf` は同じゲートを
  ループバック上の実 QUIC に広げる。そこでは実時間がサービスループの刻み — 64 KiB のストリーム
  吸い出し予算 × 1 ms のポーリング — を測るので、予算の縮小、線形に伸びなくなった吸い出し、
  ポーリングループでの新たな確保は、同じ仕事の CPU コストがほとんど動かなくても跳ねとして
  現れる。

- **`FileHost` は自分のロックを持ったまま送らない**：QUIC のサービスループは
  `SessionTransport::sendMutex_` の下で `QuicEndpoint::Poll` を走らせ、そこで閉じた接続は
  そのまま `FileHost::OnPeerGone` を呼び返し、それが `FileHost::mutex_` を取る。つまり
  `sendMutex_ -> mutex_` の順序はトランスポートが決めている。`mutex_` を先に取ってから送る
  経路 — `FileReceiver` が `hooks.send` 経由で accept、ack、cancel を出す — はこの環を
  閉じてしまい、TSan が受信ループと、生きた転送に対して `SetAccepting(false)` を切り替える
  UI スレッドとの間のロック順序逆転として捕まえた。したがって受信側が出すレコードは `mutex_`
  の下で `outbox_` に積み、解放した後にだけ送る。両方の半分にまたがって `outboxMutex_` を
  保持するので、ピアには生成された順序どおりに見える。`OnPeerGone` はそもそも送れない：
  既に `sendMutex_` の下で走っているので、積んだものは捨てる。

- **コマンドラインクライアントは 4 つ目のフロントエンドであって、2 つ目の実装ではない**：
  `core/cli` でフラグを解析し、あとはデスクトップアプリが駆動するのとまったく同じ部品を
  駆動する — ホストになるなら `SharingHost`、見るなら `ScreenViewer`、シェルを開くなら
  `TerminalViewer`。自前で持っているのはウィンドウだけである：Linux では X11 + EGL、
  Windows ではデスクトップアプリ自身の `RunViewer`。各クライアントの `cpp/` ツリーが静的
  ライブラリ（`deskhub_linux_core`、`deskhub_win_core`、`deskhub_win_view`、
  `deskhub_mac_core`）で、GUI のコードがその上に載っているのはそのためである — この分割は、
  CLI が GTK も wxWidgets もリンクせずにメディアパイプラインをリンクできるようにするために
  ある。

- **`preflight` はキャプチャすべき画面があるときにだけ走る**：どのクライアントもこれで
  キャプチャ経路を確かめる — Linux では xdg portal、macOS では画面収録の許可、Windows では
  D3D11 デバイス。シェルだけを運ぶ共有にはどれも要らないので、それでも尋ねると、ヘッドレスな
  マシンでの `share --terminal` が「画面キャプチャの権限が無い」になってしまった。
  `HostEngine::Start` はソース一覧が空なら今はそれを飛ばす。

- **シェルがあって画面のないホストは生き続ける**：ネットループは生きているソースが無くなると
  セッションを終える。そしてターミナルだけの共有には定義上ソースが無い。`keepAlive` は今、
  ループが走り出した後にしか付かない `TerminalHost` ポインタではなく、呼び出し側の意図
  （`ShareOptions::terminal`）から答える。

- **フレームゲートは締切に向けて数え、最後に通したフレームからは数えない**：30 fps の目標に
  対して 40 fps を渡してくるコンポジタは、33 ms の境界のほとんどでフレームを持っていない。
  だから「通したものから十分離れているか」だけを問うゲートは 1 枚おきに落として 20 fps で
  落ち着く — 目標より遅く、しかもばらつく。それは遅いストリームではなくジャダーである。
  `FrameGate` は代わりに走行中の期限を持つ：通過は期限をちょうど 1 間隔進めるので余りが残り、
  40 入れれば 30 出る。目標より遅いキャプチャが間引かれることはなく、実時間より遅れた期限は
  バーストを貯め込むのではなく再同期するので、静かな時間が後のバーストを買うことはない。

- **Linux のホストは自前のスレッドでエンコードし、そのスレッドに渡すのは大きいフレームでは
  なく小さいほうである**：PipeWire の `process` コールバックの中でエンコードすると、
  キャプチャが `1000 / enc_ms` fps に絞られ、エンコード時間の揺らぎがそのままクライアント側の
  フレーム間隔のジッタになった。エンコードは今や自前のスレッドで走り、`FrameMailbox` — 最新
  勝ちの 1 枠キュー — 経由で供給される。エンコーダが遅れれば新しいフレームが勝ち、古いほうは
  積まれるのではなく数えられる。キューを渡るのは既にエンコードサイズへ縮小されたフレームで、
  おおよそ 7 分の 1 のバイト数である。代わりにフルサイズのフレームを渡すと、コピーそのものより
  はるかに高くついた：キャプチャ側のコアに 20 MB のキャッシュラインがダーティなまま残り、
  エンコード側のコアがそれを引き寄せねばならず、実測で 16 ms。自分の所有するメモリを同じだけ
  読む場合は 3.4 ms だった。キャプチャスレッドはどのみち全ソースピクセルに一度触れねばならない
  ので、その 1 巡を払う場所としてそこが正しい。dma-buf のフレームは今もインラインでエンコード
  する：コールバックが返った瞬間にコンポジタが裏のメモリを再利用するので、それより長生きできず、
  どのみち VA-API が GPU 上でスケールするからである。
- **Linux のホストはインストール状況ではなく、フレームがどこにあるかでエンコーダを選ぶ**：
  dma-buf のフレームは VA-API へ行く。それを生んだ GPU 上でゼロコピー取り込みできるからである。
  マップ済み（CPU）のフレームは NVIDIA ドライバがあれば NVENC へ行く。NVIDIA GPU が描く
  デスクトップでは、コンポジタが screencast を共有メモリに再ネゴシエートするので、エンコードは
  システムメモリから直接ピクセルを取れるカードのものになるからである。`HwEncoder` は
  エンコーダ再構築ごとにその判断をし、後から別種のフレームが来たら `false` を返す。それが
  再構築の合図である。
- **NVENC の手前の縮小は自前であって、swscale のものではない**：NVENC はパックされた 32 ビット
  ピクセルを取るがリサイズはしない。そしてキャプチャはフル解像度のデスクトップである。
  `libswscale` は 3440x1440 → 1280x534 で 9.2 ms を計測した — およそ 2 GB/s で、このマシンの
  メモリ帯域より一桁遅い。パック RGB のリスケールは最適化された経路から外れるからである。
  `core/` の `RgbDownscale` はまさにこの形のために書かれた面積平均である：ソースピクセルごとに
  32 ビット 1 回のロード、整数の累算、同じフレームで 4.0 ms、しかも swscale が返していた
  バイリニアのタップではなく正しいアンチエイリアスになる。フレーム全体の NVENC のコストは
  約 5 ms に収まるので、60 fps には余裕がある。
- **性能の数字はリリースビルドからでなければ意味がない**：`make build-linux` と
  `make run-linux` は `x64-debug` プリセット、つまり `-O0` を構成する。そしてエンコード経路は
  今や `core/` のピクセル演算である。同じフレームがそこでは約 19 ms、`make release-linux` から
  なら約 5 ms である。デバッグバイナリに対して測ったジャダー報告は、ビルド種別を測っている。

- **Apple のビューアは制御タイムベース上で PTS により映像のペースを取り、ペーサは自分を
  信用しない**：届いた瞬間に毎フレーム表示すると、Wi-Fi の到着ジッタがジャダーとして見えるのに、
  遅延の数字はどれも優秀なままだった — 間隔は遅延ではない。`VideoPacer`（core、オフラインで
  テスト）はホストの PTS をローカルの表示時刻へ、e2e の指標と同じやり方で写す — `arrival − pts`
  の窓最小値 — に、到着ジッタを支払う約 33 ms のリードを足す。`VtDecoder` はそこから
  `AVSampleBufferDisplayLayer` の制御タイムベースを駆動し、250 ms を超える乖離でのみ再同期する。
  2 秒を超える pts の飛びはジッタではなく新しいストリームとして読むので、写像は窓ぶん凍る
  代わりに引き直される。外部タイムベースを描画側が守るかどうかを、あらゆる OS バージョンで
  ここから証明はできないので、デコーダは自分の背中を見張る：ペース調整したフレームが満杯の
  描画キューに飲み込まれ続けたら、即時表示に戻してフラッシュする。画面ではなく平滑化のほうを
  手放すのである。

- **音声は 1 データグラムに 1 フレーム、失われたものは決して追わない**：64 kbps の 20 ms Opus
  フレームは実測で約 160 バイト、最大でも 209 バイトで、データグラムに空いている 1180 バイトに
  対して十分小さい — だから音声経路にはパケタイザも FEC も再組み立ても NACK もない。それは
  映像経路のほとんどである。損失は最も安く済む場所で吸収する：Opus は次のフレームに帯域内 FEC を
  持ち、受信側はジッタバッファが報告した穴をデコーダに隠蔽させる。再送は無駄より悪い。200 ms
  遅れて届いたフレームは再生できないのに、後ろの 10 フレームを遅らせるからである。
  `make opus-smoke` はこのライブラリをビルドできるどのマシンでもその数字を測る。
- **ジッタバッファにタイマーは入っていない**：`AudioJitterBuffer` は純粋な状態であり、目標
  遅延は再生を始める前に何フレーム貯めるかにすぎない — 60 ms なら 3 つである。おかげで全体が
  眠りなしにオフラインでテストでき、失敗の仕方も明示的になる：バーストは積まれずに上限で
  切られ、空のバッファは途切れるのではなく貯め直し、シーケンスの飛びは数千の損失ではなく
  新しいストリームとして読まれる。ペーシングは `AudioPlayer` にあり、実時間 20 ms ごとに
  1 フレームを PCM リングへ送り出し、それをシンクの描画コールバックが吸い出す。
- **キャプチャコールバックはエンコードしない**：PipeWire と ScreenCaptureKit は数ミリ秒の
  締切を持つリアルタイムスレッドで音声を届け、そこで締切を落とすと Deskhub だけでなくホスト
  自身の再生が xrun する。Opus のエンコードは 0.3–1.5 ms でスパイクもあり、以前はビューア
  ごとの `sendto` がその後ろに同じスレッドで乗っていた。`AudioBroadcaster::Offer` は今、
  20 ms のフレームを事前確保したロックフリーの枠リングへコピーし、キャプチャ時刻を刻むだけで
  ある。エンコード、診断、ビューアごとの送信はワーカースレッドが行う。ワーカーが遅れた代償は
  数えられるドロップ（`framesRefused`）であって、ホストの音声のグリッチでは決してない。
- **音は両端が首を縦に振って初めて出る。古いクライアントには決して聞こえない**：ビューアが
  `Hello.features` のビット 0 を立て、ホストが機能に `kHostSharesAudio` を広告し、ホストは
  そのビットが立っているビューアにだけパケットを送る。`kProtocolVersion` が 2 のままなのは
  そのためである：5.0.x のビューアは `features = 0` を送るので、5.1 のホストは相手が解析
  できないメッセージをワイヤに載せない。

- **ターミナルのリンクは自分で生き延び、自分でダイヤルし直す**：ターミナルのビューアは映像
  セッションとは別の自分の QUIC 接続を持つので、映像経路のキープアライブはひとつも届かない。
  プロンプトで放っておかれると通信がまったく無く、30 秒の QUIC アイドルタイムアウトで死に、
  ビューアはそのままスレッドを `Reattaching` で止めて再ダイヤルもしなかった — シェルはホスト側で
  丸 2 分待っていたのに、誰も取りに戻らなかった。`TerminalViewer` は今、タイマーで ack を
  誘発するパケットを送り、バックオフしながら再ダイヤルし、`TerminalClient::Reattach()`
  （core に書かれてテストもされていたのに、ただ一度も呼ばれていなかった）を再利用して、同じ
  シェルをスクロールバックごと呼び戻す。`deskhub::KeepaliveIntervalUs` / `ReconnectDelayUs`
  が core にタイミングを持つ：キープアライブはアイドルタイムアウトの半分以下でパケットを 1 つ
  落としても耐えられ、再試行は `kTerminalReattachGraceUs` でぴたりと止まる。それを過ぎれば
  ホストは既にシェルを捨てており、つなぎ直すと黙って新しいシェルが開いてしまうからである。
- **レコードはまるごとストリームに載るか、まったく載らないか。そして遅れたクライアントには
  全バイトを流すのではなく描き直す**：信頼性のあるもの — 制御、認証、ターミナル出力 — は
  すべて 1 本の QUIC ストリームを共有する長さ前置のレコードなので、ワイヤに半分のレコードが
  出た時点で相手側のフレーミングは永久にずれる。`RecordStream` に再同期する手段はなく、ピアは
  接続を閉じる。`QuicEndpoint::SendStream` は以前、入るだけ書いて残りを捨てていた。それは
  `make test` のようなコマンドがリンクを追い越すまで保っていた：1 MiB のストリームウィンドウが
  埋まり、`TermData` レコードの末尾が落ち、ビューアのフレーマが失敗し、シェルは開いて 1 分後に
  「切断」した。今はストリームに余地のないレコードを拒み、それでも部分書き込みが起きたら接続を
  閉じる。裂けたストリームはその場では直せないからである。その上で `TerminalHost` は未送出の
  出力をシェルごとのキューに保持し、ティックのたびに再試行するので、一瞬リンクを追い越しただけの
  バースト — たとえばビルドの出力 — は今もバイト単位でクライアントに届く。`kMaxPendingBytes` を
  超えるとキューは伸ばされるのではなく捨てられる：どのバイトも既にホスト側のミラー `Screen` に
  届いているので、クライアントは `deskhub::term::RenderScreen` で追いつく — 現在のグリッドを
  1 回描き直すだけで、頻度は最大でも `kRepaintIntervalUs` ごとである。誰も読めなかった出力は
  バッファされずに飛ばされるので、溢れさせるコマンドは自分の速度で走り切り、それでも正しい
  画面が残る。再接続したクライアントも同じ描き直しを受け取る。ギャップの後ではバイト列上の
  位置に意味がないからである。
- **自動共有はデスクトップを待つのであって、一度列挙して終わりではない**：Windows は自動起動を
  `ONLOGON` のスケジュールタスクとして登録し、それはセッションに列挙できるモニタが揃う前に
  発火する。だから構築時の 1 回の `ListDisplays()` は空で返り、アプリは共有できるものが無いと
  報告していた。`deskhub::ui::AutoShareGate`（core、ユニットテスト済み）が再試行の規則
  — `kAutoShareProbeMs` ごとに調べ、`kAutoShareGiveUpMs` で諦める — を所有し、各クライアントは
  自分のタイマーからそれを駆動するので、方針はひとつしか存在しない。`NextAutoShareStep` は
  同じ規則の状態なし版で、Swift クライアントは `dh_auto_share_step` からそれに届く。自動共有は
  モーダルを決して開かない：ログイン時のウィンドウはトレイに隠れていることがあり、そこでは
  ダイアログは見えず共有を永久に止めてしまうので、拒否は Host のバナーとログへ行く。デスクトップの
  クライアントは OS のディスプレイ変更シグナルでピッカーを更新もする。後からモニタを挿したときに
  一覧が正しいままなのはそのおかげである。
- **msquic/ngtcp2 ではなく quiche**：Android と iOS の両方で本番の実績がある唯一の QUIC
  ライブラリである。BoringSSL が付いてきて、それが SPAKE2 とホストの身元にも使える — 2 つ目の
  暗号ライブラリが要らない。
- **コネクションマイグレーションはしない**：候補のどのライブラリにも使えるクライアント側の
  対応がない。再接続して再アタッチする方式（tmux 流。モバイルのバックグラウンド化のためどのみち
  必要）がそれを賄う。
- **Ed25519 ではなく ECDSA P-256**：BoringSSL のサーバ側は quiche 経由で Ed25519 の TLS
  ハンドシェイクに署名しない。戻さないこと。保存された Ed25519 の身元は読み込み時に差し替えられる
  — さもないと画面に何の説明も出ないまま、毎回 `QUICHE_ERR_TLS_FAIL` でハンドシェイクに失敗する。
- **パスコードの検証子は高価な KDF ではなく SHA-256 1 回**：SPAKE2 が既に攻撃者を 1 接続 1 回の
  オンライン推測に制限し、オフラインで解く価値のあるトランスクリプトを残さない。それこそ KDF の
  硬さが存在する目的そのものである。
- **quiche は FetchContent ではなく事前ビルド**：`scripts/build-quiche.sh` が
  `third_party/quiche/` の下に rust ターゲットごとのディレクトリと共有の `include/` を書く —
  quiche.h と、boring-sys が同梱する BoringSSL のヘッダをコピーして置く。Deskhub がホストの身元の
  ために BoringSSL を直接呼び、include パスをひとつにして 2 つ目の TLS ライブラリを持ちたくない
  からである。`DeskhubQuiche.cmake` がそれを `deskhub::quiche` にする。ライブラリが無ければ
  configure が失敗する。
- **Apple は `libplatform_bundled.a` をリンクする**：Xcode のアプリは platform のアーカイブを
  CMake の外から取り込むので、quiche への PRIVATE リンクはリンク行に届かない — そこで `libtool` の
  ステップが platform と quiche を、`.pbxproj` がリンクするひとつのアーカイブへ融合する。
- **Windows のツールチェーンの罠は既に片付いている — 片付いたままにすること**：quiche は Rust の
  オブジェクトを `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS` で静的 CRT に対してビルドし、
  BoringSSL のオブジェクトは `CFLAGS_x86_64_pc_windows_msvc` の `/MT` で扱う（msvc の既定は DLL
  ランタイムで、包括的な `RUSTFLAGS` でこのフラグを押し込むと cargo のビルドがまるごと壊れた）。
  ツリー全体が `MultiThreaded` を固定して合わせ、exe が VC++ 再頒布可能パッケージ無しで出せる
  ようにしている。wxWidgets は configure のたびに `wxBUILD_USE_STATIC_RUNTIME` を固定し直す。
  `wx_option()` がそれを永久にキャッシュするからである。BoringSSL は既定の Visual Studio
  ジェネレータでビルドしなければならない — cmake クレートはそこでしか /MT を構成ごとのフラグで
  伝えられないので、`CMAKE_GENERATOR=Ninja` を強制すると BoringSSL は黙って /MD に戻り、最終
  リンクが LNK2038 で死ぬ。MSBuild が長いパスで MSB6003 を出すなら、Windows の長パスを有効に
  すること。Git Bash の `/usr/bin/link.exe` は MSVC のリンカを覆い隠す（`cl.exe` のディレクトリを
  先に置く）。そのパス書き換えは `/` 形式の引数を壊す（`MSYS2_ARG_CONV_EXCL`）。NASM の
  インストーラは PATH に触れない。
- **Windows ホストでの Android 版 quiche は cargo-ndk を使わない**：cargo-ndk は boring-sys に
  拡張子のない `clang` のパスを渡し、CMake は Windows でそれを拒む。だから `build-quiche.sh` は
  `CC_*`/`CXX_*`/`AR_*`、cargo のリンカ、ABI 向けの `--target=` を自分で設定し、素の cargo を
  呼ぶ。BoringSSL はそこでも Ninja を要求し（Visual Studio ジェネレータは NDK を対象にできない）、
  bindgen は Visual Studio の libclang を拾って、自分のバイナリの隣に `stddef.h` を探す —
  `BINDGEN_EXTRA_CLANG_ARGS` がスラッシュ区切りで NDK のリソースヘッダを指す。bindgen はその
  変数をシェルの規則で分割し、バックスラッシュを食べてしまうからである。
- **クロスコンパイルするアプリはどれも先に自分の quiche をビルドする**：`build-android`、
  `build-ios`、`build-macos`、`build-linux` は、`debug`/`release` がホスト向けにそうするのと
  同じように、自分の ABI の quiche ターゲットに依存する。quiche は ABI ごとであり、それが
  無ければ CMake の configure が失敗するので、この手順を飛ばしたビルドは「ライブラリが無い」
  ではなく「ツールチェーンが壊れている」ように見える — そして最後に成功したビルドのまま
  取り残されたアプリは、ピアがもう答えないプロトコルを話す。
- **iOS の quiche は `IPHONEOS_DEPLOYMENT_TARGET=17.0` を固定する**：boring-sys の clang は
  SDK の既定に流れ、rustc は自分の最小バージョンでリンクする。その食い違いはリンク時に未定義の
  `___chkstk_darwin` として現れる。
- **クロックは 2 つ、意図的に**：`NowUs()` は単調（起動からの秒）で間隔用、`NowUnixSeconds()`
  だけが日付として表示できる。混ぜても大きな音は出ない — 保存した単調のスタンプは 1970 年
  1 月 1 日のどこかの時刻として現れる。
- **Windows の PTY の子プロセスに標準ハンドルを渡さない**：ホスト自身の stdout がリダイレクト
  されていると、Windows はそのリダイレクトを疑似コンソールの属性を越えて引き継がせ、シェルは
  パイプに向かって話す。ハンドルをまったく渡さないことが、シェルをアタッチ済みの ConPTY へ
  戻す。
- **Windows のターミナルグリッドには `wxWANTS_CHARS`**：これが無いと、フレームのダイアログ
  ナビゲーションが Enter、Tab、矢印キーをターミナルより先に食べてしまう。
- **macOS の TCC は許可をコード署名と結びつける**：ローカルでビルドした app.app（アドホック署名、
  ビルドのたびに署名し直す）と Developer ID の dmg が同じ `com.deskhub.macos` の行を取り合う —
  システム設定は許可済みと表示しているのに、いま起動したコピーは拒否される。アクセシビリティに
  ついては黙ってそうなる。`make reset-macos-permissions` がすべての許可を消し、次の起動で
  改めて尋ねさせる。
- **macOS は CI ではデスクトップビルド、リリースでは署名ビルド。同時に両方にはならない**：
  `build-desktop` は push のたびにアドホック署名でアプリをコンパイルするので、ビルドできなく
  なった Cocoa の変更はそのプルリクエストで落ちる。`deploy` は `release-macos`、つまり fastlane の
  経路 — Developer ID、公証、dmg — で同じアプリに到達し、ユーザーが実際に開けるものを作る。
  だから再利用可能なワークフローは `for_release` が立っているとき macOS のジョブを飛ばす。
  さもないとタグひとつのために、誰も出荷しないバンドルを作るだけの macOS ランナーをもう 1 台
  払うことになる。`build-mobile` が iOS と Android だけを担うのも同じ理由、同じ分け方である。
- **どのワークフローも quiche と opus をひとつの action から得る。そしてキャッシュキーが契約
  そのものである**：`.github/actions/third-party` はジョブが名指しした任意のターゲット向けに
  両ライブラリをビルドする。同じ「キャッシュしてビルド」のブロックが 19 個あったのが、ジョブ
  あたり 1 行になったのはそのおかげである。その `cache-key` 入力は飾りではない — 2 つのジョブが
  互いのライブラリを復元し合うのを防いでいる唯一のものである。ターゲットの集合が違えば別物だし、
  同じトリプルをビルドする 2 つのランナーイメージも別物である：ubuntu-latest でコンパイルされ
  ubuntu-22.04 で復元された `libquiche.a` は、そのリリースが避けるために存在している glibc を
  リンクする。ビルドの成果物を変えるものは何であれ、そのキーに属する。
- **Windows では静的なリリース CRT ひとつ、すべての構成で**：cargo は quiche を静的リリース CRT に
  対してビルドし（msvc の既定 — `RUSTFLAGS` で強制しないこと。proc-macro に漏れて cargo を殺す）、
  CMake ツリー全体が `MultiThreaded` を固定して合わせる。それがアプリを VC++ 再頒布可能パッケージ
  なしの単一 exe に保つものでもある。Rust にデバッグ CRT のビルドは無いので Debug も同じにする：
  `_ITERATOR_DEBUG_LEVEL=0`、`/U_DEBUG`、`/RTC1` は外す — リリース CRT には `_CrtDbgReport` も
  ランタイムチェックの支援も無い。食い違えば LNK2038 の壁で終わる。
- **パスコード = セルフサービスの入場、承認 = その代替**：入力されたコードは常に検証され、
  コードが無ければ人が決める。パスコードは、攻撃者が持ち帰れるどんな形でもネットワークを
  渡らない。
- **VT エミュレータは自前**：5 つのクライアントすべてで使えるライセンスのプラットフォーム
  ターミナルウィジェットは存在せず、自分で持つことでターミナルの挙動がオフラインでテストでき、
  どこでも同一になる。
- **ホストのシェルミラーは 1 バイト目から養われる**：PTY の出力は破壊的な単一消費者のストリーム
  である — 読んでビューアへ送ったバイトは後から再生できない — ので、*Stop & attach* が開く
  グリッドは、ボタンが押されたときではなくバイトが通り過ぎるときに組み立てねばならない。
  リモートのビューアが付いている間、ミラー自身のターミナル問い合わせへの応答は捨てられる：
  ビューアの画面が既に答えており、シェルが 2 つの答えを聞いてはならないからである。
- **ポートはひとつ**：ビーコン、画面、ターミナルが 1 つのリスナーを共有し、QUIC が接続と
  ストリームを多重化する。かつての 2 つ目のポートは、QUIC 以前の画面経路がソケットを独占して
  いたからだけ存在していた。
- **ひとつの `HostLink`、かつての 4 つのハンドシェイク**：ダイヤル + 信頼確認 + 認証 + 回復は、
  クライアント側で 4 回書かれていた — ソース照会、ビューア、ファイル送信、そして自前の生の
  `QuicEndpoint` の上のターミナル — だから送信ウィンドウがホスト鍵の変化を知ったのは、ビューアの
  3 つ後の修正だった。`HostLink` は今やクライアント側でダイヤルも認証もする唯一のコードである。
  サービスは自分の `Chan` を開き、自分の受信キューを得て、自分のスレッドで吸い出す。ターミナルの
  「バックオフして再ダイヤル」はリンクへ移り、回復を求めるすべての画面がそれを継承する。信頼の
  規則もひとつの場所にある：鍵が変わればリンクは `Deciding` に停まり、人が答えるまで待つ
  （素通しなのはソース照会だけで、`trustGate=false`、何も記憶しない — その呼び出し側には出す
  プロンプトが無いからである）。そしてホストが暗号的に証明したパスコードだけが、鍵を自動的に
  ピン留めする。
- **`HostLink` は `SendMessage` ではなく `Send` で送る**：Windows では platform 層の背後の OS
  ヘッダが `SendMessage` を `SendMessageA` のマクロとして定義し、`HostLink.cpp` ではそれがクラス
  宣言の後、メソッド定義の前に来ていた — その結果 MSVC は、どのヘッダも宣言していない
  `SendMessageA` というメンバの定義を要求した。Win32 API の名前（`SendMessage`、`PostMessage`、
  `CreateWindow`、`GetObject` など）は、OS ヘッダが届きうる翻訳単位ではメソッド名として決して
  安全ではない。直し方は `#undef` ではなく改名である。
- **portal の ScreenCast セッションは D-Bus 接続と生死を共にする**：GLib は共有のセッション
  バスを弱参照でキャッシュするので、最後のハンドルに `g_object_unref` すると接続そのものが
  破棄される。すると `xdg-desktop-portal` はセッションを落とし、コンポジタは PipeWire のノードを
  壊し、portal が渡したばかりのノード id は何も指さなくなる — ストリームは `paused` に至り、
  *no target node available* で失敗する。だから `PortalScreenCast` は呼び出しごとに借りるのでは
  なく、セッションが開いている間ずっと自分の `GDBusConnection` を所有する。デスクトップアプリは
  長らくこれを覆い隠していた。GTK がプロセスの生存期間中セッションバスへの参照を保持するからで
  ある。`deskhub-cli` は GTK をリンクせず、その参照が無かった。
- **アイコンはすべて派生物で、丸いのは一部だけ**：`make icons` は唯一のマスター
  `assets/icon_1024.png` からセット全体を作り直す。macOS、iOS、Play ストアの掲載、Android の
  アダプティブアイコンの処理は、素材を自分の形にマスクするので、それらのアセットはフルブリードの
  正方形のままにする。Windows、Linux、API 26 以前の Android ランチャーは渡されたものをそのまま
  描くので、それらのアイコンには角丸と透明が焼き込まれている — さもないとアプリは、ほかの丸い
  アイコンの隣で硬い青い四角として現れる。`scripts/make-icons.py` は意図して標準ライブラリ
  だけで書かれている：bootstrap は画像ツールを何も入れないからである。
- **デスクトップのクライアントは同時に多くのホストを抱え、スマートフォンは 1 台だけ抱える**：
  Windows、Linux、macOS の接続画面は自分では接続状態を持たない。応答したホストは接続ウィンドウ
  — `client/windows/win32/MainFrame.cpp` の `ConnectionFrame`、`client/linux/gtk/MainWindow.cpp`
  の `ConnectionWindow`、`client/macos/app/swift/App.swift` の `connection` `WindowGroup` — を
  得て、そのホストのアドレス、パスコード、機能、ソース、操作チェックを所有するので、画面は
  次をダイヤルする自由を保つ。メインウィンドウは開いているものの一覧だけを持ち、同じホストを
  二度ダイヤルしたときにウィンドウを前面へ出し、各ステータスプローブをアドレスの一致する
  ウィンドウへ押しやり、終了時にすべて閉じる。Android と iOS は意図して単一接続のままである：
  スマートフォンの画面に 2 枚目のパネルの余地は無く、開くセッションはどのみち全画面である。
  「同じホスト」の意味はどこでも `ui::SameDeviceAddr` である — 次の項目を参照。
- **ひとつのホスト、2 つの綴り、1 つの比較**：`ScanAddressText` はポートが既定なら省くので、
  走査で出た行は `192.168.1.60` と読めるのに、ユーザーが入力して接続したアドレスは
  `192.168.1.60:47777` と読める。それを文字列として比べると黙って失敗し、そうしていた場所は
  どこも本当に何かを失っていた：接続パネルは一致するデバイス行を見つけられず ping を表示せず、
  `PasscodeForDevice` は走査一覧から選んだホストに保存したコードを見つけられなかった。だから
  アドレスの等価は `ui::NormalizedDeviceAddr` / `ui::SameDeviceAddr`（`core/ui/Strings.h`）を
  通す。Swift と Kotlin のクライアントには `dh_same_device_addr` として公開されている。
  2 つのデバイスアドレスを `==` で比較しないこと。
