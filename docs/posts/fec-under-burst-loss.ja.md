# パケットロスを生き延びる五つのやり方を競わせた。どれも基準に届かなかった。

*Deskhub はリモートデスクトップのツールである。これはその A1 bake-off の記録だ。テーマはバースト
ロス下の前方誤り訂正。結論は否定的な結果なので、以下の数字はほとんどが自分の既定値が負けたところの
数字である。*

---

## どの表を見る前にも、まずここを読む

これらは**シミュレーション**の数字だ。どの行も、`core_tests` の中で回る、シードつきの決定的モデルから
出ている。ネットワークカードも GPU もそばにはない。それが買うのは再現性——二台のマシンで二回走らせても
バイト単位で同じ CSV が出る——であり、代償として現実味を、次の四つの形で失っている。後のどの表にも
この四つを持ち込んで読んでほしい。

| モデルに無いもの | 意味するところ |
| --- | --- |
| **ジッタ** | 片道遅延は一定の 20 ms（RTT が近い行では 2 ms）。落とされなかったパケットはすべて時間どおりに着くので、NACK の往復はちょうど `2 × delay` であり、それより悪くなることがない。現実のリンクはその尾を伸ばすし、そのとき損をするのがまさに NACK である。 |
| **順序の入れ替わり** | パケットは送信順に届く。したがって再構成側の overtaken/リオーダ処理は一度も働かず、順序の乱れで混乱したはずの方式もここでは実際より綺麗に見える。 |
| **輻輳** | パケットはロスモデルによってのみ落ちる。キューが無いので、修復トラフィック自身が引き起こす落ちは一つも無い。ここが一番大きい：以下の表のパリティのオーバーヘッドはシミュレーションでは**ただ**であり、現実のリンクでは**ただではない**。 |
| **本物の映像** | 1 フレームは `Rnd()` のバイト列で、デルタフレームは常に 8 パケット、IDR は常に 40 パケット。シーンチェンジも、サイズ分布も、内容依存の壊れ方も無い。「フレームが壊れた」は「そのパリティでないパケットが少なくとも一つ落ちた」という意味でしかなく、見た目がどれだけ酷いかは何も語らない。 |

もう一つ、こちらはモデルの話ではなく手続きの失敗である：

> **この記事の合否しきい値は、データの一部がすでに見えた*あとで*決められた。**
> この bake-off の規則は、数字を一つも見ないうちに目的関数と基準線を固定することだった。規則は目的
> 関数については守られ、基準線については破れた。しきい値を書き下ろした時点で、先行するパラメータ
> スイープとハードウェア計測はすでに走り終えていた。予測ではなく事後の基準として読んでほしい。以下の
> 否定的な結果はそれでも生き残る——**データを知ったうえで**引いた線すら、どれも越えられなかったの
> だから——が、肯定的な結果であれば生き残らなかった。

## 問い

Deskhub は映像を UDP データグラムで送る。パケットが一つ失われると、視聴側の再構成器はフレームを
組み立て終えられず、そのフレームの参照は消え、視聴側はホストにキーフレームを要求する。キーフレームは
40 パケット、デルタフレームは 8 パケットなので、パケットを失いつつあるリンクは二度罰を受ける。一度は
ロスそのもので、もう一度はロスが引き起こす IDR の嵐で。

だから目的関数は**毎分の IDR 要求回数**であって、救済率ではない。救済率は方式を論じるときの言葉で
あり、ユーザーが感じるのは IDR/分のほうだ。

基準線は、データの一部を見たあとに書かれたものである：

- 家庭内 WiFi で実測された動作点（ロス 0.1%、バースト 1）で **2 IDR/分以下**
- わざと過酷にした動作点（ロス 5%、バースト 4）で **20 IDR/分以下**
- そして勝者が使ってよい CPU は XOR エンコーダの **3 倍**まで。ただし救えるフレームが **2 倍以上**なら
  この限りではない

出場は五つ：グループ数からインタリーブ深さを導く XOR（現行の出荷版）、深さを独立に指定する XOR、
GF(256) 上の Reed–Solomon、実測ロスでパリティ行数を動かす Reed–Solomon、そして再送のみの NACK-only。
`fec-sweep.csv` はこれらをパリティ行数（1/2/3）、インタリーブ深さ（導出/4/8）、ロスモデル（一様 /
Gilbert–Elliott）、ロス率（0.1 / 1 / 5%）、RTT（4 / 40 ms）と掛け合わせた 180 行である。
`nack-hybrid.csv` は修復モードだけを取り出し、RTT 4 / 20 / 40 / 80 ms と視聴側の保持ウィンドウにわたる
72 行である。

## 結果 1：ロス 5%、バースト 4 では、どれも届かなかった

基準は 20 IDR/分。スイープにはその動作点の行が 36 ある。その中で最良が 36 IDR/分——しかもそれは
**データ 100 パケットあたりパリティ 143 パケット**を送って買った数字だ。

| scheme | parity rows | depth | overhead | rescued | **IDR/min** |
| --- | ---: | ---: | ---: | ---: | ---: |
| xor（出荷版） | 1 | derived | 12.5% | 33.87% | **171.00** |
| xor | 1 | 8 | 90.9% | 78.69% | **81.00** |
| rs | 2 | 8 | 188.7% | 86.67% | **45.00** |
| rs | 3 | 4 | 142.9% | 90.57% | **36.00** ← スイープ中の最良 |

> **この表の末尾ではなく、この表の隣に置くべき注意：**overhead の列こそ、これが買い物リストではなく
> 否定的な結果である理由である。シミュレーションには輻輳が無いので、142.9% のオーバーヘッドはそこでは
> 何も要求しない。20 Mbps のリンクなら映像がおよそ 8 Mbps、パリティが 12 Mbps ということになり、
> ビットレート制御を押し下げ、フレームを小さくし、その行の他のあらゆる数字を変えてしまう。モデルは
> それを示せない。だから最下行は「勝者」ではない。モデルが答えられなくなる地点である。

その行を出すには：

```sh
awk -F, 'NR==1 || ($6=="5.00" && $7=="4.0")' docs/data/bake-off/fec-sweep.csv
```

## 結果 2：共通する 40 点すべてで、Reed–Solomon と XOR は同一の数字を出した

`fec-sweep.csv` には、`xor` の行と `rs` の行が方式名以外まったく違わないパラメータ点が 40 ある。その
40 すべてで、**残り 29 列のどれもが一文字たがわず等しい**。近いのではなく、等しい。

```sh
python - <<'PY'
import csv, collections
rows = list(csv.DictReader(open('docs/data/bake-off/fec-sweep.csv')))
params = ('fec', 'armed_from_feedback', 'groups', 'model', 'loss_pct', 'burst_pkts', 'seed',
          'parity_rows', 'nack', 'rtt_ms', 'overtaken_limit')
by = collections.defaultdict(dict)
for r in rows:
    by[tuple(r[k] for k in params)][r['scheme']] = r
pairs = [(v['xor'], v['rs']) for v in by.values() if len(v) == 2]
same = sum(all(a[k] == b[k] for k in a if k != 'scheme') for a, b in pairs)
print(len(pairs), 'pairs,', same, 'identical')
PY
```

```
40 pairs, 40 identical
```

これはバグではないし、言葉にした瞬間に驚きではなくなる。**その 40 点はすべて `parity_rows=1` であり、
パリティ 1 行の Reed–Solomon 符号は*すなわち* XOR だ。**コーシー行列は 1 の並んだ一行に縮退する。
GF(256) の体と、コーシー行列と、ガウス消去の復号器を書いたが、実際に出荷されているパリティ設定では、
そのすべてが二行の XOR ループがすでに作っていたパリティバイトを計算し直しているだけだった。

再現されないのはコストのほうだ。このマシンでは `core_perf` の `video/fec-encode-rs` の行が
**143 µs/フレーム**、`video/fec-encode-xor` が **22.7 µs/フレーム**——6.3 倍である。*（この対は計測で
あってシミュレーションではない。ある Intel デスクトップ上の `core_perf` から出ており、CSV のように
バイト単位で再現するものではない。本稿で CSV の行でない唯一の数字なので、表に混ぜずここで名指しして
おく。）*

つまり Reed–Solomon が元を取り始めるのはパリティ 2 行からであり、パリティ 1 行ではビット単位で同一の
結果に対する 6.3 倍の税である。出荷時の既定は XOR のままとする。

## 結果 3：インタリーブ深さは安いレバーではない。そして私はそれを安いと書いた

この分析の初稿は、インタリーブ深さを「この格子で最も安いレバー」と呼んでいた。1 フレームをより多くの
FEC グループへ散らしても CPU は増えない、という理由である。それは正しく、そして無関係である。

| scheme | parity rows | depth | overhead | rescued | IDR/min |
| --- | ---: | ---: | ---: | ---: | ---: |
| xor | 1 | derived | **12.5%** | 33.87% | 171.00 |
| xor | 1 | 4 | **43.9%** | 62.90% | 117.00 |
| xor | 1 | 8 | **90.9%** | 78.69% | 81.00 |

同じ方式、同じパリティ行数、同じロス、同じシード。深さ 8 は IDR 率を半分にし——そしてオーバーヘッドを
12.5% から 90.9% へ持ち上げる。デルタフレームが 8 パケットだからだ。深さ 8 では各グループがパケットを
一つしか持たず、各パケットは自分自身のためだけのパリティを運ぶ。それは符号化ではなく、すべてを二度
送っているだけだ。20 Mbps の予算では、キーフレーム要求を半分にするために画面の半分を差し出すという
意味になる。

> **注意：**8 パケットのデルタフレームはモデル内の定数であって、計測値ではない。現実のデルタフレームは
> 大きさが変わるし、深さ 8 の縮退した挙動はその定数が生んだ人工物でもある。人工物を差し引いて残るのは
> 形のほうだ。深さは、それがパケット数をどれだけ追い越すかに比例して帯域を食い、決してただではない。

```sh
awk -F, 'NR==1 || ($1=="xor" && $2=="1" && $3=="0" && $6=="5.00" && $7=="4.0" && $29=="40")' \
    docs/data/bake-off/fec-sweep.csv | sort -u
```

## 結果 4：出荷中の起動ポリシーは、FEC を常時オンにするのにも、FEC を持たないのにも負ける

これは Deskhub 自身の既定値が、並んだ選択肢の中で最悪になる表である。

FEC は常時オンではない。フィードバックを見張り、報告されたロスが十分に悪いときに FEC を起動する
ポリシーがある。家庭内 WiFi が実際に生んだ動作点——ロス 0.1%、バースト 1、1800 フレーム——で、その
ポリシーを三つの代替案と並べるとこうなる：

| 構成 | FEC 起動 | overhead | 救えたフレーム | **IDR/min** |
| --- | ---: | ---: | ---: | ---: |
| 修復を一切しない | — | 0.0% | 0/16 | 32.00 |
| FEC 常時オン | 100.0% | 12.5% | 16/16 | **0.00** |
| **出荷中の起動ポリシー** | 30.0% | 4.1% | 6/16 | **20.00** |
| NACK のみ、RTT 4 ms | — | **0.0%** | 15/16 | **2.00** |
| NACK のみ、RTT 40 ms | — | 0.0% | 0/16 | 32.00 |

この動作点の基準は 2 IDR/分以下だった。出荷構成はそれを 10 倍外している。このポリシーは 7 割の時間を
非起動で過ごす。報告されたロスがしきい値と比較される前に丸められ、0.1% は 0 に丸まるからだ。

基準を満たした行は、**前方誤り訂正がまったく無い**行である。短いリンクでの NACK のみ、帯域の
オーバーヘッドはゼロ、壊れた 16 フレームのうち 15 を救った。これは同じ作業文書に記録された私自身の
以前の結論——再送は実装する価値がない——をひっくり返す。

> **注意、しかも大きな注意：**その NACK の行は、モデルのジッタ無し仮定が配当を出したものだ。RTT 4 ms
> では再送は必ずフレームの締切前に届く。モデルがちょうど 4 ms で届くと保証しているからである。すぐ下の
> RTT 40 ms の行——16 中 0 を救済、32 IDR/分——が、往復が締切に収まらなくなったときに起きることだ。
> ジッタの尾を持つ現実の 4 ms リンクは、その二行のあいだのどこかにいるのであって、良いほうの行の上には
> いない。

```sh
awk -F, 'NR==1 || ($6=="0.10" && $7=="1.0" && $9=="1800")' docs/data/bake-off/fec-sweep.csv
```

## 結果 5：修復モード対 RTT——それぞれがどこで壊れるか

`nack-hybrid.csv` は三つの修復モードを、四つの RTT と視聴側の保持ウィンドウにわたって、ロス 1% と 5%、
バースト 4 で走らせる。面白いのは最良のケースではなく、それぞれの壊れ方の形である。

**ロス 5%、RTT 4 ms**、保持ウィンドウ無しでは：

| repair | overhead | rescued | IDR/min |
| --- | ---: | ---: | ---: |
| fec-only | 12.5% | 29.51% | 180.00 |
| nack-only | **0.0%** | 57.69% | 126.00 |
| fec+nack | 12.5% | **68.42%** | 126.00 |

**ロス 5%、RTT 80 ms**、長いリンク上の同じ三行では：

| repair | overhead | rescued | IDR/min |
| --- | ---: | ---: | ---: |
| fec-only | 12.5% | **31.25%** | 153.00 |
| nack-only | 0.0% | **7.69%** | 180.00 |
| fec+nack | 12.5% | 25.42% | 153.00 |

往復が伸びるにつれ NACK の救済率は 57.69% から 7.69% へ落ち、ハイブリッドも道連れにする。RTT 80 の
`fec+nack` は同じ RTT 80 の `fec-only` *より悪い*。NACK の予算を注いだフレームがすでに締切を過ぎて
いるからだ。視聴側の保持ウィンドウはその大半を取り返す——RTT 80 で `hold_frames=8` なら `fec+nack` は
救済 67.21%、63.00 IDR/分に戻り、このファイルでロス 5% のどの行も届く最小の IDR/分と並ぶ——が、
8 フレーム保持することは `longest_stall_ms` に 116 ms として現れる。売り物が「すぐ反応すること」
そのものであるツールの上で、である。

> **注意：**`hold_frames` は、ここで唯一、測れた良い数字を測っていない悪い数字と引き換えにする列だ。
> 視聴側で足された遅延は目的関数にまったく入っていないので、この表は保持ウィンドウを順位付けはできて
> も、どれならユーザーが我慢するかは言えない。

```sh
awk -F, 'NR==1 || ($4=="5.00" && $3=="0")' docs/data/bake-off/nack-hybrid.csv
```

## 何が出荷されたか

何も出荷されなかった。既定値は出発点のままである。XOR、パリティ 1 行、導出された深さ、既存ポリシー
による起動。Reed–Solomon、適応パリティ、NACK は `--fec=`、`--fec-depth`、`--fec-parity`、`--nack` の
背後に計測用のフラグとして残る——次のラウンドのために取ってあり、誰も走らせないコードに CI が金を
払わないよう fuzz とサニタイザのマトリクスからは外し、そして選ぶためのデータを何も持たないエンド
ユーザーには出さない。

この bake-off が実際に生んだものは三つある：

1. 書き直しを止められるだけ強い否定的な結果：パリティ 1 行の RS は 6.3 倍の CPU 請求書つきの XOR で
   あり、方式はそもそもボトルネックではなかった。
2. 本当のボトルネックの順位付け：**起動ポリシー**は実測された動作点で 20 IDR/分を費やしており、これは
   スイープ内のどの方式選択の値打ちよりも大きい。次に直すべきはそこだ。
3. 一つのひっくり返し：NACK-only は計測もされずに切り捨てられていたが、短いリンクではこのファイルの中で
   基準を満たす唯一の構成であり、しかもオーバーヘッドはゼロである。

正直な要約はこうだ。答えようとして出発した問い（「XOR か Reed–Solomon か？」）は間違った問いであり、
このスイープが走らせる価値を持ったのは、主にそう教えてくれたからである。

## すべてを再現する

```sh
git clone https://github.com/manhpham90vn/Deskhub
cd Deskhub
make test                  # core_tests をオフラインでビルドして実行する
scripts/bake-off-csv.sh    # [csv] 行を out/bake-off/*.csv に切り分ける
diff out/bake-off/fec-sweep.csv docs/data/bake-off/fec-sweep.csv
diff out/bake-off/nack-hybrid.csv docs/data/bake-off/nack-hybrid.csv
```

二つの `diff` は何も出力しないはずだ。どの行もシードつきのシミュレーションが生む——シードは
`0x5DEECE66D` で、`fec-sweep.csv` の全行の `seed` 列に印字されている——ネットワークも GPU も使わない
ので、テストをビルドできるどのマシンでもファイルはバイト単位で再現する。

- 生データ：[`docs/data/bake-off/fec-sweep.csv`](../data/bake-off/fec-sweep.csv)（180 行）·
  [`docs/data/bake-off/nack-hybrid.csv`](../data/bake-off/nack-hybrid.csv)（72 行）
- それを生成するスクリプト：[`scripts/bake-off-csv.sh`](../../scripts/bake-off-csv.sh)
- シミュレーションそのもの：
  [`core/tests/transport/LossGoodputTests.cpp`](../../core/tests/transport/LossGoodputTests.cpp)
- 各表がプロジェクトの言葉で何を結論したか：[`docs/ARCHITECTURE.ja.md`](../ARCHITECTURE.ja.md)

列の意味は CSV のヘッダにある。`rescue_pct` は `frames_rescued / frames_damaged`、`overhead_pct` は
データパケットに対するパリティパケットの比、`idr_per_min` はキーフレーム要求を
`frames_sent × 16 667 µs` で換算したもの、`longest_stall_ms` は配信された二つのフレームの間の最大の
間隔である。
