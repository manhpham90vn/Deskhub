# Deskhub — Functional Specification

This specification describes what people can do with Deskhub and how the app responds.
For installation, build instructions and security guidance, see [`INSTALL.md`](INSTALL.md),
[`BUILD.md`](BUILD.md) and [`SECURITY.md`](../SECURITY.md). Implementation details live in
[`ARCHITECTURE.md`](ARCHITECTURE.md) and the source tree.

- **Status:** describes the behaviour of the current code.
- **Audience:** testers, reviewers, contributors and people preparing store listings.

---

## 1. Product summary

Deskhub lets you share a machine's screen with another device on a network both can
reach. The viewer can also control the shared machine's mouse and keyboard when the host
allows it. The same app can share a screen or connect to another machine. Desktop hosts
can also offer a **terminal**: a shell that a connected device opens in its own window
(sections 4 and 5).

An installer is available but not required. Deskhub needs no account, sign-in,
background service or cloud component. A client connects to a host by IP address over a
network both devices can reach.

## 2. Vocabulary

| Term | Meaning |
| --- | --- |
| **Host** | The machine whose screen (or terminal) is being shared. |
| **Client** / **Viewer** | The machine watching a host, and optionally controlling it. |
| **Source** | One shareable thing on the host: a display, or the terminal. A host may share several at once. |
| **Session** | One viewer watching one source. Each source opens in its own window. |
| **Machine key** | The one key a machine creates on first run and never replaces automatically. It is the machine's identity in both roles: a host proves itself with it when others connect, and a client signs in with it when it connects to a host. People see it as one fingerprint (`SHA256:…`); its public half is what a host owner adds to the allowed clients. |
| **Allowed clients** | The host's list of public keys that may connect (`authorized_keys`), each with a label. Only a listed key gets in (section 9). |
| **Trusted host** | A host this machine has decided to trust, by its key: the fingerprint pinned on first connection or taken from its QR code, a name, and the last address it answered at. Trust follows the key, so a trusted host keeps its trust when its address changes. |
| **Connection request** | What a host records when a device it has not allowed yet tries to connect: the device's name, key fingerprint, address and the time. The host's owner can **Approve** or **Deny** it (H-18). |
| **QR code** / **invite** | A code a sharing host can show — also a `deskhub://pair/…` link — that carries the host's addresses, its fingerprint, its name and a one-time token. A device that scans or pastes it trusts the host and is let in at once, with no approval step (C-12). |
| **Device name** | The one name this machine goes by — shown to viewers when it hosts and sent to the allowed clients that connect to it, sent to hosts when it connects, and used as the label of its copied public key (T-26). |

A single machine can be host and client at the same time.

## 3. Roles by platform

| Platform | Can host | Can view | Shares its sound when hosting |
| --- | :--: | :--: | :--: |
| Windows | ✅ | ✅ | ✅ |
| macOS | ✅ | ✅ | ✅ |
| Linux | ✅ | ✅ | ✅ |
| Android | ✅ view-only | ✅ | ⚠️ Android 10+ |
| iOS | ✅ view-only | ✅ | ⚠️ app audio only |

Every platform plays a host's sound when viewing (V-6); the last column is only about
sending this machine's own sound as a host.

Every platform offers the same client feature set unless a feature is marked for desktop or
mobile, or section 12 states otherwise. Phones and tablets host in **view-only** mode: they stream their screen but never accept
remote input, because no mobile OS lets an ordinary app drive the device.

The app is organised into the same named sections everywhere: **Host**, **Client** and
**Settings** — plus a **Devices** page holding the keys that decide who connects where
(section 9).

The three desktop platforms also have a command-line client, `deskhub-cli`. It shares this
machine (`share`, with `--terminal` for a shell, `--files` to take files and `--qr` to print
a QR code a phone scans), watches and drives a host (`connect`), opens a remote shell
(`shell`), sends files (`send`), and manages allowed clients, connection requests, trusted
hosts and saved host aliases (`access`, `trust`, `host add` / `host update` / `host remove`).
`settings get` and `settings set` read and change the app's settings. A command that
connects waits up to two minutes for a host's owner to approve this machine (C-5);
`--approval-wait SEC` changes that wait (1 – 600 seconds). The CLI reads and writes the same
settings, machine key, allowed clients and trusted hosts as the app. Screen viewing through
the CLI is available on Windows and Linux; on macOS, use the app to watch a screen.

## 4. Hosting — sharing this machine's screen

| ID | Feature | Description |
| --- | --- | --- |
| H-1 | Display picker | Before sharing, the user ticks which of this machine's displays to expose. At least one must be ticked. |
| H-2 | Multi-display sharing | Several displays can be shared simultaneously; each becomes a separate source that viewers pick between. |
| H-3 | Source limit | A maximum of **8** displays can be shared at once. If the machine has more, the user is warned that only the first 8 will be shared. |
| H-4 | Start / stop sharing | One action starts sharing, one stops it. Once sharing starts or is starting, a banner shows the state (*Starting share…* / *Sharing*) and its detail; before that the button's own label (*Start sharing*) is the only status shown, so no banner is drawn. |
| H-5 | Stop one display | An individual shared display can be stopped without ending the whole share. |
| H-6 | Connection details | While sharing, the app lists this machine's network addresses and the port viewers must use, so they can be read out or copied. Beside that list sits **Show QR code**. On desktop it opens a small *QR code* window: the code, the `deskhub://pair/…` link it encodes with a copy button, and a clock counting down the five minutes the code is good for; when the clock runs out the window says the code has expired and offers **Generate new QR code**, which makes a fresh one. Closing the window, or stopping the share, revokes the code so it can no longer be used. Each code lets one device in the moment it scans or pastes it (C-12). On a phone or tablet the code unfolds on the Host page instead, with the same countdown, expiry note and **Generate new QR code**: the button reads *Hide QR code* while it is up, and hiding it revokes it the same way. If no code can be made, every platform says so instead of showing nothing. On desktop the *Share on network* choice (T-9) sits on the hosting screen beside this list, and the list shows only the chosen network's address — *All networks* shows every address. While sharing (or starting to share) the choice is locked; stop sharing to change it. |
| H-7 | Live session table | For each shared display the host sees: display name, resolution, number of viewers, capture rate, send rate, bandwidth in use, and round-trip time. Each connected viewer appears as its own row under its display, identified by its device name and address — "Name (ip:port)" (C-7), or by the bare address when it sent no name. |
| H-8 | Disconnect a viewer | The host can drop any individual viewer from the session table. |
| H-9 | Viewer limit | At most **5** screen sessions may be open on one host at a time, counted across all its shared displays — a viewer watching two displays counts twice. Further attempts are rejected as busy. Shells (H-12) and file transfers (H-16) do not count towards it. |
| H-10 | Failure reporting | If sharing cannot start, the reason is shown to the user rather than failing silently. A terminal that cannot start because its port is taken says exactly that. |
| H-11 | Terminal source (desktop) | The source list also offers **Terminal — a shell on this machine**. It is ticked afresh every time the list is shown and never saved; sharing screen without terminal, terminal without screen, or both, are all valid. Everything shares the app's one UDP port (T-4), allowed clients (S-2) and network choice. |
| H-12 | Shell sessions in the table | While the terminal is shared, the live table shows a *Terminal* row (with its port), and each open shell as a row beneath it identified like a viewer (C-7), with *Disconnect*; the *Terminal* row's *Stop* ends terminal sharing alone. At most **8** shells are open at once. Every shell opened, closed or reattached is written to the session log (G-3) with the client's address, name and key. |
| H-13 | Shells stay on the host | A shell whose connection is lost — the network drops, or the client window closes — is kept on the host with its contents and scrollback intact: there is no time limit. The same client reattaches on its own: it retries with a widening delay for two minutes, says it is reattaching while it does, and picks the same shell back up. Any admitted client can also ask the host which shells it is keeping and reattach one of them by its id instead of opening a new one. A shell ends only when its shell process exits, the host stops sharing the terminal, or it is closed from the session table; closing a client window never ends it. Any admitted client may also end a kept shell by its id, from that list; the machine that was typing in it is told its shell ended. |
| H-14 | Stop & attach (desktop) | Every shell row — live or waiting for a reattach — also offers **Stop & attach**: the remote client is disconnected (its window reports the shell ended) and the very same shell opens in a terminal window on the host, contents and scrollback intact. From then on the shell belongs to the host machine: the old client cannot reattach, no time limit applies anyway (H-13), the table marks the row *attached on this machine*, and closing the host's window — or *Stop* on its row — ends the shell. The takeover is written to the session log (G-3). |
| H-15 | An idle shell is not a dropped shell | A terminal connection carrying no traffic is kept alive by the client, so a shell left sitting at a prompt is not mistaken for a broken link and closed. |
| H-16 | File transfer source (desktop) | The source list also offers **File transfer — files viewers send**, ticked afresh every time the list is shown and never saved; it shares the app's one UDP port (T-4), allowed clients (S-2) and network choice like the terminal (H-11). Files land in the folder named on the live table's *File transfer* row once sharing starts (H-17, T-25). A batch carries at most **32** files, **8 GiB** per file and **32 GiB** in total; anything larger, or a name that cannot be stored, is refused with the reason. Each file is written beside its final name with a `.deskhub-part` suffix and renamed only once it has arrived whole and its checksum matches; a damaged file is thrown away and stops the batch. Nothing is ever overwritten: a name already in the folder gets a number appended. If the folder cannot be written to, no files are taken and the host says so rather than failing silently. |
| H-17 | Transfers in the table | While file transfer is shared, the live table shows a *File transfer* row naming the folder, with an **Open folder** button beside it that opens that folder in the system file manager, and each machine currently sending as a row beneath it, identified like a viewer (C-7), with the file being received, its place in the batch and the share done — or the reason the batch stopped. The *File transfer* row's *Stop* ends file transfer alone. Every batch offered, accepted, refused or finished is written to the session log (G-3) with the machine's address, name and key. |
| H-18 | Connection requests | A device that connects without being among the allowed clients is not turned away: once it has proved it holds the private half of the key it presents — so nobody can file a request in another device's name — the host records a **connection request** and the Host page lists it, between the address list and the live session table, on every platform. Each row shows the device's name (or *(unnamed)*), the start of its key fingerprint, its address, and **Approve** and **Deny**. *Approve* adds the device's key to the allowed clients with the device's name as its label, so its next attempt — it keeps trying on its own (C-5) — gets in; *Deny* drops the request from the list and turns that device away for the rest of the request's 10 minutes: its next attempt is refused rather than filed again, and a device still waiting (C-5) stops at once, saying the owner declined its request. A request expires by itself after **10 minutes**, a host keeps at most **16**, dropping the oldest to make room, and at most **one per address**: a device asking again refreshes its own row rather than adding one, and a request from an address that already has one replaces that row, whichever device sent it. With nothing waiting the section says so in one line. The same list sits on the Devices page (S-3), so a request can be answered without opening the Host page, and each new request also raises one **system notification** — *Connection request*: ‹name› (‹address›) wants to connect to this machine — while the app is running, once per device, on every platform; there is no notification for a request that arrives while the app is closed, and none is sent anywhere but to this machine's own notification centre. The CLI lists them with `access requests` and answers with `access approve` / `access deny --fingerprint SHA256:…`; a running `share` also prints each new request as it arrives. |

## 5. Connecting — viewing another machine

| ID | Feature | Description |
| --- | --- | --- |
| C-1 | Connect by address | The user types the host's IP address in one field and the UDP port in another, prefilled with the default `47777`. Pasting `192.168.1.10:47777` into the address field still works — its explicit port wins over the port field. The same field also takes a pasted `deskhub://pair/…` link from a host's QR code (C-12): Connect then dials the addresses inside the link, and the field is filled with the one that answered. Invalid input — including text that is neither an address nor a Deskhub link — produces an explanatory hint, not a failure. |
| C-2 | First connection to a host | Connecting to a host this machine has never trusted opens a **New host** dialog showing the host's key fingerprint and asking the user to compare it with the one on the host's Devices page (S-3). *Cancel* saves nothing and connects nowhere; **Trust and connect** saves the host to the trusted hosts (S-8) and connects. If the address used to belong to a different trusted host, the dialog says so — naming that host and its fingerprint — because a different key at a known address is a different machine. A host already trusted connects without asking anything, whichever address it is reached at. A host reached by scanning its QR code in the app, or by pasting its link (C-12), is trusted without the dialog: the code already carries its fingerprint, and the connection goes ahead only if the machine that answers proves it holds that key. A `deskhub://pair/…` link opened from outside the app is not trusted that way: unless its host is already trusted, the dialog appears first, showing the fingerprint the link carries (C-12). |
| C-3 | Control opt-out | Before connecting, the viewer can untick *control the remote machine* to watch without sending any input. A host that accepts no input at all — a phone or tablet (P-4), or a desktop sharing with input off — says so when asked what it is sharing, and the desktop clients carry a standing note that control and terminal do nothing against such a host. |
| C-4 | Source picker | If the host is sharing more than one display, the viewer is asked which to view. Picking several opens several windows. If the host shares exactly one display, it opens immediately. |
| C-5 | Clear failures | The viewer is told why a connection failed — the host is unreachable, is not sharing, is not trusted yet, refused this device, or its owner did not approve this device in time (S-2). A host that has not allowed this device does not fail it at once: the client fills the address fields with the host that answered and shows *Waiting for the owner of ‹host› to approve this device…* with a **Cancel** button, and keeps redialling on its own every few seconds for up to **2 minutes**; the moment the owner presses *Approve* (H-18) the next attempt gets in and the page moves on as if nothing had happened. If the owner presses *Deny* it stops at once and says so. Otherwise only after those two minutes does it fail, saying the owner did not approve this device in time and to ask them to press *Approve* under *Connection requests* on their Host page, then connect again — the request stays on the host for 10 minutes, so a late approval needs only a second Connect. A host that turns this device away without keeping a request names the ways in: connect again so its owner sees the request and presses *Approve*, scan the QR code it shows (C-12), or copy this device's public key from *Devices → Copy public key* for the owner to paste under *Devices allowed to connect to this machine*. A host that is turning this device away for now after several failed attempts says to wait a few seconds; one that does not answer the sign-in at all is reported within about 15 seconds. An outright refusal asks the user to have the host's owner check that this device's public key is still listed under *Devices → Devices allowed to connect to this machine*. After a refusal or an approval that did not come in time, the CLI adds the `deskhub-cli access approve --fingerprint SHA256:…`, `deskhub-cli key public` and `deskhub-cli access add --stdin` commands that do the same. |
| C-6 | Session end notice | When a session ends, from either side, the viewer sees why. |
| C-7 | Viewer name | A connection always carries this machine's device name (T-26); the connect page has no name field of its own. Hosts show the name next to this machine's address so viewers can be told apart. |
| C-8 | Open a shell | *Terminal — open a shell* is a button that appears once a host has answered (C-10), on every client. The shell opens in its own window — grid, scrollback, status line, and on phones an extra key row (Esc, Tab, latching Ctrl/Alt, arrows, ^C) — and that window states why a shell could not open (this device not approved in time, refused, unreachable). Watching the screen and running a shell at the same time is normal. Every client learns what the host shares before opening anything: against a host with no terminal — a phone or tablet, or a desktop not sharing one — the button stays disabled, so no terminal window is opened at all. A client can also ask the host which shells it is keeping and reattach one of them by its id instead of opening a new one. When the host is already keeping shells, pressing it opens a **list of those shells** first — each row naming its id, size and the machine that opened it — and the shell only opens once one is reattached or *New shell* is chosen; with nothing kept, a new shell opens straight away. A shell someone else is typing in, or one taken over at the host (H-14), is listed but cannot be reattached. Each row the client may end also offers *Close shell*, which asks first and ends that shell on the host for whoever holds it. |
| C-9 | Send files | Every client can send files to a host that is taking them. *File transfer — send files to it* is a button that appears once a host has answered (C-10), on every client, and opens a **Send files** screen. On Android and iOS files are picked from the system photo picker or the system file browser, and a copy is staged in the app's own cache before it is sent. One batch at a time: while one is running the pickers are disabled and a second offer is refused as busy. Progress names the file being sent, its place in the batch and the share done, and the transfer can be stopped at any point. When it settles, every file in the batch is listed as sent or not sent, with the reason. Every client learns what the host shares before opening anything: against a host that is not taking files the button stays disabled, so no window opens. |
| C-10 | Connect, then choose | Connect only authenticates: it dials the host, checks its key (S-8), proves this machine's own key (S-2), and asks what the host shares. What a host that has answered offers is the same everywhere: its address, a **Disconnect** control, the live line of V-7, and one button each for *Remote desktop — view its screen*, *Terminal — open a shell* and *File transfer — send files to it*, each enabled only if the host shares that capability. Each session opened afterwards signs in with the same key again; nothing is ever asked at the host. Where those land differs by platform (C-11). |
| C-11 | One window per host (desktop) | On Windows, Linux and macOS a host that answers opens a **connection window** of its own, titled with its address and holding everything C-10 lists. The connect page itself never changes state: the address and port fields, Connect and the recent list stay put, so the next host can be dialled while the first is still open, and a machine can be connected to several hosts at once. Connecting again to a host that already has a window raises that window instead of opening a second. Closing a connection window, or its **Disconnect**, drops that host alone and leaves the others untouched; quitting the app closes them all. Sessions already opened from a window (V-1, C-8, C-9) are separate windows of their own and outlive it. On Android and iOS there is one connection at a time and it stays on the connect page: until Connect succeeds the page is the fields, Connect and the recent list — nothing else; once the host answers those give way to what C-10 lists, and Disconnect, or editing the address or port, returns the page to the first state. |
| C-12 | Connect by QR code | The quickest first connection needs no fingerprint comparison and no approval. On a phone or tablet the Client page has a **Scan QR code** button that opens the camera; the first time, the operating system asks for camera permission, which Deskhub requests only here and uses for nothing else — decline it and the page says how to paste the link instead. Opening a `deskhub://pair/…` link from another app (the system camera, a message) lands in the same place, but when that host is not trusted yet it first shows the *New host* dialog (C-2) with the fingerprint the link carries, because a link can come from anywhere; *Cancel* connects nowhere, and *Trust and connect* carries on exactly as a scan would. Every client, desktop included, can also paste the link into the address field (C-1). The code carries up to four of the host's addresses with its port, the host's key fingerprint, its name, and a random one-time token. The client dials the addresses in turn and, before sending anything else, checks that the machine answering holds the key named in the code: if it does not, the connection stops with *The machine that answered is not the one that made this QR code* and the token is never sent. If it does, the host is trusted (without the *New host* dialog when the code was scanned or pasted in the app), the token goes with this device's key and name, and once this device has proved it holds that key the host adds it to its allowed clients, labelled with the device's name, and lets it in — the Client page moves straight to what C-10 lists. Each code works once and for at most **5 minutes**; closing its window on a desktop host, hiding it on a phone or tablet, or stopping the share, revokes it (H-6). A device the host already allows can scan a code purely to pick up the host's current address: it gets in as usual and the token is left unused. Camera frames are decoded on the device and never stored or sent anywhere. |

## 6. Finding machines

| ID | Feature | Description |
| --- | --- | --- |
| D-1 | No network scan | Deskhub never scans the network and a host answers no discovery packets. A client reaches a host by an address the user types (C-1), a recent address (D-5), a trusted host (S-8), or the addresses inside a QR code the host's owner shows them (C-12) — the code travels by eye or by paste, never over the network, so it is not discovery. |
| D-4 | Click to connect | Picking a recent address, or *Connect* on a trusted host, starts a connection to it. |
| D-5 | Recent devices | Hosts connected to before are kept in a recent list on the Client page — up to **10** — each showing the host's name (its device name, T-26, which the host sends only after this machine has authenticated; the address when it sent none), its address and when it was last connected. A host is added only once it has answered. The recent list of older versions is not carried over. |
| D-8 | Forget a device | A recent address can be removed from the list. |

## 7. Viewing a session

| ID | Feature | Description |
| --- | --- | --- |
| V-1 | Fit to window | The remote screen is scaled to fit the window, preserving aspect ratio, with the window sized to the source on open. On desktop, when the stream's shape genuinely changes mid-session — a phone or tablet host rotating, or a switch to a differently shaped display — the window re-fits itself to the new shape; quality changes at the same shape leave the window alone. |
| V-2 | Zoom and pan (mobile) | On phones and tablets the view can be zoomed up to **5×** and panned. Zoom level is displayed and can be reset in one action. The desktop viewers always show the whole screen fitted to the window (V-1). |
| V-3 | Session status | The window shows a live status line: frame rate, bandwidth, packet loss, round-trip time and end-to-end latency. |
| V-4 | Titled windows | Each viewer window is titled with the source it is showing plus its current status, so multiple sessions are distinguishable. |
| V-5 | Disconnect | The viewer can end the session at any time. |
| V-6 | Sound | Where both machines support it (section 3), the viewer hears what the shared machine is playing, in step with the picture to within about a frame. Sound is carried on its own channel: a single lost packet is usually rebuilt from the one after it, a longer gap costs a fraction of a second of audio, and neither ever disturbs the picture, and a machine playing nothing costs almost no bandwidth. It is off for a viewer that turns it off (T-23) and never sent by a host that turns it off (T-22). |
| V-7 | Connection health | The reading sits where the host was answered — the connection window on desktop, the connect page on Android and iOS (C-11) — not in the session window: it shows the host's address, a **Disconnect** control (V-5) and a live line saying it is connected, with the ping beside it, going red the moment that host stops answering. The reading comes from a once-a-second ping over the authenticated connection, so it is there before a session is opened and stays there while several are, and on desktop each open host carries its own. A session window that loses its host still says it is reattaching (V-8). |
| V-8 | Auto-reconnect | A session that loses its host — the network drops, the stream goes silent — does not end. The window keeps its last picture, states that it is reattaching, and redials with backoff for up to a minute; when the host answers again the picture resumes on its own. Only after that minute, or when the host deliberately ends or refuses the session, does the window close with the reason. A shell window retries on its own for two minutes and then reports the connection as lost; the shell itself stays on the host with no time limit, ready to be picked back up (H-13). |

## 8. Controlling the remote machine

| ID | Feature | Description |
| --- | --- | --- |
| I-1 | Mouse | Movement, left / right / middle / back / forward buttons, and the scroll wheel are sent to the host. |
| I-2 | Keyboard | Key presses and releases are sent, including modifier combinations. |
| I-3 | Pointer lock (desktop) | `F9` locks the mouse to the remote screen for games and other software that expects raw movement; `F9` or `Esc` releases it. The current state is shown in the window title. |
| I-4 | Focus safety | Losing focus releases the pointer lock and any keys still held down, so no key can be left stuck on the host. |
| I-5 | Touch trackpad (mobile) | On phones and tablets the video acts as a trackpad: drag moves the pointer, tap clicks, double-tap right-clicks, hold-and-drag drags, and a vertical two-finger drag scrolls. |
| I-6 | Pointer / pan mode (mobile) | A toggle switches between moving the remote pointer and panning a zoomed view. |
| I-7 | On-screen keyboard (mobile) | The device keyboard can be shown or hidden on demand and types into the remote machine. |
| I-8 | Hotkey bar (mobile) | Shortcut buttons for keys a touch keyboard makes awkward: `Esc`, `Tab`, `Enter`, the four arrows, `Del`, `Ctrl+C`, `Ctrl+V`. |
| I-9 | Host always wins | Input from the person physically at the host machine takes precedence over every remote viewer. |
| I-10 | One driver at a time | Among the viewers of one shared display, only one controls the mouse and keyboard at a time. The earliest to have joined that display wins contention; the others' input is ignored until the current driver has been idle for **1 second**. Viewers of different displays are arbitrated separately. |
| I-11 | View-only enforcement | When the host has disabled control, or the viewer chose to watch only, no input reaches the host and the viewer window states that it is view-only. |

## 9. Access control and safety

| ID | Feature | Description |
| --- | --- | --- |
| S-1 | Encryption | Sessions run over an encrypted transport (QUIC/TLS). Everything a session carries — video, control, input, clipboard and terminal traffic — travels encrypted between the two machines. The host answers nothing in plain text: any unencrypted packet arriving at the port is dropped, and it says nothing — not even what it shares — before a client has authenticated. [`SECURITY.md`](../SECURITY.md) has the full picture. |
| S-2 | Allowed clients gate admission | Access works like SSH. A client proves it holds the private half of its machine key; the host lets it in only if that public key is among its allowed clients. A key gets onto that list in one of three ways, each a deliberate act by the host's owner: they press **Approve** on the device's connection request (H-18); the device scans or pastes the QR code the owner shows while sharing (C-12), whose one-time token stands in for the click; or the owner pastes the device's public key (copied on the device with *Copy public key*) on the Devices page or with the CLI (`access add --stdin`). A pasted key may be an `ecdsa-sha2-nistp256` or an `ssh-ed25519` line. There is no passcode and no switch that lets unknown machines in: nobody gets in without a live token or an Approve. A token works once, for 5 minutes, and is revoked when the code's window is closed, the code is hidden, or sharing stops; a wrong token is counted like a bad signature (S-4). With no allowed clients, nobody gets in. A key's label is only a display name, never a permission. |
| S-3 | Devices page | The **Devices** page is one list of four sections, in this order. **This machine**: the device name (S-11 — the label other machines see) and the machine's `SHA256:` fingerprint with a *Copy* button, for the person connecting to compare, plus **Copy public key**, which copies the line another host's owner can paste to allow this machine; the same key is what this machine signs in with as a client. **Connection requests**: the same list as on the Host page (H-18), with *Approve* and *Deny*, so a request can be answered here even when nothing is being shared; it is refreshed every second while the page is open. **Devices allowed to connect to this machine**: each by label and fingerprint with *Remove*, plus *Allow* to paste a new public key and *Remove every client*. Removing a device disconnects its running sessions at once, and that device is told it was removed rather than trying to reconnect. **Trusted hosts**: each with its name, the last address it answered at and its key fingerprint, *Connect* and *Remove*. There is no host/client split and no list of keys to manage: the one machine key serves both roles (S-9). |
| S-4 | Lockout on repeated failure | **3** bad signatures from one client key and address within a minute block that key from that address for **10 seconds**; a wrong QR token, sent by a device that has signed with its key, counts against the same limit for the address it came from, so a token cannot be guessed. Waiting for approval never counts as a failure. A host keeps at most **8** connections waiting to authenticate, turns away any further one, and drops any that has not authenticated within **10 seconds** of connecting. A connection the host does not let in — refused, or waiting for approval — is closed by the host about **2 seconds** after it has answered. It also keeps at most **16** connection requests, at most **one per address**, each for **10 minutes** (H-18). Other clients are unaffected. |
| S-5 | Control switch | The host can share with *viewers can control this machine* turned off, making every session view-only regardless of what viewers request. |
| S-6 | Consent to capture | On platforms that require it, the operating system's own permission prompts and screen-picker dialogs are used; Deskhub cannot capture without the user granting it. |
| S-7 | Explicit sharing only | Nothing is shared until the user starts a share. Closing or stopping ends all sessions. |
| S-8 | Trusted hosts follow the key | A client pins the key of every host it trusts — on first connection after the user confirms the fingerprint (C-2), including a `deskhub://pair/…` link opened from outside the app, or from the host's QR code scanned or pasted in the app (C-12) — and checks it before sending anything. Trust belongs to the key, not the address: a trusted host that moves to a new address is recognised there and connects without any dialog, and *Trusted hosts* remembers the new address as its last one. A different key at a known address is simply a host this machine has not met: the *New host* dialog appears as for any first connection, with a warning that the address used to belong to another trusted host, which stays in the list until the user removes it. The CLI refuses a host it does not know, prints its fingerprint, and saves it only when rerun with `--accept-new-host-key`; a host can also be pinned in advance (`host add ALIAS --address IP[:PORT] --host-key-stdin`), and `trust forget` takes a fingerprint, an alias or a last address. |
| S-9 | Machine key | Every machine has exactly one key, created on first run and never replaced automatically; it is the identity in both roles and there is nothing to generate, import or pick. *Copy public key* on the Devices page (CLI: `key public`) copies one line, `ecdsa-sha2-nistp256 AAAA… <device name>`, labelled with this machine's device name (T-27); that line is what a host's owner pastes to allow this machine (an `ssh-ed25519` line is accepted too), and what a host stores when it approves this machine's connection request or admits it by QR code. The private key never leaves the machine. Deleting the key file gives the machine a new identity: hosts that allowed it have to allow it again, and clients that trusted it are shown the *New host* dialog again. |
| S-10 | No carried-over access | Access settings from older versions are not converted. Coming from 7.0.x, every client has to be let in once more — by approval or QR code, or by pasting its key — because the key a client signs in with is now its machine key; any `client_key*.pem` and `host_cert.pem` left behind are ignored, never read or migrated. Older versions cannot connect to 9.0 and are told the versions do not match: 7.0.x, 8.0.0 and 9.0 do not talk to one another, so update every device. |

## 10. Settings

Settings are per machine, persist across restarts, and apply the next time sharing
starts. Phones and tablets expose only the device name (T-26), the network port (T-4),
clipboard sync (T-17), sharing sound (T-22), playing sound (T-23) and keep awake (T-19), plus the network to share on (T-9) on their
sharing screen; they host with the built-in defaults for everything else.

On the desktops the Settings page groups them into three boxes: **Host** for what only
sharing uses (T-1 – T-3, T-6, T-11, T-22 and the folder of T-25), **Client** for what
only watching uses (T-23), and **General** for what both sides use (T-26, T-4, T-13, T-15,
T-17, T-19).

| --- | --- | --- | --- |
| T-1 | Frame rate | 1 – 240 fps | 60 |
| T-2 | Bitrate | 1 – 1000 Mbps | 20 |
| T-3 | Quality | 720p · 1080p · 1440p · Native | 1080p |
| T-4 | Network port | 1 – 65535 | 47777 |
| T-6 | Viewers can control this machine | on / off | on |
| T-9 | Share on network | All networks · one of this machine's addresses | All networks |
| T-11 | Start sharing when the app opens | on / off | off |
| T-13 | Start Deskhub when you log in | on / off | off |
| T-15 | Keep running in the background | on / off | off |
| T-17 | Sync clipboard text | on / off | off |
| T-19 | Keep this device awake during sessions | on / off | on |
| T-22 | Share this device's sound with viewers | on / off | on |
| T-23 | Play the sound of the device you are watching | on / off | on |
| T-26 | Device name | up to 64 bytes of text | empty — the operating system's name for this machine |

| ID | Feature | Description |
| --- | --- | --- |
| T-7 | Automatic quality | Stream quality adapts on its own to the available network capacity within the configured limits; no user action is required when conditions change. |
| T-8 | Validation | On the desktops a number typed outside its range is pulled back to the nearest limit, and non-numeric text is ignored so the previous value stays. On phones and tablets a port outside its range, or non-numeric text, is not applied and the previous value is kept. |
| T-10 | Network fallback | When a specific network is chosen (T-9), the host is reachable only through that address. If that address no longer exists when sharing starts, the host shares on all networks instead and says so in the sharing status. A saved address that is currently unavailable is still listed, marked *not connected*. |
| T-12 | Auto-share on launch | Desktop only. With T-11 on, opening the app goes straight to the Host page and starts sharing with the saved settings, exactly as if the user had pressed Share. When the app is launched at login (T-13) the desktop may not have any display yet; sharing then waits, re-checking every half second for up to 30 seconds, and starts the moment a display appears. Until then the Host page says it is waiting. If no display ever appears, the app shares whatever else is ticked (the terminal) or stays idle with the reason on the Host page — an automatic share never opens a dialog box, because at login the window may be hidden in the tray where nobody would see it. The platform rules still apply: Linux shows the desktop's screen-sharing dialog the first time and reuses the remembered choice after that (P-3), and macOS still requires its permissions (P-2). |
| T-14 | Launch at login | Desktop only. With T-13 on: Linux writes an autostart entry into `$XDG_CONFIG_HOME/autostart` (`~/.config/autostart` when that is unset); Windows registers a scheduled task named *Deskhub* that starts the app elevated at logon, so no UAC prompt appears; macOS registers a Login Item the user can also see in System Settings. Turning it off removes that artifact again. The checkbox always shows what the operating system reports, not merely what was last saved. |
| T-16 | Background mode | Desktop only. With T-15 on, a tray / menu-bar icon appears with *Show/Hide window*, *Start/Stop sharing* and *Quit*; closing the window hides the app instead of quitting it, and sharing continues in the background. The window always appears on launch and hides only when the user closes it, so T-13 + T-11 + T-15 together start sharing at login with the window shown until it is closed. On Windows, left-clicking the tray icon shows or hides the window. On macOS the Dock icon disappears while the window is hidden; the menu-bar icon is there whenever T-15 is on, window open or not, and also appears when the window is closed while sharing. On Linux the tray needs a StatusNotifier host (standard on KDE; GNOME needs the AppIndicator extension) — without one, closing the window still quits, so the app can never become unreachable. On Windows and Linux, while sharing is active, closing the window always hides to the tray even with T-15 off (when a tray is available), so connected viewers are not dropped; on macOS, too, closing the window while sharing hides the app behind the menu-bar icon, and with nothing shared and T-15 off it quits, exactly like Linux. |
| T-18 | Clipboard sync | With T-17 on, plain text copied on any machine in the session appears on the others within a couple of seconds, in both directions; the host relays a viewer's copy to the other viewers. Text is capped at 32 KiB (longer copies are cut at a whole character); images, files and formatting are never transferred. The host's toggle governs the session: with it off, the host ignores and never sends clipboard data. Each machine also needs its own toggle on to read or write its local clipboard. On Android and iOS the operating system constrains this: an Android device picks up its own copies only while Deskhub is the app in the foreground, though incoming text is applied at any time; an iOS viewer may show the system paste prompt when Deskhub reads a fresh copy; and an iOS device that is hosting does not take part at all, because its broadcast runs in a separate process without clipboard access. |
| T-20 | Keep awake | With T-19 on, the machine does not go to sleep and the display does not turn off while it is sharing or viewing; the block is released the moment the share or the session ends, and no sleep settings are changed. A host holds it for as long as it is sharing, whether or not anyone is watching. On Windows, macOS and Linux this covers both display and system sleep for hosts and viewers alike (on Linux it needs systemd-logind and a desktop that honours the freedesktop screensaver interface — standard on KDE and GNOME). The operating system still wins where it insists: closing a laptop lid, pressing the power button, or macOS on battery power may still sleep the machine. On Android and iOS the toggle keeps the screen on while viewing a stream, and on Android also while a shell window is open; sharing from a phone already survives the screen turning off (P-5), so hosting there does not hold the screen. |
| T-25 | Where files land | Desktop only. Files viewers send are written to a folder this machine chooses — `Deskhub` in the user's home folder unless another is picked. The chosen folder is named on the live table's *File transfer* row while sharing (H-17), with an **Open folder** button beside it — not before sharing starts, since the folder has no effect until then. It is created if it does not exist, and the choice is saved with the other settings. Nothing outside that folder is ever written: a sender's name is stripped to its last path element and scrubbed of anything the local filesystem cannot store. |
| T-27 | Device name | Settings → General → *Device name* names this machine everywhere: viewers see it when it hosts (H-7), clients it admits see it in their recent list (D-5), hosts see it when it connects (C-7), and it labels the public key it copies and the key a host stores when it approves this device or admits it by QR code (S-9). Left empty, the operating system's name for the machine is used: its hostname on Windows, Linux, macOS and iOS, and the device model on Android. On macOS and iOS the empty field and the Devices page show the system's device name as a hint, but what other machines see and what labels the key is the hostname. Control characters are removed. |
| T-24 | What sound is shared | With T-22 on, the host shares what its own speakers are playing — the mix every application on it produces. It never captures a microphone: Deskhub has no two-way audio. Android is the one platform where a permission is involved at all — its playback-capture API sits behind the permission the system labels *Microphone*, which the app asks for when a share starts and uses for nothing else; decline it and the share goes ahead without sound. No other platform asks for a microphone permission. A viewer only receives sound if it asked for it (T-23), so a host with T-22 on sends nothing to a viewer that is not listening, and both toggles take effect the next time a session starts. |

## 12. Platform-specific behaviour

| ID | Platform | Behaviour |
| --- | --- | --- |
| P-1 | Windows | The app asks for administrator rights once at start, which is what allows it to type into elevated windows. It adds its own firewall rule when sharing begins, and only ever replaces or removes rules it created itself — a rule the user made, such as one blocking Deskhub, is left alone. |
| P-2 | macOS | Shows a **Permissions** panel with the live grant state of *Screen Recording* (needed to share) and *Accessibility* (needed to accept remote input), a button to request each, and a shortcut into System Settings. Some keystrokes are silently blocked by macOS unless Accessibility is granted. |
| P-3 | Linux | The Host page lists this machine's displays and the terminal as tick boxes, like the other desktops, and only the ticked displays are shared. The desktop still confirms the screen capture in its own screen-sharing dialog after pressing Share; that confirmation is remembered where the desktop supports it (ScreenCast portal version 4+): later shares reuse it silently, including across restarts, so the dialog appears only the first time. If none of what the desktop granted matches the ticked displays, the remembered confirmation is forgotten and the dialog is shown once more, so the user can grant the right displays; if the desktop rejects or has expired the confirmation — after a compositor upgrade or a monitor change — the dialog simply appears again, and cancelling it never retries. If the desktop grants displays the app cannot match to the ticked list, everything the desktop granted is shared rather than nothing. Ticking only the terminal skips the desktop dialog entirely. Sharing additionally requires the system to permit input injection. |
| P-4 | Android / iOS | Hosting is **view-only**: the device streams its screen and silently drops every control packet, because neither OS lets an app inject input system-wide. It shares no terminal — and says so when asked, so no client opens a terminal window against a phone (C-8) — and the desktop clients can say the control tick will do nothing (C-3). It takes files from the moment the app is on screen, under the batch rules of H-16, with no switch to find, and keeps taking them while the screen is being shared, so a viewer can watch the screen and send files to it at the same time; on iOS the broadcast extension holds the one port for the length of a broadcast and serves both from it. Photos and videos it receives are added to the device's photo library — on iOS behind the system's add-only Photos permission, asked for the first time one arrives and never granting Deskhub any read access, with the file going to Documents instead if it is declined; on Android to `Pictures/Deskhub` and `Movies/Deskhub` through the system media store. Every other file lands where the system file browser can see it (the app's Documents folder on iOS, `Download/Deskhub` on Android), and a notification names what arrived. The Android media store this uses needs Android 10: on Android 9 and older an arriving file stays in the app's own folder on the device, out of the gallery and out of Downloads. The whole screen is shared as a single source, so the display picker, multi-display sharing and per-display stop (H-1, H-2, H-3, H-5) do not apply. While hosting, a phone shows the same **Show QR code** button (H-6) and **Connection requests** list with *Approve* / *Deny* (H-18) as a desktop. Turning the device turns the stream with it: what viewers see stays the right way up, and their window re-fits to the new shape (V-1). The session UI is touch-first: trackpad gestures, zoom controls, hotkey bar, on-screen keyboard, display switcher, and a close button in the corner shared with the shell and file-transfer screens. |
| P-5 | Android | Sharing needs the system screen-recording consent dialog, which is granted per share and cannot be remembered, and sharing sound additionally needs the permission Android labels *Microphone* — its playback-capture API is gated behind it — asked for when the share starts; declining it shares the screen without sound. While sharing, an ongoing notification is shown and the stream survives the app going to the background or the screen turning off. Stopping the share from the system notification ends the session. The `CAMERA` permission is asked for only when the user taps *Scan QR code* (C-12) and is used for nothing else; the frames are decoded on the device. On Android 13 and newer the app asks for permission to post notifications when it opens; declined, the connection-request (H-18) and files-arrived (P-4) notifications are not shown, and everything else works as before. |
| P-6 | iOS | Sharing is started from an in-app **Start sharing** button which opens the system broadcast sheet, because iOS requires that sheet to confirm every broadcast, and runs in a separate broadcast process so it continues after the app is closed. The sharing screen reports the number of connected viewers — listing the names of those that have set one (C-7) — and the broadcast process's current memory use — iOS ends a broadcast that grows past its memory limit — without the per-viewer table of H-7, and viewers cannot be dropped individually (H-8). It does show the QR code (H-6) and the connection requests (H-18): the broadcast process writes each request to the folder the two processes share, the app lists it, and an *Approve* in the app is what the broadcast process reads on the device's next attempt. A system event that ends the broadcast — an incoming call, for instance — ends the session. A session open when the app leaves the screen — a stream, a shell or a file transfer — is kept alive for as long as iOS grants an app that has left the screen, around half a minute, so a short look at another app does not drop it; beyond that the system suspends the app and the session reattaches by itself when it comes back (V-8). Camera permission is asked for only when the user taps *Scan QR code* (C-12) and is used for nothing else. |

## 13. Explicitly out of scope

Deskhub does **not** provide, and this specification does not cover:

- Microphone capture, two-way audio, or any voice channel. Sound travels one way only,
  from the shared machine to the people watching it (V-6).
- Remote printing.
- Clipboard sync beyond plain text (images, files, rich text).
- Any account, directory or presence system, and any invitation that travels through a
  service: the QR code a host shows (C-12) is read off its screen or pasted by hand, and
  nothing carries it between machines on the user's behalf.
- Discovery, relay, rendezvous or NAT-traversal service — reaching a host over the
  internet is the user's responsibility (for example via a VPN).
- Session recording.
- Unattended access, wake-on-LAN, or remote power control.
- Multi-user administration, roles, or audit trails.
